# 二、方案
## （一）业务背景与问题痛点
网络团队日常工作主要分为 **2大方向：网络运维与网络变更**，针对这些方向，我们重点聚焦，逐个突破，把 AI 内化提效切实应用落地到每个实际场景中，**真正实现「把 AI 从成本转化为生产力」**

### 1.1 网络运维
#### 那些「扎心」的运维痛点
凌晨三点昏暗的灯光、永远响不完的告警电话、反复核对的配置命令、故障时被催问的焦灼——这些场景，每一位网络工程师都刻骨铭心。身处云时代，面对数以万计的设备与千万级的端口规模，以及业务侧日益严苛的质量要求，传统运维“依赖经验+堆砌人力”的模式早已难以为继。**运维做得越久，越能体会那种“痛在身上，急在心里”的滋味：**

**1. 被禁锢的工作模式：为何不能更快捷？**

我厌倦了必须掏出电脑、敲击一堆复杂命令才能查看问题的日子。我期望的 AI 时代，手机即是作战终端——无论是在用餐还是通勤，只需简单的自然语言交互，就能完成故障排查、隔离与止损。**让运维从“重型终端”解放，转向“随时随地”**

**2. 被割裂的数据孤岛：为何获取真相这么难？**

为了验证一个机房的网络异常，我往往需要跨越 5 个以上的平台，反复输入查询条件，在碎片化的数据中艰难拼凑真相。我期望平台能“读懂”我的意图，**不再是我去一个个系统里“找数据”，而是想要的数据能自动“找上门”**

**3. 被琐事淹没的价值：为何总在救火？**

我们在这个劳动密集型的怪圈里陷得太深，每天被海量的收尾工作和琐碎杂事填满，根本无暇顾及网络的深度分析与架构优化。我们急需一套具备“自闭环”能力的系统，自动消化那些繁琐的重复性工作，**让工程师从“搬砖”中抽身，去构建一个更具鲁棒性的网络**

##### 总结一下网络运维工作中的痛点
**难以快速GET到想要的数据**

日常运维工作中为了解决一个问题需要查询很多的平台，而且平台的信息不直观、各种查询条件的反复输入，不能通过平台中的数据快速获取到想要的内容。如为了排查一个机房是否存在网络异常的问题，运维同学往往需要查询5个以上的平台数据，才可以得出最终的结论



**工作模式还是太传统**

我期望在吃饭期间、坐车期间，就能把问题排查了、处理了、解决了，我不希望掏出电脑霹雳啪啦搞一堆命令，去看一个不知所云的问题，我期望手机是我的工作终端，可以支持问题排查、设备交互、隔离止损，这种才是AI时代运维同学期望的工作模式



**日常工作太多太杂**

网络很多问题都是在处理事后的收尾工作，全网将近10w台网络设备，300w个模块，其实有很多分析和优化的工作需要很多精力和投入，找到对应答案让网络变得更好，但当下光是处理这些杂七杂八的工作就已经让现在工程师应接不暇了，应该有自闭环的系统，把繁琐且量大的工作自我完善，不希望看到网络成为一个劳动力密集型的工作



**被动式运维策略**

当前网络系统的鲁棒性主要依赖冗余架构建设与高度自动化的故障恢复机制。目前，我们的平均故障修复时间（MTTR）已优化至6.14分钟，但这仍属于在故障发生后压缩定位与恢复时间的范畴。长期来看，此类事后治理手段的边际效应逐渐递减，使得进一步提升 MTTR 的成本面临瓶颈。同时，任何实际发生的故障，即便是毫秒或微秒级的中断，均可能对客户业务造成影响，大客户的用户体验难以保障

### 1.2 网络变更
#### 「变更之痛」带来的挑战
随着业务迭代速度呈指数级增长，系统变更的频率与复杂性也急剧攀升，而我们依赖的传统“人肉”模式已难以为继，成为业务稳定性的核心瓶颈，我们虽然在24年完成了白屏化等变更自动化的突破，但其本质还是对传统变更的平台化提效。除了为后续无人值守AI变更打好基础外，并没有打破其固有瓶颈：为此我们做过详细的工程经验统计，**一次完整的****变更，其中80%的工作量以及90%的风险，都存在于前期的准备阶段**；包含从配置的编写、提交、审批，哪怕一个简单的配置编写、操作表单的填报往往需要耗费3~5小时的时间，甚至超过1天，严重拖慢业务快速试错与上线节奏。更关键的是，在审批环节，由于**完全依赖人工判断，其决策质量深受审批人的经验、了解程度、责任心及疲劳程度等不确定因素影响**，存在显著的“非主观失效”风险，使得审批这一关键控制点的质量难以得到持续保障。所以AI+变更的模式自然而然就优先成为了我们下一个目标。

##### 当前工作模式
我们现行的变更机制本质上是依靠“人海战术”来保障质量，但实际效果有效但很难长期维持，具体来说，网络各方向同学会提前一周花费数天时间完成所有变更单的线上编写提交等准备工作，同时次周需要组织十几位同事共同投入一到两小时，集中审核大量且复杂的变更单。面对成百上千条命令，评审者很难在短时间内发现所有细微差错（例如少打一个空格，单词拼错误等低级笔误）。历史上我们已经因此出现过线上故障，这证明当前模式无法根除风险，是流程上的一个关键瓶颈。

可能有一些研发或者非网络专业的同学会疑惑，为什么2025年的今天我们为什么还在执着在变更的编写和审核阶段，而且手段还如此传统，或者很难理解这些稀松平常的低级的语法错误到底有什么风险，是不是过度紧张了，亦或者觉得写bug那是不是因为工程师水平的问题？提高了就好？

其实，简单点形容 **“网络变更，就像是直接在生产环境数据库上执行 SQL或者修改Schema，而且没有备份，也几乎没有回滚机会。”  **同时我们也尝试从下面几个方向与我们当前的研发环节进行类比：



* **没有“编译”阶段：风险前置，无处隐藏**
    * 写代码时：有编译器、解释器、IDE作为第一道防线。它们会实时检查语法错误、类型不匹配、未定义变量等低级错误。一个分号错误都通不过编译。
    * 写网络配置时：网络CLI更类似一种伪代码，行业内并没有通用的标准，更**没有“编译器”，**不同厂商型号都回存在自己私有的语法和逻辑，而且绝大多数命令行语法逻辑互斥，设备只是简单直接的接受并执行。一个拼写错误、一个错误的IP地址，设备不会提示你，它会“忠实”地执行这条错误指令，然后静待灾难发生。所以**网络变更要求100%的“一次写对”，且所有语法检查都依赖人脑完成。**

* **匮乏的测试环境：从“模拟器”到“真枪实弹”**
    * 写代码时：拥有从本地环境、测试环境、沙盒环境、预发环境到生产环境的完整链条，可以在无限接近真实的环境中进行充分验证。
    * 测试网络变更时：网络设备全部为物理硬件，拓扑极其复杂，所谓的测试环境往往只是**一个“功能模拟器”**，无法100%复现生产网络庞大的流量、复杂的路由策略和异构的设备交互。很多问题，只有在生产环境“真枪实弹”地执行时才会暴露。**网络变更更多依赖于理论推演和审单人的经验和技术能力。**

* **没有绝对的“灰度发布”和“快速回滚”：箭已离弦，覆水难收**
    * 写代码时：可以通过金丝雀发布、分批发布等手段，先让1%的流量验证新功能。一旦出错，可以秒级回滚到上一个稳定版本
    * 执行网络变更时：**变更本身就是在修改“公路”本身**。改一条核心路由，就像是瞬间拆掉了所有车流都在使用的立交桥。影响是全局的、即刻的。回滚？敲下no命令可能需要时间生效，而网络协议收敛、路由重建更需要时间，这有可能就是几分钟到几十分钟的服务中断，"雪崩"这件事在网络看来十分容易。**网络变更的“发布”是非原子性的，其“回滚”也不是一键秒级，而是痛苦的抢救或者止损过程。**

* **不可控的“爆炸半径”**
    * 代码中的一个Bug：通常影响的是一个服务、一个API、一个功能模块。它的影响范围通常是可控、可隔离的。
    * 网络配置中的一个错误：其“爆炸半径”是整个网络平面。一条错误的路由可能导致**一个机房、一个地域、甚至所有用户的访问中断**。网络配置错误是系统性、平台级风险，其影响范围是指数级放大的。




所以在软件研发中，责任由“编写、测试、发布”等多个环节共同分担。而在网络变更中，由于测试和验证环节的缺失，绝大部分的责任和风险，都前置并压在了“编写”和“审单”这两个纯粹依靠人脑的阶段。这也是为什么我们之所以对待变更如此谨慎甚至“苛刻”，但又略显“落后”的原因

|**环节**|**当前传统变更**|
|-|-|
|**1. 写变更单（发起）**|手工填写表单：需手动输入变更命令、原因、影响范围。**依赖个人经验，容易遗漏细节或写错命令。**沟通成本高：需自行联系相关系统负责人确认影响|
|**2. 审变更单（审批）**|人工风险评估：审批人依靠个人经验和有限的精力进行主观判断。量变导致质变：过多冗长的代码量以及复杂逻辑，将**大幅度提升隐患风险**信息不对称：审批人可能不了解全部细节，增加决策风险。|
|**3. 执行变更单（实施）**|手动操作：工程师在变更窗口手动执行命令，易产生误操作。被动监控：执行后人工观察监控，**发现问题滞后**。缓慢回滚：一旦失败，需查找回滚方案并手动执行，故障时间长。|
|**4. 闭环与复盘**|文档滞后：复盘报告需人工整理，常常遗漏细节。经验流失：**成功的经验和失败的教训难以沉淀到组织流程中。**|

## （二）项目方案/解决方案
### 2.1 网络运维
#### 2.1.1 AI聚屏 --- 数据可视化只是第一步
在高度数字化的今天，网络早已超越成本中心，成为驱动业务的核心引擎。我们手中掌握着日志、流量、成本、IP等高质量数据富矿——这些不仅是运维指标，更是能够“开口说话”的战略资产。通过深度挖掘，它们足以构建起一个洞察全局的“战略仪表盘”，为网络架构优化、精准扩容及成本管控提供前所未有的数据驱动依据，让决策先于问题。



但是将数据价值高效可视化的传统路径却充满挑战。无论是重大活动保障、日常值班还是周期性复盘，一张定制化数据大屏往往需要经历“提需求-评审-研发-测试”的漫长流程，牵扯多方人力，成本高且响应迟缓，难以跟上业务快速迭代的节奏，所以这也是掣肘我们的难题。



但转机在AI时代，过去难以规模化的定制需求，如今在AI的赋能下正变得游刃有余。我们构想这样一种模式：**通过自然语言描述或简单配置，由AI理解业务意图，自动生成精准、美观且可交互的数据大屏****。** 这不仅能将开发资源从重复劳动中解放出来，更能实现“按需所见”的即时数据分析能力，让每一位网络专家都成为数据的策展人，真正释放数据的潜在威力，引领网络运维进入智能化的新阶段。**让****可视化成为从 "被动运维" 转向 "主动运营" 的第一步**

##### **实现方式**
|**对比维度**|**传统大屏生成**|**AI生成大屏**|
|-|-|-|
|**核心逻辑**|手工匠造：像定制西装，精确但周期长。|智能涌现：像用“魔法画笔”作画，描述即所得。|
|**启动方式**|需求文档：需要撰写详细的需求说明书。|自然语言指令：直接描述想要什么。|
|**生成过程**|编码与配置：前端工程师写代码，连接数据源。|解析与创造：AI理解意图，自动编排布局和图表。|
|**核心技能**|编程能力（如JavaScript, SQL）、设计能力。|业务理解能力、提问和沟通能力。|
|**迭代成本**|高：任何改动都需要开发人员修改代码并测试。|低：通过对话即可实时调整，秒级响应。|
|**人力与时间**|多人协作，数天至数周。|单人主导，分钟级。|

系统部作为基础设施后端团队并没有深厚的FE资源，但依然可以利用公司级前端低代码框架（amis），加持LLM即可实现多样的前端渲染，人人都可以是UI/UE/FE。整个过程只需要 三步 ：

1. **依托MCP完成所有后端数据的改造，并通过 RAG+网络数据湖 实现所有数据模块的关联查询及格式化处理**
2. **基于百度低代码框架Amis + 大语言模型能力 完成定制化数据展示组件**
3. **根据自然语言意图，多Agent协作，最终绘制数据大屏绘制**

只需这三步我们可以完成所有想要的数据可视化，无论是用于一次性工作、统计汇报、数据分析，都可以实现分钟级的创建和销毁。

##### **总体流程&技术架构图**
[流程图]


在架构中使用的amis，是一个低代码转化成前端语言的组件，简单说，amis 是可以把 “写 React 组件代码” 变成了 “写 JSON 配置”，框架会自动把 JSON 转成对应的 React 组件，并渲染出来。

拿一个表单页面举例，如果用React组件，通常需要写成如下这样：

```
<Page title="页面标题" subTitle="副标题">
  <Form title="用户登录">
    <InputText name="username" label="用户名" />
  </Form>
</Page>
```
把以上配置方式转换成 amis JSON，则需要写成如下这样

```
{
  "type": "page",       // 对应React的<Page>组件
  "title": "页面标题",  // 对应Page的title属性
  "subTitle": "副标题", // 对应Page的subTitle属性
  "body": {             // Page的子组件（对应<Page>的子元素）
    "type": "form",     // 对应React的<Form>组件
    "title": "用户登录",// 对应Form的title属性
    "body": [           // Form的子组件（对应<Form>的子元素）
      {
        "type": "input-text", // 对应React的<InputText>组件
        "name": "username",   // 对应InputText的name属性
        "label": "用户名"     // 对应InputText的label属性
      }
    ]
  }
}
```

Agentic Workflows（智能体工作流）是一种由‌**AI智能体驱动的新型工作流范式**‌，通过任务分解、工具调用、动态决策与迭代优化，实现复杂任务的自动化处理。其核心在于赋予工作流‌**自主性、目标导向和环境适应性**‌，与传统预设规则的工作流有本质区别

* **核心特征**‌

    1. ‌**自主决策**‌：AI智能体可根据任务目标动态规划路径，无需固定预设步骤，实时调整策略
    2. **‌结果导向：**以结果为目标驱动任务分解，按需调用工具（如API、数据库），灵活适应复杂场景
    3. ‌**环境交互与迭代优化**‌：智能体通过感知环境反馈（如用户输入、数据变化）持续优化执行过程，提升任务成功率
    4. ‌**动态工具调用**‌：根据任务需求自主选择工具，而非依赖预定义工具链

* ‌**与传统工作流的对比**‌

|‌**特性**‌|‌**传统工作流**‌|‌**智能体工作流**‌|
|-|-|-|
|‌**执行逻辑**‌|固定规则，线性流程|动态规划，实时决策|
|‌**适应性**‌|需人工干预调整规则|自主响应环境变化|
|‌**工具调用**‌|预设工具链|按需动态调用工具|
|‌**适用场景**‌|标准化、低复杂度任务|多步骤、高不确定性复杂任务|

#### 2.1.4 **光模块故障预测 --- 运维策略“左移”**
我们正迈入稳定性建设的新阶段，致力于从**“韧性”维度**提升网络可靠性，推动**运维策略“左移”——即从被动响应转向主动预测**。通过在故障实际发生前进行有效预测与干预，最大程度避免客户感知到异常，从而持续提升客户对稳定性的满意度。

**实现原理细节**

**1，模型训练相关工作 & 特性：**

* **采样频率**：DDM/30 min，FEC/1 min；出现中断会记录并关联维修动作（清洁或更换）
* **窗口构造**：每个样本为**同步的 24 小时时间窗**，包含 **15 个特征**（14 个 DDM + 1个 BER）；缺失 FEC 的模块对相应字段 **零填充并用掩码标识** 
* **清洗与对齐**：按模块编号分组，进行**平滑/对齐**；删除监控系统随机填充的**噪声/异常值**；按模块编号随机**划分**训练/验证/测试
* **归一化**：DDM 线性插值 + z-score；FEC 先取对数再 z-score
* **正负样本**：正样本为**模块更换事件**（315），负样本为**在网 400G 模块**（1498）
* **防过拟合**：早停、正则化、权重衰减



**2，训练过程：**

**FGL（**Future-Guided-Learning**） 如何工作**

* **学生/教师**：教师在“未来段”的 DDM/FEC 上训练，获得更贴近失效临界区的表征；训练时，用**KL 蒸馏**把教师的“软目标”传给学生，学生仍以**二分类**（故障/正常）的 **BCE** 为主损失，同时加入蒸馏损失；**温度系数 τ** 控制分布平滑（硬化 / 软化），**α**平衡监督与蒸馏项 
* **直观理解**：临近故障前，**光功率参数出现细微异常波动**；教师先学到这些“未来特征”，再用蒸馏让学生在“过去窗口”里也能捕捉到

学生模型的损失函数定义：

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=6f653ee430e343cd9eacc20d2f01ccc2&docGuid=Mr35OTiVPipbwR "")
* **ℒ_CE(z_s, y)**：交叉熵损失
    * **z_s**：学生模型的原始输出分数
    * **y**：真实标签（0=正常，1=故障）
    * **作用**：确保学生模型的基本判断正确

* **α**：平衡权重（0-1之间）
    * **作用**：控制教师对学生的影响力


**进一步分解说明**：

1. **softmax(z_t/τ) 和 softmax(z_s/τ)**

    * **z_t**：教师模型的输出分数
    * **z_s**：学生模型的输出分数
    * **τ**：温度参数
    * **作用**：将原始分数转换为概率分布

2. **τ的作用**：

    * τ=1：正常概率分布
    * τ>1："软化"概率分布，让次要信息更明显
    * **类比**：不仅告诉你正确答案，还告诉你其他选项为什么错

3. **D_KL(P || Q)**：KL散度

    * **测量两个概率分布的差异**
    * P = 教师模型的输出分布
    * Q = 学生模型的输出分布
    * **目标**：让学生模型的输出分布尽量接近教师模型

4. **τ²**：缩放因子

    * 补偿温度参数对梯度大小的影响
    * 确保训练稳定性

##### **实现方案**
**智能生成变更单**

* 提取变更平台对应OPEN API Schema提供给Agent，同时辅助RAG（有些和百度网络相关的背景信息需要靠RAG补充） + 不同场景的Prompt模版（使用MCP Server进行管理），再结合用户输入的自然语言描述的需求（支持多轮交互修正补齐），实现通用场景变更单生成能力



**智能审核变更单**

1. 变更检查命令 & 变更执行命令 & 变更回滚命令分别审批，全量覆盖
2. 加入RAG（厂商手册），降低审单幻觉，提升审单准确率
3. 基于积累的变更单历史数据（历史经验的沉淀，有成功和失败的案例），进行模型训练、微调，让AI具备参考历史来判断当前的能力，进一步提升审单准确率
4. 引入自我反思架构（一个模型输出 + 另一个模型double check审批，如果有问题则反馈具体问题到第一个模型，第一个模型根据第二个模型的反馈结果进行反思，重新进行处理），实际测试观察到准确率确实会有进一步的提升，因为反思模型还会外挂之前积累的「历史审核错题集」
5. **🏋️ ****训练微调全流程（基于百度千帆平台）**
    1. 收集过往正例（从历史变更单中提取）
    2. 数据清洗（可能存在设备替换变更操作，导致当前厂商型号和操作命令不匹配的情况）
    3. 数据均衡，因为历史数据中变更失败的反例相对于变更成功的正例比较少，使用LLM基于少量的高质量的种子数据构造反例（日常积累的各类型错误的变更单），并逐个进行人工标注
    4. 指令遵循（SFT） + 偏好对齐（e.g., KTO、DPO）进行多轮训练调整，并持续观察效果
