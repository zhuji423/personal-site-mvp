# 背景


**Specification-Driven Development（SDD）** 作为一种“先写规范、再由 AI 生成代码”的工作模式，近期受到广泛关注。其核心理念是通过结构化文档（Spec）明确需求、设计与验收标准，为 AI 提供稳定、一致的上下文，从而提升生成代码的准确性与可维护性。



**结合自身的实践感受与同行的分享，总结了SSD的以下优缺点：**



### **优点**
### **缺点**
#### **1. 设计可沉淀**
将原本散落在聊天记录或口头沟通中的需求固化为文字资产，避免信息流失；

#### **2. 上下文更完整**
相比零散指令，完整 Spec 能减少 AI 的歧义理解；

#### **3. 支持协作分工**
产品、测试、开发可在同一份规范上协同，尤其适合跨角色团队；

#### **4. 利于长期演进**
当项目复杂度上升时，规范可作为重构或交接的依据。

#### **1. 流程重**
小功能需撰写大量描述性文档，投入产出比；

#### **2. 上下文膨胀**
Spec 越写越长，反而稀释关键信息，增加 AI 理解负担；

### **3. 维护成本高**
需求变更需同步更新 Spec，否则文档迅速失效；

#### **4.适用场景有限**
对简单、内部、低频变更的服务模块，收益远小于开销；

#### **5. 易产生“虚假完备感”**
看似设计周全，实则缺乏真实编码反馈，反而抑制迭代灵活性。



在最近的日常迭代中，尤其是在编写 rules 相关的新代码库 时，频繁需要新增 / 修改接口或实现小功能。这些需求通常**逻辑清晰、边界明确、复杂度低**，但**节奏快、数量多**。若采用完整的 Spec-Driven 开发流程——包括撰写研究文档、产品故事、技术规范、验收标准、执行计划、任务拆解等内容，再经过评审、存档与多方同步——不仅会显著拖慢开发速度，还容易因维护成本过高导致文档迅速过时、失去参考价值。

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=91452bb011914327964f15be7d51f859&docGuid=XQiSVeyzikPN0G "")


而另一方面，若完全放弃规范，仅依赖口头约定或临时指令，则会导致**接口契约模糊**。在引入 Coding Agent（如 Claude Code）辅助编程时，极易因上下文缺失而产生**误解、重复返工，甚至生成不一致的代码**。因此，我们希望尝试一种**介于“无规范”与“重型 Spec”之间的中间态**：

* **聚焦最小可行接口契约**，不追求完整的产品级 Spec；
* **以接口文档作为人与 AI 协作的上下文载体**，内嵌机器可读的状态元数据（如 `implemented: false`）；
* **通过命令的形式形成可复用的实践**（如 `/implement_api`）；
* **自动更新文档状态**，确保契约始终可信、可追溯。



# 目标
让 Markdown 接口文档成为项目演进的**结构化上下文源**，能够被 Coding Agent 自动解析、理解并用于生成或修改代码。通过状态元数据（如 `implemented`、`sync_status`）记录接口的生命周期，使文档不仅能描述“应该是什么”，还能反映“当前是什么”，从而为后续任务提供准确、可追溯的变更上下文。



### 长期演进方向
在实现接口级契约闭环的基础上，逐步构建 **项目级变更上下文的自动维护能力**，使整个代码库的演进过程对 Coding Agent 透明、可追溯：

* **自动聚合接口变更**：基于文档状态变化（如 `implemented: false → true`）或代码 diff，自动生成结构化的“本次变更摘要”，包括新增/修改的接口、影响的服务、关联的数据模型等。



* **维护项目演进日志**：将每次任务产生的上下文（需求意图、生成逻辑、状态变更）沉淀为机器可读的变更记录（如 `CHANGES.md` 或 `context.json`），形成轻量级“系统记忆”。



* **支持增量式上下文召回**：当 Coding Agent 执行新任务时，能自动检索相关历史变更上下文（例如：“上次修改 tag 接口时用了 Redis 缓存”），避免重复设计或逻辑冲突。

## 核心开发约定

### 代码组织规范
```
com.baidu.bapi.vibecommunity/
├── controller/    # REST API控制器，统一前缀/api/v1/
├── service/       # 业务逻辑接口
│   └── impl/      # 业务逻辑实现
├── repository/    # 数据访问层，Spring Data JPA
├── model/         # JPA实体类
├── dto/           # 数据传输对象
├── vo/            # 值对象，Controller返回
├── config/        # 配置类
├── aop/           # 切面编程，用户认证拦截
├── context/       # 用户上下文管理
├── util/          # 工具类
└── web/           # 全局异常处理
```

### 命名约定
- **类命名**: 实体无后缀，控制器`Controller`，服务`Service`+`ServiceImpl`，数据访问层`Repository`，DTO/VO加相应后缀
- **方法命名**: 查询用`find`/`get`，删除用`delete`，转换用`fromEntity`/`toVO`
- **数据库字段**: 下划线命名(`created_at`)
- **URL命名**: camelCase格式，统一前缀`/api/v1/`

### 数据流模式
**Entity → DTO(Service层) → VO(Controller层)**
- 使用静态工厂方法转换: `ContentDetailDTO.fromEntity(entity)`
- 使用`toVO()`方法最终转换
- 分页使用自定义`PageResponse`包装

### 事务与异常管理
- **事务注解**: `@Transactional(rollbackFor = Exception.class)`
- **全局异常处理**: 统一使用`ResponseBodyWrapper`包装响应
- **异常分类**: 4xx客户端错误(warn日志)，5xx服务器错误(error日志)

### 审计与软删除
- **自动审计**: `@EntityListeners(AuditingEntityListener.class)` + `@CreatedBy`/`@LastModifiedBy`/`@CreatedDate`/`@LastModifiedDate`
- **软删除**: `status`字段(1=正常，0=已删除)
- **禁用DDL**: `spring.jpa.hibernate.ddl-auto=none`

### 配置管理
- **环境变量驱动**: `${ENV_VAR:default_value}`模式
- **敏感信息**: 通过环境变量注入(密码等)
- **多环境支持**: 本地/测试/生产配置分离

### 日志规范
- **英文描述**: 所有日志message必须使用英文

### 认证与权限
- **统一认证**: AOP拦截器处理所有请求
- **用户上下文**: ThreadLocal存储当前用户信息
- **IP白名单**: 支持配置IP访问控制

### 开发流程
1. **文档优先**: 需求开发前先修改相关文档(`document/design.md`等)
   - 系统设计文档：document/design.md
   - api 文档：document/api_doc.md
2. **人工确认**: 文档修改后需人工确认再开始开发
3. **代码规范**: 遵循命名约定和包结构规范
4. 不需要每个需求都新建文档，优先修改文档。新建文档之前需要发起询问。

## 技术集成要点

### 数据库配置
- **连接池**: HikariCP，精细化配置(min-idle=5，max-pool-size=5)
- **JPA配置**: 显示SQL格式化，关闭Open EntityManager
- **查询优化**: 批量查询避免N+1问题，使用Projection进行统计

- **备用队列**: Kafka，相同消息处理逻辑
- **幂等性**: `@MQIdempotent`注解确保消息幂等性

### 缓存策略
- **Redis支持**: 可配置缓存前缀和过期时间
- **连接池优化**: 支持Redis连接池配置

### 第三方库使用
- **JSON处理**: FastJSON2
- **文档生成**: springdoc-openapi-ui

### 命令: /api_design
```

argument-hint: [功能需求描述]
description: 根据功能需求生成或更新标准化的 HTTP 接口文档草案（Markdown），支持新增与修改场景，带状态元数据
---

## 目标
根据用户提供的功能需求描述，**生成或更新**标准化的 HTTP 接口文档草案（Markdown 格式）。该文档将用于后续开发与同步，必须包含结构化元数据以便状态追踪。
- 文件路径建议为：`document/apis/<module>/<module>_api.md`
- 从`document/apis/`中选择符合用户需求的模块，若不存在则新建相应模块（如 “标签”、“用户”、“内容” → 映射为 tag, user, content）
- 若需求指向已有接口，则视为修改操作，分析修改要点

### 重要原则
- 仅处理需求中明确提及的接口，禁止过度解读
- 不确定是否已有接口时，必须反问，不得猜测
- 当前任务仅针对文档，不得擅自编写代码

## 输入
输入为用户需求，需结合现有文档以及代码确定是新增接口还是修改已有接口。若描述模糊，应要求澄清，而非猜测。

### 接口状态元数据
每个接口必须插入以下 HTML 注释形式的元数据块：
```html
<!-- api-meta
implemented: false
sync_status: OUT_OF_SYNC
checked_at: N/A
-->
```

- `implemented`: 后端是否已实现（初始 `false`）
- `sync_status`: 文档与代码是否一致（初始 `OUT_OF_SYNC`）
- `checked_at`: 最近核对时间（初始 N/A）；同步更新`sync_status`和`checked_at`

### 待修改内容（仅当为修改接口时出现）
说明接口变更的内容，例如：
- 请求参数增加 username
- 补充权限校验

### 接口内容
接口应包含以下信息：
- 功能说明
- URL / Method
- 请求参数（表格）
- 请求示例（JSON）
- 响应结构
- 响应示例（JSON）

### 简要实现思路
**描述简要实现思路即可，不要罗列具体大段代码**。例如：
- 参考xxx接口实现
