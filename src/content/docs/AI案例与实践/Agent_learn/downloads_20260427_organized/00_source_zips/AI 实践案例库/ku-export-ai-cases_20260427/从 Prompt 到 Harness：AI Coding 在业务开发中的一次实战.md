# **从 Prompt 到 Harness：AI Coding 在业务开发中的一次实战**
*—— 从一线需求开发中提炼 Agentic Engineering 的架构原则*

---

## 引言：为什么我要亲自写代码
在小度加龙虾的封闭开发中，我近距离观察了团队使用各类 AI Coding 工具的全过程。一个明显的发现是：虽然工具已经普及，但不同人使用出的效果差异巨大——同样的 Agent，有人用它完成了完整的需求闭环，有人还停留在"问它一段代码怎么写"的阶段。

过去我们争论 Vim 还是 Emacs，本质上是个人偏好问题，只要技能足够熟练，用什么工具都能高效产出。但 AI Coding Agent 不同。它不再是纯粹的编辑器，而是一个"智能体"，你与它协作的方式直接决定产出质量。更重要的是，它正在改变整个研发体系的瓶颈分布——哪些环节变快了，哪些环节反而成了新的卡点，这些变化对架构设计和团队组织都有深远影响。

为了拿到第一手感受而非泛泛而谈，我选择亲自下场，用真实的业务需求来验证一个假设：**如果为 Agent 构建足够完善的环境和工具链，一个不熟悉具体代码细节的工程师，能否高效完成需求交付？** 如果能，这意味着什么？如果不能，瓶颈又在哪里？

## 一、实验设计：刻意选择"小需求"
我选择的是小度 Aries 模块的一个典型 Bad Case：用户查询笔顺时，一到三个字都能正常返回结果，四个字时会答非所问，只返回词语释义。

之所以选这种级别的需求，是刻意为之。我想验证的不是"AI 能不能帮我做一个很牛的架构设计"，而是一个更基础也更重要的问题：**AI Coding Agent 能否系统性地接管日常业务开发中最大量的"改进迭代类"需求？** 这类需求单个不复杂，但占据了一线工程师大量时间。如果这个环节能被 Agent 高效接管，释放出的产能将是巨大的。

同时，我刻意不深入了解 Aries 的代码逻辑细节，以此来测试这套流程对"领域知识"的依赖程度到底有多高。

## 二、脚手架设计：Agent 能力的边界由环境决定
为了尽可能还原真实场景，我从环境搭建开始。而回过头看，这个环节反而是整个过程中最关键的部分——它揭示了一个重要的架构原则。

### 2.1 核心矛盾
我的开发模式是本地用 Claude Code 写代码，但编译和服务部署需要在开发机上完成（BCloud 构建 + Aries 服务连接沙盒上下游）。核心矛盾在于：本地登录开发机需要 Relay 人工校验，Claude Code 无法直接 SSH 连接。这意味着所有交互都需要我手动中转，Agent 的自主性被完全废掉了。

这个矛盾其实揭示了一个更普遍的问题：**当前 AI Coding Agent 的能力上限，往往不取决于模型本身有多强，而取决于它能触达多少环境。** 模型再聪明，如果连编译结果都看不到，它就无法形成有效的反馈循环。

这也解释了一个有趣的现象：为什么 JavaScript/TypeScript 等解释型语言在 AI Coding 时代变得格外流行？本质原因在于它们的反馈环天然就短——本地一行命令就能跑，浏览器刷新就能看到结果，Agent 写完代码可以即时验证、即时迭代。而 C++ 这类编译型语言，从代码修改到看到结果，中间隔着编译、部署、启动服务等多个环节，反馈环被大幅拉长。这也正是 Vibe Coding 的产出几乎清一色是 Web 应用的根本原因——不是 AI 只会写前端，而是前端生态的反馈环条件天然最好。我在 Aries 上花大力气搭建脚手架，本质上就是在人为缩短一个编译型语言项目的反馈环。

注1：我也在内网搜了一些开发机上安装CC进行开发的知识库，后来觉得还是太麻烦了，所以还是选择本机开发再同步的方式

注2：安全大家别忽视，每个人需要对自己的行为负责

### 2.2 设计方案：基于 FTP 的间接控制
在安全约束下，我设计了一套间接控制方案，核心思路是**用文件传输代替命令执行**：

**DEV Push（代码同步）。** 在内网找到一个基于 FTP 的文件同步方案后，我构建了第一个 Claude Code Skill，让智能体可以按配置将本地代码推送到开发机。

**Flag 文件触发构建。** 在开发机上部署一个 Watch Build 脚本持续轮询监听。智能体只需通过 FTP 推送一个 Flag 文件，脚本检测到后自动触发 BCloud 编译和服务重启。这样做有两个好处：复用现有的 FTP 传输能力，不需要额外开发；没有暴露新的网络接口，避免了远程执行命令的安全风险。

**DEV Sync（结果回收）。** 同样利用 FTP 机制，让智能体主动拉取构建结果和服务日志。

### 2.3 闭环的意义
至此，整个环境对 Claude Code 形成了闭环：本地修改代码 → 推送到开发机 → 触发编译和服务启动 → 拉取日志和结果。智能体可以完全自主地完成这个循环。

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=6e9607d697d44ac58529d15fa268116f&docGuid=Fz78Mn5Ig9WlLh "")
这套方案技术上并不复杂，但它背后的原则是通用的：

> **在启动任何 Agentic Engineering 项目之前，首先要回答一个问题：Agent 的"感知-决策-执行"循环是否完整？如果它无法观察到自己行动的结果，再强的模型也无法形成有效迭代。脚手架的本质，是为 Agent 构建完整的反馈环。**
## 三、开发流程：先 Plan 再实施
脚手架就绪后，进入具体的需求开发。对于 Bad Case 修复，仅仅靠代码静态分析往往是不够的。即使你对代码很熟悉，大部分情况下仍然需要针对具体 Case 添加日志，基于实际运行的 Log 来追踪逻辑流转，然后才能设计修复方案。

我的开发流程遵循一个核心原则：**先 Plan 再实施**。

以笔顺 Bad Case 为例，我的实际操作过程是这样的：

1. **先补日志，不急着修。** 把 Case 信息交给智能体后，我明确要求它先不要分析如何解决问题，而是在现有代码中补充相关的日志输出。这一步的目的是让我们先看到真实的执行路径，而不是让 Agent 基于静态代码做猜测。
2. **通过脚手架获取真实日志。** 利用前面搭建的 DEV Push → Flag 触发构建 → DEV Sync 的完整闭环，将带日志的代码部署到开发机，跑出实际的 Log。
3. **基于日志给出修复方案。** 将真实日志交给 Agent 分析，这时它对问题的理解是建立在实际数据而非猜测之上的，输出的修复计划质量明显更高。
4. **Review 后执行。** 我审查修复计划确认合理后，Agent 执行修改、部署、验证。

这个流程的成功率远高于直接用一句话描述问题然后让 Agent 去修。原因在于，Plan 阶段本质上是在帮 Agent 建立对问题的完整上下文——而上下文的质量，直接决定了 Agent 输出的质量。

以上每一步我都封装成了对应的 Skill，后续遇到同类需求时，整个流程可以一键串联。

PS：这里我不太想仔细对比诸如superpowers，gstack等等沉淀的技能，因为这些都不合适。

## 四、技能积累：把重复操作转化为复利
开发完成后，最常见的两个操作是目标 Case 验证和大量跑 Diff。这些都是高频操作，我遵循了一个重要原则：**把重复操作沉淀成 Skill，让每一次投入都能产生复利。**

具体来说：

* 从月度评估和其他产研开发同学那里收集随机 Query，构建了 DEV Test 和 DEV Diff 工具，让 Agent 自动跑 Diff 并对结果进行评估。
* 将 iCode 评审流程自动化：流水线触发、AI CR 代码报告生成、根据报告结果迭代修改、添加 Patch Set。
* 所有这些流程都沉淀成 Skill，后续任何需求开发都可以直接复用。

到这里，整个流程从 Bad Case 分析到代码提交评审，完全由 Claude Code 自驱动完成。我最终只需要检查输出的 Diff 表格即可。

在整个实践过程中，我累计积累了十几个 DEV Skill，覆盖了从环境搭建、代码同步、构建触发、日志拉取、Diff 测试到 iCode 提交的完整链路。这些技能组合在一起，就是我个人的 Agentic Engineering 工具箱。我已经将完整的技能组 Overview 文档和所有 DEV Skill 的源码放在了内部 iCode 代码库中，欢迎大家查阅和复用：

## 五、实战验证：一天完成两个跨领域需求
为了进一步验证这套流程的通用性，我拿了产品每周值周 List 中的两个 Case：一个是 VOD 相关，一个是音乐相关，都与时效性有关。这两个需求我此前都没有深入了解过相关业务代码。

在 iCafe 建完卡片后，我直接将 Case 交给 Claude Code，由它自动完成以下流程：

1. 添加日志代码并拉取日志
2. 分析问题并给出执行计划
3. 实施计划并进行目标 Case 验证
4. 统计 Diff 规模，自动触发 iCode 提交流水线

整个过程我主要的工作是 Review Agent 的 Plan、检查 Diff 结果、确认最终输出。一天时间完成了两个需求的开发及提交评审。

这个结果回应了我最初的假设：**在脚手架和工具链足够完善的前提下，工程师对具体业务细节的依赖确实可以大幅降低。** Agentic Engineering 的能力是通用的，核心不在于你对某个垂类领域有多深的了解，而在于你能否为 Agent 提供充分的上下文和环境支持。

## 六、质量保障：不看代码 ≠ 不管质量
需要特别说明的是，"不深入看代码"并不意味着对质量不负责。我在这个过程中依赖了多层质量保障机制：

**Plan Review。** 每次修改前，我都会仔细审查 Agent 的修复计划。计划中包含了它对问题的理解、修改范围、预期影响。如果计划本身有逻辑漏洞，在这一步就能拦截。

**自动化 Diff 评估。** 通过 DEV Diff 工具，Agent 会在大量随机 Query 上跑对比测试，而不仅仅是验证目标 Case。这确保了修复不会引入新的回归问题。

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=fec0820c280d438faa4819a959963d5a&docGuid=Fz78Mn5Ig9WlLh "")
**iCode 评审闭环。** AI CR 报告 + 人工评审的组合，提供了代码层面的质量兜底。

**但这套机制也有明确的适用边界。** 它适合改进迭代类需求——逻辑相对局部、影响范围可控、可以通过 Diff 验证的场景。对于涉及架构变更、跨系统联动、或需要深度领域判断的需求，仅依赖 Plan Review 和 Diff 是不够的，仍然需要人的深度介入。认清这个边界，和掌握这个工具一样重要。

## 七、从 Prompt 到 Harness：AI Coding 的三次跃迁
基于这次实践，结合业界最新的讨论，我认为 AI Coding 的使用水平正在经历三次跃迁：

**第一层：Prompt Engineering。** 向 Chatbot 提问，获取代码片段或解决方案。人驱动每一步，AI 是被动的问答工具。这是大多数人的起点。

**第二层：Context Engineering。** 核心认知从"怎么问"转变为"给 Agent 提供什么上下文"。在这一层，你开始关注如何结构化地向 Agent 传递信息——编写 CLAUDE.md、构建 Skill、把架构决策和编码规范写入仓库，让 Agent 自己能发现和理解项目的全貌。Vibe Coding（即凭直觉和 AI 快速生成代码）也属于这一层的应用形态，它能快速产出 Demo 和原型，但对已有工程体系的融入能力有限。

**第三层：Harness Engineering（Agentic Engineering）。** 这一层的关键词不再是"提问"或"上下文"，而是"系统"。你需要为 Agent 构建完整的运行环境，包括三个核心维度：

* **反馈循环**：Agent 能否自主完成"写代码 → 部署 → 观察结果 → 迭代"的完整循环？这是我在本次实践中主要解决的问题。
* **约束机制**：如何通过 CI、Linter、架构规则等确定性手段，机械化地约束 Agent 的产出质量，而不仅仅靠 Agent 自觉？业界的实践表明，约束解空间反而能让 Agent 更高效地收敛到正确结果。
* **长期治理**：Agent 会复制仓库中已有的模式——包括不够好的模式。随着时间推移，代码库不可避免地积累熵。如何通过自动化清理、规范编码化等手段持续维护代码质量，是 Harness Engineering 的长期挑战。

坦率地说，我目前的实践主要集中在第三层的"反馈循环"维度，以及第二层的 Context Engineering（Skill 沉淀、结构化上下文）。约束机制和长期治理是我下一步需要深入的方向。但即便只做到这一步，效率提升已经非常显著——这也说明了搭建反馈闭环作为 Harness 第一步的杠杆效应。

## 八、Claude Code 实用技巧
在实践过程中，有几个具体技巧值得分享：

**Plan Mode 先行。** 在执行任何任务之前，先开启 Plan Mode，与 Agent 充分沟通方案后再执行。这是我观察到的影响成功率最大的单一因素。

**Remote Control。** 完成全自动化闭环后，Claude Code 支持用手机上的 Claude App 进行远程控制。这意味着在外出或通勤时也能触发和监控开发任务。这几乎是我最喜欢的特性了，也是我没在开发机上尝试的原因，因为不确定能否正常工作。

**持续跟进新特性。** Claude Code 迭代速度很快，建议每周花时间尝试新特性。比如 Loop Monitor 可以监控智能体的执行过程，Insight 能分析你近期的使用模式并给出优化建议。如果遇到输出质量不稳定的问题，可以尝试调整 Effort 参数或开启 Adaptive 自适应思考。

## 九、思考与展望
### 能力重心的转移
一个优秀工程师最重要的能力是：发现问题、定位问题、分析问题、解决问题。AI Coding Agent 已经能在后三个环节提供巨大帮助，但"发现问题"仍然需要人的深度参与。我们需要将注意力从"怎么解决"转移到"解决什么"上——这可能是 AI 时代工程师最重要的能力重构。

### 提效的真正阻碍不在 AI 本身
在实践中我发现，跨模块、跨工种协作的真正阻碍，往往不是 AI 能力本身，而是 Debug 环境、研发上线流程、权限体系等周边配套设施。回到我前面提到的原则——Agent 的能力边界由环境决定——这意味着**研发效能的下一个突破口，不是更强的模型，而是更开放的研发基础设施。** 这也是我下一阶段想继续践行的方向。

### "黑灯工厂"趋势与它的前提
最近业界在讨论"Dark Factory"的概念——就像高度自动化的工厂即使关灯也能运转，AI 软件开发也在朝这个方向发展。这个趋势分为两个阶段：第一阶段是"人不写代码"，所有代码工作由 Agent 完成；第二阶段是"人不看代码"，人只关注意图、计划和结果。

但我想补充一个容易被忽略的前提：**黑灯工厂之所以能关灯，不是因为没有管理，而是因为有极其完善的传感器、反馈系统和异常处理机制。** 同理，AI 软件开发要走向"人不看代码"，前提是我们有足够可靠的自动化测试、Diff 评估、回归检测等质量保障体系——也就是 Harness Engineering 中"约束机制"和"长期治理"这两个维度的成熟。没有这些基础设施，盲目追求"不看代码"是危险的。

---

希望这篇文章能给大家一些启发。AI Coding 的能力已经从"偶尔能用"进化到"大部分情况都能用"，怎么用好它，是每个工程师都需要掌握的技能。与其只拿它问问代码怎么写，不如有意识地沿着 Prompt → Context → Harness 的路径持续进化——构建环境、设计约束、审查结果，让 Agent 成为你的执行引擎。这也是我写这篇文章的初衷。

文章发出后收到了不少同学的反馈和讨论，这里整理几个有代表性的问题。

### Q1：文章启发性够了，但想复刻这个流程不容易。能不能把每个环节"为什么做、在解决什么问题、对应哪几个 Skill"讲得更清楚？
这个建议很好，也是后来补充分层架构图的原因。那张图（见第四章末尾）就是为了解决这个问题——四层架构从环境基础到任务编排，每层标注了它解决的核心问题和对应的 Skill。

但我想强调一点：**具体的 Skill 不是重点，分层思路才是。** 每个人的技术栈、开发环境、上线流程都不同，我的 DEV Push / DEV Sync 是基于 FTP 的，换一个团队可能完全用不上。真正可复用的是这套分层逻辑本身——先确保 Agent 能触达环境，再构建原子操作，然后串联成迭代循环，最后编排成端到端的任务流。按这个思路，每个人都会沉淀出属于自己的 Skill 组合。

### Q2：为什么不直接在服务器上用 Claude Code，避免本地和开发机之间的同步问题？
这是个很好的思路，如果条件允许确实是更简洁的方案。选择本地开发主要是因为我当时的具体环境约束。

但更值得讨论的是：**云端开发虽然对服务端场景几乎完全可行，但并非所有场景都适用。** 比如端侧开发（Android 应用开发等）、以及一些需要 Browser Use 的外围操作（比如我获取流水线上 AI CR 报告的那个 Skill，就需要通过浏览器抓取），在云端环境下都很不方便。所以文章中搭建脚手架的思路，本质上是一种在各种约束条件下都能适配的通用方法。

### Q3：Skill 源码放在个人仓库，是不是可以建一个团队共享的 Skill 仓库？
完全认同这个方向。个人 Skill 沉淀是第一步，团队级别的 Skill 共享是自然的下一步。事实上，底层的原子操作 Skill（如代码同步、构建触发）通用性很高，非常适合抽取到团队仓库中。而上层的任务编排 Skill（如某个具体业务的 Bad Case 修复流程）则更偏个性化，可以作为参考模板而非直接复用。

### Q4：AI 时代，质量保障是不是变得更重要了？
是的，这也是我在文章中专门用一个章节讨论质量保障的原因。当 Agent 接管了大量代码编写工作后，人的角色从"写代码的人"变成了"审查结果的人"。这时候，**质量保障的重心从"写的时候小心"转移到了"写完之后怎么验证"**——自动化 Diff 评估、回归检测、AI CR 这些机制变得比以往任何时候都重要。这也是 Harness Engineering 中"约束机制"维度的核心命题。

### Q5：这套方法的推广价值在哪里？是"道"还是"术"？
坦率说，我在写这篇文章时一直在犹豫要不要把 Skill 层面写得这么具体。因为我更想传达的是"道"的层面——分层思维、反馈环闭合、重复操作复利化这些原则。具体的 Skill 在某种意义上都不重要，每个人根据自己的技术栈和开发环境，都会沉淀出不同的实现。

但最终还是选择了把具体实现放上来。原因是：**没有"术"的支撑，"道"很容易变成空谈。** 读者需要看到一个完整的、跑通了的具体案例，才能真正理解这些原则意味着什么，然后才能在自己的场景中举一反三。
