# 背景
随着大数据技术的发展，传统的离线计算框架 **MapReduce（MR）** 已逐渐暴露出诸多局限。**Spark** 作为新一代大数据计算引擎，凭借内存计算、统一计算引擎和丰富的生态体系，已经成为离线计算领域的主流框架。

厂内的离线任务中，MR和Spark任务的资源成本各占一半，因此我们设计了史帕克，通过模型能力将MR任务翻译为Spark SQL，达到计算提速&资源优化的目的。

## 🚀 AI模型翻译
**性能提升**：从小时级到分钟级，从分钟级到秒级

**人力节省**：开发效率提升，SQL语法人人都了解，大大降低维护成本

**资源优化**：相同任务集群资源消耗减少三成以上

**选择Spark SQL，让大数据开发更简单、更快速、更经济！**



## 🔄 数据抽样自动对DIFF
**数据抽样**

* ✅ 多input抽样：将MR多个输入，分别执行随机抽样。

**Diff对比**

* ✅ 抽样数据运行MR：将抽样数据作为输入，集群提交MR
* ✅ 抽样数据运行SparkSQL：将抽样数据作为输入，集群提交Spark
* ✅ MR&Spark结果**行级DIFF**：将结果进行排序，对比DIFF。

## pipeline说明
为了逻辑的快速验证，我们设计了一套pipeline：

[流程图]
1. **第一阶段：等待翻译**，在此阶段会拉取用户代码，切换到对应分支，校验提交入口脚本是否存在。
2. **第二阶段：翻译中**，向大模型发起翻译请求，可翻译会给出SQL及UDF，无法翻译会给出原因（例如：调用so文件、模型训练任务、读取了pb数据源、对输入输出文件名有特殊逻辑等SQL无法实现的逻辑）。
3. **第三阶段：测试集构建中**，根据input参数对输入数据进行随机抽样，方便快速验证。
4. **第四阶段：测试任务构建中**，使用测试集，分别提交SQL和MR测试任务。
5. **第五阶段：DIFF比较中**，对两者产出的测试任务结果进行排序，比较是否存在DIFF。
6. **最终阶段：翻译完成**，由于跨引擎的迁移，可能会存在细微DIFF，或者由于浮点数精度、随机逻辑等无法避免的DIFF存在，完成第五阶段后，无论是否存在DIFF都认为翻译成功，会向代码库发起CR。
