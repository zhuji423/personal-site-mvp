# 一、AI破除压测困局，**告别“工具迷宫”，迎接自主规划测试**
## 1.1 人工困局
在当前的业务测试中，针对业务扩展、资源评估或架构迭代等场景，压测已成为评估服务稳定性的核心手段，能够通过模拟高并发场景，客观反映系统在真实负载下的表现。然而，在传统压测模式下，测试流程主要靠人工推动、整体流程分散、测试报告依赖人工整理等问题亟待解决，具体体现在以下几个方面：

* **学习成本较高**：执行一次完整的压测任务，通常要求RD&QA人员熟悉多个独立工具的操作流程，包括但不限于环境搭建、流量引流、数据包改造(筛选、增加字段、修改字段值等)、发压等环节。每个工具均有其特定的配置项与使用逻辑，跨工具协作无形中增加了团队成员的技能门槛。
* **执行效率受限**：
    * **流程割裂，操作繁琐**：传统压测往往需在不同工具界面之间频繁切换，依次完成环境搭建、引流、改包、发压等步骤。这种离散式操作不仅打断工作流，也容易因人工干预引入误配置风险。
    * **状态感知被动**：任务启动后，执行进度与结果无法主动推送给用户，需测试人员反复查看任务状态，严重拖慢问题定位与响应速度。
    * **排查成本高昂**：一旦任务执行失败，往往需要协调多个工具的开发人员共同参与排查。在此过程中，还需手动收集并整理本地配置文件、日志等信息，沟通与调试周期长，严重影响团队协作效率。




## 1.2 AI破局 
在常规的压测行为中，压测常规步骤基本为环境搭建、线上引流、选择压测工具、执行压测计划、产出压测报告几个步骤，如果有特殊流量场景还涉及到流量构造，归根结底压测是RD&QA确认压测目标之后来制定压测方案，利用特定的几个测试工具一步步执行，最终产出压测结论。而结合最近AI技术迅速发展，我们是否可以将传统的测试模式升级为“目标驱动”的智能测试模式。这一变革的核心，是从**“人执行工具”转变为“人下发命令、AI驱动系统”的人机协同新模式**，进入一个全新的自主化、智能化的测试模式时代。用户只需要给出自己的测试需求，然后**由AI来自主动态决策、执行任务规划、主动纠错自愈****。**

### **传统模式：“执行上行” (Execution-Up)**
在传统测试平台中，用户（RD/QA）是任务的“驾驶员”和“执行者”。

* **流程**：用户的大脑作为“调度中心”，需要主动思考并执行一系列操作：

    1. **分析需求**：我要做什么测试？（例如：对新接口进行压测）
    2. **规划路径**：我需要用到哪些工具？（例如：先引流，再发压）
    3. **寻找工具**：在平台界面上找到“引流工具”和“发压工具”的入口。
    4. **填写参数**：理解每个工具的复杂参数，并手动填写。
    5. **串联执行**：手动操作第一个工具，等待结果，再手动操作第二个工具。

* **特点**：
    * **用户是驱动源**：所有的操作指令都**由用户向上发起**给平台。
    * **用户承载所有知识**：工具的使用顺序、参数含义、异常处理等都依赖用户的经验。
    * **平台是被动的**：平台只是一个被操作的“工具箱”。


[流程图]


### **AI驱动模式：“需求下行，执行上行” (Requirement-Down, Execution-Up)**
在新架构中，**AI智能体**成为了新的“调度中心”，用户则退居为“指挥官”。

* **需求下行 (Requirement-Down)**
    * 用户只负责下达一个**目标式的需求**（例如：“对新接口X进行阶梯发压测试，观察性能表现”）。
    * 这个需求作为一道“指令”，**向下传递**给AI智能体。
    * 至此，用户的主动工作就基本结束了。

* **执行上行 (Execution-Up)**
    * **智能体规划**：Master Agent接令后，开始思考（规划），将需求拆解为“引流 --> 发压”等步骤。
    * **智能体调用工具**：Agent根据规划，**自主地、向下地**调用相应的工具（通过Tool和MCP Server）。
    * **工具返回结果**：被调用的工具（如NXSTP）在执行完毕后，将结果（成功/失败/数据）**向上返回**给智能体。
    * **智能体决策与同步**：Agent根据返回的结果，决定下一步动作（继续执行下一步、重试或报错），并将最终结论和进度**向上同步**给用户界面。

* **特点**：
    * **需求单向下达**：**用户只关心“做什么”（What）**，不再关心“怎么做”（How）。
    * **执行由AI驱动**：具体的工具调用、参数组装、流程串联均由智能体自主完成。
    * **平台是主动的**：AI智能体能主动调度资源，完成任务。

# 二、技术实现介绍 - 多Agent&MCP成就从“需求理解”到“工具执行”的完整闭环
为了实现“人下发命令，AI驱动系统”的目标，深入解决特定测试场景问题，我们基于open manus框架二次开发，完成从用户交互到最终工具调用的完整链路，引擎层与工具层构成了从"需求理解"到"工具执行"的完整闭环。其核心是**TestOne** 作为神经网络进行需求分析，负责信息流转与协调；**Master Agent** 作为大脑，负责决策规划；**MCP Server**** Tool**则将决策转化为精准行动。

## **2.1 交互层：打造“对话式、可感知、一体化”的测试协同界面**
**从“手动执行”到“指令下发”是生产模式的变革：**传统模式中用户想实现“先引流，再发压”的任务，首先要求这些用户必须是工具专家，然后手动在A平台完成引流配置，执行引流计划，获取引流结果后，再切换到B平台，在发压计划中填入所需的参数，执行发压计划，获取发压结果报告。整个过程是断裂的、机械的指令配置。此模式下存在**配置复杂、过程黑盒、流程割裂三大痛点**。因此，我们通过构建**智能交互模式完成用户与AI测试能力的触发，用户只需要用****自然语言下发需求****，AI可以****将复杂的测试工程转化为简单、自然的对话过程**，并通过流式输出让用户**对整个执行过程“心中有数”**，建立信任感。

**1. 交互方式：简单直观**

我们将每个测试工具对应的能力通过自然语言进行刻画，这样将测试能力转化为一种AI Agent，即不再要求人作为工具专家，用户只需“表达意图”，而非“操作工具”。当用户想实现引流 + 发压两个任务时，用户只需要通过自然语言，如 “对app-763模块先引流，再发压” 一站式发起复杂需求，AI就可以明白用户想要完成引流任务和发压任务。

**2. 过程感知：心中有数**

AI在驱动整个流程时，其**短期记忆**（会话上下文、任务状态、工具执行情况）被转化为可读的**流式消息**，我们将这部分数据进行可视化，实时展示AI的任务拆解详情与执行状态，实时推送工具调用的成功/失败状态，同时关键结果以流式消息主动推送给用户。这样用户从“被动等待者”变为“主动感知者”，对整个执行链路了如指掌，建立信任感。例如：

* `思考过程 开始执行步骤1：1.获取引流所需的参数`
* `「引流工具」完成 查看详情`
* `获取发压计划详情...`

**3. 协同管理：可溯可复**

AI作为总指挥，统一收集不同平台工具的所有消息，并智能地将其推送到界面的不同区域（如：核心步骤到**执行面板**，详细日志到**日志区**，阶段结论到**总结区**），避免信息过载。

* **信息沉淀与溯源**：所有的流式信息都会被自动归档，形成一个完整的任务执行时间线，便于**溯源**和**复盘**。

## 2.2 **引擎层：构建“智能大脑+敏捷执行”的测试中枢**
为**实现****从“标准化测试执行”到“智能化任务协作”的演进**，解决传统测试方案在灵活性、并发性和智能决策能力方面存在的问题，引入了基于 **Mixture of Experts（专家混合）架构** 的多智能体系统。通过主 Agent 负责任务编排与流程调度，多个专家 Agent 聚焦具体场景任务，从而实现：

* 测试任务的智能拆解与动态规划；
* 异步任务并行与断点恢复；
* 工具层统一接入与封装；
* 测试流程的高可控、高复用与自适应执行。

**1. ****智能决策：****从“手动配置”到“意会神通”**

传统的测试流程被预先固化为线性脚本，**无法根据实际上下文或动态变化的需求（如不同的流量筛选条件）进行智能调整**。任何变更都需要人工修改脚本，无法实现“自适应执行”。因此，我们将复杂的测试任务拆分为若干由专家 Agent 处理的子任务。Master Agent 负责统一协调、策略决策与状态追踪，专家 Agent 则在各自领域内提供专业化能力。这种架构同时具备：

* **灵活性**（动态规划任务路径）；
* **智能性**（结合上下文进行工具选择）；
* **可控性**（Master Agent 保持整体任务一致性）；
* **可扩展性**（可按测试场景新增专家 Agent）。

|**角色**|**核心职责**|**示例**|
|-|-|-|
|调度层|**流程编排引擎**：将用户Query拆解为可执行的场景序列（场景1→步骤1→步骤2...）**状态管理中枢**：维护任务中心，实时追踪每个子任务执行状态**决策调度器**：基于任务进度动态决策下一步动作，确保流程连贯性|任务分解、事件回调、状态恢复|
|决策层|**需求解析器**：理解用户深层意图，生成合理的测试子阶段**路径规划器**：在自主规划模式下，动态构建最优执行路径**自适应调整器**：根据执行反馈实时优化后续步骤|多轮交互测试任务规划|
|执行层|**工具路由器**：从Tool List中智能匹配最适合的测试工具（自定义Tool或MCP Tool）**参数组装器**：根据阶段目标自动生成工具调用参数**执行监控器**：封装调用逻辑，确保执行的高效性和准确性|diff agent、引流 agent|
|工具层|**工具接入层**：封装外部MCP Server与内部自定义Tool，提供标准化调用接口|调用自定义 Tool 与 MCP Tool|

**2. 动态编排：双模驱动，稳健灵活**

传统的测试方法所有任务都采用同一种执行策略，**要么全部固定（不灵活），要么全部手动（效率低）**。然而在不同的需求中测试任务并非同质的，它们存在于一个从“高度标准化”到“极度开放”的频谱中。但如果都采用Workflow的方式，那么无法自主发现新的问题或测试场景，业务逻辑的微小变化，都可能需要人工修改大量的预置Workflow，成本极高。如果都采用自主规划的方式，那么对于关键流程，若AI在推理时可能存在“幻觉”，或产生非预期的路径分支，这种不确定性是致命的。因此，我们采用自主规划与Workflow相结合的方式，**实现**“智能”与“可靠”**的目标。**例如：

**阶段一：Workflow 作为主干框架（保障流程可靠性与效率）**

* **用户输入**：用户在交互层输入：“对ae-app-763进行引流+改包+压测。”
* **意图识别与Workflow匹配**：

**阶段二：自主规划赋能关键环节（提供动态灵活性）**

接下来，系统并不会死板地执行Workflow的每一步，而是在具体步骤中注入智能。例如：

关键节点：步骤2 - “对录制的流量进行必要的筛选”

* 分析用户的需求是改流量还是过滤流量
* 根据用户的需求，对用户给出的流量进行过滤
* 过滤完生成新的二进制流量包

**3. 任务完成度：保障长周期任务的可靠性与成功率**

* 传统测试模式中，**测试任务像单线程一样，需要手动一个接一个地执行，导致效率低下**，因此采用异步并行执行架构，通过并行化大幅缩短端到端执行时间。主要包括：
    * **任务解耦**：主Agent可发布异步长时间任务（如引流任务，创建环境等任务）到MCP Server
    * **并行推进**：在等待异步任务结果期间，继续执行其他独立子任务

* 但长时间的异步任务会导致MCP Server断开连接，因此采用事件驱动唤醒机制，确保异步任务与主流程的平滑衔接。主要包括：
    * **状态监听**：MCP Server通过事件中心SDK发布任务完成事件
    * **智能唤醒**：Agent接收到回调事件后自动唤醒并处理后续逻辑

* 传统测试模式中，**对于耗时数小时的测试任务很难保证端到端的成功率**。一旦中断，必须从头开始重跑，成本极高。因此通过智能中断恢复能力，给任务提供连续性保障，应对各种异常情况。主要包括：
    * **状态持久化**：将会话上下文、任务状态等短期记忆完整保存
    * **现场恢复**：中断后能够准确恢复到断点状态，确保长任务可靠性




## 2.3 **工具层：打造“即插即用、敏捷执行”的MCP工具生态**
为实现 **“AI驱动压测”** 的业务愿景，我们首先需要解决核心的工具瓶颈。传统的压测工具（如本地的 `uload、codec`）是一个封闭的黑盒，或者利用api进行交互（如引流）缺乏与AI智能体进行高效、标准化交互的能力，成为智能化转型的首要障碍。为支撑上层AI智能体的高效运作，为此，我们**联合系统测试服务（NXSTP）进行了关键性共建**，将核心的压测能力通过 **MCP-Server** 进行重构和封装，把传统的命令行工具转变为标准的 **MCP Tool**。

**工具建设思路**

        测试工具是满足一个测试需求的具体实现，这些工具可以辅助/替代测试人员完成测试活动的执行，提高测试的效率和效果。在软件交付的发展过程中，我们经历了由全面的**手工测试(第一代)到自动化测试及部分智能化（第二代）**再到当前以**AIQA为核心的交付过程，**不同交付模式下，对测试工具的实现、管理方式等都有着不同特点及实现要求。

|**测试发展阶段**|**手工测试阶段**|**自动化/半智能化阶段**|**AIQA阶段**|
|-|-|-|-|
|**工具的实现形式**|单机的脚本/程序，通过手工执行、本地获取单次执行结果|通过将工具进行无状态化、微服务化管理，通过API触发分布式执行，整合汇总多实例数据产出报告|工具除了满足自动化相关能力，可能本身也会具备一些智能能力，被上层模型/Agent调用整合分析得到测试结论|
|**工具的使用方**|测试人员|流水线（CI/CD）/自动化API等|大模型/AI-等Agent|
|**工具典型特点&要求**|相对比较简单能够比较友好的完成某个具体的工作需求，对测试人员的专业知识、经验要求高|相对比较复杂支持通过编排进行快速的验证及重复的执行，方便与各种自动化流程整合，给出准确固定的测试结论|比较复杂需要支持多种类型模型的使用对输入参数、输出报告格式的要求较多对各种动态编排及智能分析的支持|

基于当前交付新阶段对测试工具的新要求，传统的积累的测试工具(本地发压性能测试、通过api使用部分服务化工具)等已经无法满足上层智能体/模型对测试工具的需求，因此设计全新满足智能体使用的工具，来增强AIQA的能力，助力新交付模式的达成。

**1. MCP与****Function Call**

之前团队支持半智能化相关的能力时候，工具多是采用API的方式支持上层 AI 工作流都依赖于传统的函数调用，但是随着模型的增多及工具迭代等，相关适配工作成本及变更影响范围等不断变大，动态及可扩展性也收到很多的限制，而Model Context Protocol（MCP）是一个更轻松的让基于大型语言模型（LLM）的AI系统能够方便地和外部的数据源、工具以及服务进行交互的开放标准，降低各种模型适配成本的同时，也更好的支持后续的迭代及扩展，因此我们测试工具选择通过支持MCP的方式支持AIQA使用。

|**维度**|**Function Calling**|**MCP**|
|-|-|-|
|**灵活性**|结构化但相对刚性，适用于简单任务|更灵活，适用于多步骤和富上下文的动态交互|
|**可扩展性**|每个新集成都是定制添加，维护成本高|标准化方法，易于扩展和维护，降低了“M×N”问题|
|**生态系统**|每次添加新功能都需要手动更新定义|新能力通过添加配置MCP服务器来增加，自动发现工具|
|**适应性**|模型需预先知道可用函数，环境变化时需手动更新|运行时动态发现功能和资源，更具适应性|
|**工具发现**|需要手动向模型添加新的函数定义|支持运行时动态查询和工具发现|
|**执行模型**|单步执行，由应用程序协调|支持多步骤推理，模型可更自主地请求工具或数据|
|**复杂性处理**|适用于单一或简单的操作|适用于复杂、并行的操作和工作流|

**2. 工具的粒度**

通常情况下，一个测试需求的完成需要组合编排调用多个原子的测试能力，一方面这些原子能力拆分的足够细可以极大的方便上层的灵活调用，但是另一方面，很多不同原子能力之间的调用顺序、数据等又存在比较复杂的依赖约束，如果将这些全部开放给模型来动态编排，在当前相关模型的能力条件下，不光会增加模型的负担，也存在较大的准确性及效率问题。

![一个简单的压测任务](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=b9462716cb124aba9ba955c574aa511c&docGuid=ppdA3LMmbftMHG "一个简单的压测任务")
如上图所示，一个简单的压测任务可能包含多个阶段的工作，这些阶段原本都属于一个测试工具（包含在一个测试计划中），这在传统的使用模式下没啥太大问题，但是在提供给AI使用的时候，就会损失很多的灵活性，如果发压参数调整一次就需要重新编排执行一个计划，那这个成本就会变大很多，因此我们需要将环境部署、数据准备、压测、报告分析等尽量的拆分，这样基于实际运行过程中的数据指标产出，AIQA可以通过引擎层的相关能力，实现最大效率的动态编排执行，提高测试效率

但是另一方面，像压测过程中的指标采集、发压、异常检查等这些，虽然也是独立的原子能力，但是他们在能力组合及执行顺序等方面都需要作为一个整体，如果全部按照独立拆分，在模型编排的时候又会造成很多不必要的成本消耗及不确定性。

因此在实践的过程中，我们需要结合不同场景、不同能力特点，进行合理的工具粒度拆分实现，在提高模型编排灵活性的基础上，降低模型成本，提高效率。

**3. 工具的描述**

一般而言，系统级测试中要基于不同的场景、模块、测试需求等选择不同的工具、参数进行，这些工具、参数存在一些相似性，又存在显著的差别，在之前平台的实践过程中，工具、参数的选择、准备也是较大的一个难点，而当前模型能力还无法完全达到/超过专业测试人员的水平，所以在实践中也存在工具、参数识别、提示词膨胀等各种问题。为了降低这些问题，我们除了在上层通过一些rag等方式来提高模型能力之外，在工具实现的过程中，也需要尽可能通过提供模型更易懂的描述，来降低模型的识别成本。

* 标准化工具和参数名：通过为工具使用更直观、更一致的描述性名称，对参数的含义、要求格式、依赖关系等进行更清晰的定义等方法，提高模型识别使用的准确性
* 提供工具、参数的使用示例，对工具的应用场景、参数的准备实例等在描述中加以体现，确保模型选择、传入的参数符合预期
* 明确的错误返回：针对不同错误提供清晰的错误定义及解释，并且对解决的办法做针对性的描述，避免模型理解错误返回的成本
* 配合其他知识、训练等提高模型选择能力，通过与上层引擎层、交互层相关能力配合，做一些模拟、训练、反馈等，提高准确性

**MCP 实践中的其他问题问题**

**面向上层业务Agent使用的工具支持与升级**

* **单点工具能力升级**
    * 针对新协议、请求返回计算需求进行能力需求升级，使用全新driver替换uload，直接解析NB录制产出数据进行发压，提高任务执行效率
    * 解决发压控制模型问题导致因为后端返回耗时压力上不去的问题，使用go协程实现，在后端响应慢及异常等情况下，仍支持严格按照配置发压，防止压力上不去
    * 针对阶梯发压场景需求，在对一个模块进行宽范围qps压测的场景下，通过升级压力工具，在不用启停发压任务的前提下，支持按照参数步长、最大最小压力等参数进行一次任务自动阶梯发压，也支持通过配置相关noah监控及压力变化函数、策略等基于后端返回状态进行压力控制，用最小的成本、最快的效率准确评估模块真实性能

* **回调能力支持**
    * 提供计划开始执行、执行结束的回调能力，基于不同模块调用区分，通过参数指定不同回调地址的方式，将参数执行及结束相关状态以回调的方式通知模型，提高模型执行的效率


**面向端到端场景通用Agent工具设计**

     除了针对前述业务AIQA的工具使用需求以外，针对一些简单业务、通用化程度较高的系统级测试场景，NXSTP也面向端到端场景设计工具能力，后续会以通用系统级测试场景Agent的方式接入TestOne，与不同业务的AIQA共同支持系统级执行测试

* 提供基于模块协议类型、系统级测试场景、不同业务及用户等信息进行已有场景计划查询的工具能力，基于该工具，模型可以从历史执行记录中获取最大概率适配当前测试场景需求的计划及相关的参数推荐，经过简单的修改即可以在不用自己创建单独计划的前提下快速发起测试任务，降低用户使用成本
* 针对模型可解析的报告与人看报告的相关差异，提供适配模型解读的通用指标描述及报告形式，方便Agent拿到对应数据以后可以按照统一的标准及领域知识进行结果解读及推理判断
* 针对任务执行过程中的异常及参数配置问题，提供统一的定位Agent能力，可以接入数字人、mcp工具等方式实现基础服务与上层业务定位能力的融合，更好的方便上层Agent基于任务及定位信息作推理判断
