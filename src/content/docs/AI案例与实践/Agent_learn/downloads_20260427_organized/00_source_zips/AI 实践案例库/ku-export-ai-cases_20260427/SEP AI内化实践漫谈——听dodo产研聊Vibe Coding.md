SEP AI内化实践漫谈——听dodo产研聊Vibe Coding

#### 🧑‍🏫 案例作者：dodo产研团队
#### 🎬 案例分类：开发、研发全流程
#### 🔧 使用工具：dodo
#### 📒 案例概要：本文从需求管理、代码风格、Code Review、问题排查、自我迭代、测试体系、团队分工七个维度，系统梳理 dodo 团队在 AI 辅助研发实践中的真实经验——包括踩过的坑、摸索出的方法，以及对 Vibe Coding 模式的深度反思，供有意推进 AI 内化的团队参考借鉴。
* **项目背景：**dodo是百度内部一款通用智能体产品，启动于 2026 年 1 月底，由工程效能部打造。团队早期仅有数名 RD 和一名核心 PM，无专职前端工程师，有AI原型但无完整PRD，以 Vibe Coding 方式快速推进，数月内完成从 0 到 1 的冷启动，并持续高频迭代至今。
* **对谈嘉宾：**周梧桐（dodo主理人，工程效能部）、王哲（dodo班主任，工程效能部）　
* **对谈视频链接：**[我们用AI Coding养大了dodo，顺便攒了点经验](https://learn.baidu.com/dulearn/app-dulearn-page.html#/home/course-detail/57557?isFromPc=1&reportLog=true?t=mention&mt=doc&dt=sdk)

## 引言：从"混乱开局"到"规范成长"
四周前，几个研发同学在内网悄悄上线了一个叫dodo的智能研发助手。

没有PRD文档，没有评审会议，甚至没有专业的前端工程师。项目从一开始就选择了与传统研发完全不同的路径——纯Vibe Coding。

"其实最开始的时候，项目挺混乱的。"王哲回忆，"年前那段时间，我们根本没想清楚dodo到底要做什么，想到什么就做什么，做完了直接提交。"

但三个月后，dodo已经有了三个用户群，内置了30多个skill，每天在群里活跃讨论的用户络绎不绝。

**核心提效数据对比**

|**阶段**|**传统模式**|**AI Coding模式**|**效能/质量变化**|
|-|-|-|-|
|**需求管理**|人工整理PRD、手动建卡|智能体自动建卡、自动流转|需求跟踪从被动记录变为自动跟踪|
|**代码风格**|人工review、逐行检查|踩坑驱动写rule、标准模板引导|快速生成代码同时保持风格统一|
|**Code Review**|逐行、逐文件人工review|人机协同，AI辅助分析|review时间减少，风险可控|
|**问题排查**|人工定位、链路复杂|AI First，智能体自主定位|问题定位不依赖人，效率显著提升|
|**测试模式**|单测+人工点点点|端到端优先，AI辅助验证|后端测试链路跑通，边界条件agent验证|

## 需求管理——从 PRD 到原型
传统研发流程是：写 PRD → 沟通对齐 → PRD 评审 → 开发。但dodo从一开始就跳过了 PRD。三个用户群每天需求涌入，他们是怎么接住的？

梧桐的回答让人印象深刻：他们从一开始就是纯 Vibe Coding，没有 PRD，没有评审会，直接用 Google AI Studio 搭出初步原型，再根据场景特征逐步细化。

他们形成了三种需求管理方式：

### Wish List 页面
由团队同学自己 vibe coding 出来。他想做一个需求收集页面，于是从头到尾跑通了前后端开发与上线全流程，页面就这样诞生了。现在还配套写了一个 skill，可以直接向 wish list 添加需求。

### AI 辅助建卡
梧桐有个习惯：只要用户在群里反馈问题，她就把dodo拉进来，让它基于上下文直接创建需求卡片。功能上线后，还会让dodo review 哪些卡片已绑定代码、完成上线，并自动将其流转到「已完成」状态。

### 小需求直接交给dodo
粒度较小的需求，直接让dodo自主完成。团队自发发现的问题通过 iCafe（需求管理系统）管理，如今连 iCafe 卡片都由dodo代为创建。

AI 时代的需求管理正在发生范式转移。传统模式是「先想清楚再动手」，dodo团队的模式是「先动起来再想清楚」——从原型出发，快速验证，持续迭代。更神奇的是，AI 能理解群聊上下文、自动创建结构化需求卡片、跟踪状态流转。规范不是预设的，而是在实践中慢慢生长出来的。

## 代码风格统一 —— 一场持续的战争
AI 写代码很快，但每个人的风格可能截然不同。当大量 AI 生成代码混在一起时，如何保证代码风格的统一？

梧桐坦言，这是项目迭代仅一周就暴露出来的痛点。传统工程里，代码风格统一相对容易——大家有时间、有预期，能往一个共同认可的规范收拢。但 Vibe Coding 模式下，快速生成的代码风格参差不齐，团队成员互相都看不太懂对方写的代码。

她们的应对方案：

### 直接写 Rule
借助 coding agent 支持的 Rule 机制，将整体代码风格规约显式描述出来，作为 AI 生成代码的约束基线。

### 踩坑经验转化为 Rule
很多 Rule 来自真实踩坑。看到代码「消化不良」，就告诉 AI 不要这么写，沉淀为一条新 Rule。规范在实践中不断生长。

王哲坦率地说：dodo在这方面目前并没有做到令人满意的状态。直到现在，生成的代码风格依然不够统一。前端尤为明显——之前的前端全由后端同学纯 vibe coding 写出，没有人梳理最佳实践和规范。很多前端代码写完了，团队自己也说不清它是否优雅，但功能是跑通的。新版本计划引入专业前端同学，由他来梳理规范、在专业领域定义 Rule。

不过有一个场景做得相对不错——skill 的适配。dodo目前有 30 多个内置 skill，最早约 10 个是团队自己写的，后来陆续集成了 skill 广场和开源社区的优秀 skill。集成过程中，各 skill 的规范和对沙箱环境的依赖不尽相同。团队的做法是：以自己写的标准 skill 为模板，把它的特性和规范描述清楚，再引导模型将其他 skill 改造成适配版本。

代码风格统一在 AI coding 时代确实更难了。dodo团队的坦诚令人欣赏——他们没有说「我们已经做得很好」，而是承认「还没有做好」。规范不是预先定义好的，而是在踩坑中慢慢积累。专业领域仍需专业人才，这是 AI 暂时替代不了的。

## 代码评审——从写代码到 Review 代码
代码都是 AI 写的，Code Review 还需要逐行看吗？工程师的角色发生了哪些变化？

梧桐介绍，他们现在的 Code Review 基本是人机协同模式。由于需求迭代节奏很快，逐行、逐文件审查的传统方式已不再适用。现在她们用 iCode 上的「小码哥」做智能评审，同时让dodo自己进行 review，给出影响点分析和改进意见。整体感受是：Code Review 的时间越来越少，评审重心从「盯代码细节」转向「验证功能是否达成预期、评估影响范围」。对代码细节的掌控确实不如以前深，但有 AI 辅助，风险相对可控。

王哲分享了一个角色转变的切身感受：

### 🔧 以前
王哲写完代码 → 找梧桐做 Code Review → 梧桐逐行审查

### 🤖 现在
王哲让 agent（zulu / ducc / dodo）做代码设计 → 王哲 review 方案 → agent 写代码 → 王哲 review 代码 → 提交给梧桐轻量 review

王哲的总结一针见血：「代码不是我写的，我从写代码的人，变成了 review 的人。」

工程师的角色在 AI 时代发生了深刻转变——从代码写作者，变为评审者与设计者。Review 时间减少了，但质量未必下降，因为评审逻辑从「逐行审查」转向了「结果导向」：功能有没有达成预期？影响是什么？值得注意的是，领域 expertise 依然重要——有些东西，AI 还是替代不了。



## 问题排查——AI First，但人不放手
出了线上 bug，是怎么排查的？AI 能自己查 bug 吗？最近一两周问题频发，团队是如何应对的？

王哲坦言，高频用户应该能感受到，最近一两周群里的问题确实不少。原因是多方面的——模型侧的压力水位、快速迭代引入的风险，都在叠加。团队在问题排查上投入了相当多的精力。

他们将问题分为三类，采用不同的处理策略：

### ① 陌生场景：AI First
绝大多数情况下，先让 AI 上——把现象交给 AI，让它结合代码分析可能的原因，梳理调用链路。再根据 AI 的指引，人工去看日志的关键词和位置，进一步定位问题。

### ② 重复问题：经验优先
对于反复出现的问题，团队已积累了处理经验。比如用户从 GLM5 切换到 Claude 模型后首轮报错，原因是模型间不兼容——遇到几次之后，简单确认现象即可直接给出解决方案。

### ③ 长链路效果问题：skill 串联
用户发出一个 query，模型思考 20 分钟后给出的结论与预期有偏差——比如调研报告主题偏移、内容保存位置不对等。团队沉淀了一套基于 coding agent 的问题排查链路，将用户流程中的关键环节串联起来，让dodo自己用这个 skill 定位问题所在。

王哲分享了一个令人印象深刻的案例：内测早期，服务还不稳定。有个同学反馈浏览器操作失败，王哲还没来得及看，那个同学又发来一张截图：「dodo告诉我，你们后端某个服务异常了，需要重启。」王哲看了dodo的分析逻辑，觉得非常有道理，重启后问题解决。

这个案例说明：当dodo被赋予足够的工具和上下文信息时，它有能力自主定位问题。团队也在探索更进一步的可能——用户在群里反馈问题时，dodo能否直接自动排查并给出解决方案？目前还涉及权限等问题，尚未找到优雅的实现方式，但未来可期。

问题排查从「人主导」转向「AI First，但人不放手」。信息串联是关键——当工具、上下文、日志等信息被有效串联，问题定位就不再完全依赖人。AI 可以成为强有力的助手，但最终决策仍需人来把关。那个「dodo自己诊断出服务异常」的案例，让人看到了 AI 智能体真正的潜力。

## 自我迭代——惊艳、风险与控制
dodo可以自己完成从开发到上线的全流程吗？长期让 AI 写代码，会不会让工程越来越脆弱？

梧桐说，自我迭代这种方式确实很酷。但她们也在实践中发现：AI 在自我迭代时，解决思路不一定符合预期——很可能偏离原有的架构风格，不按整体工程规约走。出现这种情况，团队会及时介入调整。

她也坦诚地承认：Vibe Coding 越多，工程看起来越脆弱。这是一个无法回避的现实。但她的态度是：**如果止损速度够快，这种风险是可以控制的。** 快速回滚、快速止损，本身就是一种有效的风险管理策略。

王哲则分享了他们评估「哪些需求适合让dodo自主完成」的判断框架：

### ✅ 适合自我进化
需求明确、改动范围小、方案收敛——比如「把左侧对话栏从按创建日期排序改成按更新日期排序」。拿这个需求问三个人，90% 给出相同答案，就可以直接交给dodo。

### ❌ 不适合自我进化
需要新建页面、大改后端逻辑，或者方案存在明显分歧——拿这个需求问三个人，三个人给出三种方案，就需要先和 AI 聊几轮把方案敲定，再让它写代码。

王哲特别强调了一种难以言传的「手感」：掌握这个工具的人，需要具备识别需求的直觉——什么场景可以直接让 AI 写代码，什么场景需要先把方案聊清楚。这种手感，是在长期协同中慢慢培养出来的，很难用规则完整描述。

自我迭代是 Vibe Coding 最惊艳的地方，也是最需要警惕的地方。dodo团队的应对思路很务实：与其试图让 AI 不犯错，不如建立快速回滚机制，让犯错后能迅速恢复。方案明确是 AI 自主开发的前提，而判断方案是否明确，恰恰是人最不可替代的价值所在。

## 测试——从「点点点」到智能测试
AI 能帮上测试的忙吗？前期没有专职 FE，测试是怎么做的？现在的测试体系是什么样的？

梧桐说，她现在的工作重心已经从「写代码」转向了「方案评审（与 AI chat）」和「测试」两大块。

最初项目 demo 刚跑起来时，没有 FE，前端由后端 RD 自己 vibe coding 出来——目前团队里最「脆弱」的那些前端页面，就是那时候写的。UI 迭代频繁、改动幅度大，测试只能回归到最原始的方式：**点点点**，纯人力。

后来接口开发多了，情况有所改善。梧桐介绍了她们当前的测试分布：

### 接口测试（占比↑）
直接跑通接口、验证端到端场景。比单测更能反映真实可用性，是目前占比最高的测试类型。

### 单测（占比↓）
AI 写单测容易引入大量 mock，无法真实验证链路是否跑通。与其测 mock，不如直接跑真实接口。

### 人工点点点（保留）
前端仍有部分场景需要人工 check，暂时无法完全自动化。

王哲从 QA 视角补充了后端测试的实践：他们将测试任务交给 zulu 或 ducc 等编码智能体，让它们在线下环境连接真实数据库，完成新功能开发后自动编写测试用例并执行。整条链路——造数据、灌数据、查任务、看效果、分析日志——基本跑通。

但这只是 agent 的「自测」环节。真正的质量保证，还需要人工再过一遍：边界条件和异常场景，agent 跑一遍就信；核心主流程，人工 double check。

测试在 AI 时代正在悄然重构。传统测试金字塔强调单测要多，但 AI 时代似乎在挑战这个假设——端到端测试的价值被重新发现。前期「点点点」的纯人力测试，不是落后，而是创业团队的真实写照：先跑起来，再逐步建立体系。

## 前端自动化测试——可行，但还不够
接入 browser use 之后，可以自动测试前端并自动修复吗？

王哲在加入dodo项目的前一年多，在 QA 团队主导了一个专项：前端测试智能化。这个专项的起点，是 Anthropic 发布 Claude 3.5 并支持 computer use 能力。团队开始探索用 AI 操控浏览器、从端到端做前端测试。

他的结论是：技术上，这条路是走得通的——AI 可以理解需求、拆解用例、逐步点击执行、观察效果。但现阶段存在三个明显瓶颈：

### ① 成本高
要保证高准确率，依赖的必须是国际顶级模型，成本相对高昂，安全合规上也存在顾虑。

### ② 速度慢
操作密集型用例（如需要点击数百步）交给模型会非常耗时。每执行几步，就要把最新浏览器状态传给模型分析，再决定下一步操作，整个轮询过程相当缓慢。

### ③ 规模化条件尚不成熟
目前更适合在特定项目中做验证性探索。能否大规模落地，主要取决于模型速度的提升和成本的下降——这两个条件具备后，才有可能在所有前端测试场景中批量推广。

至于能否自动修复？从逻辑上完全行得通。AI 反馈的问题描述往往比人更详细——执行了什么、遇到了什么、现象是什么，过程清晰完备。一旦测试链路整体跑通，问题反馈进入研发修复流程的后半段，会更加顺畅。

前端自动化测试展示了 AI 的潜力，也暴露了现实的约束。有些技术很性感，但就是无法大规模落地——这不是谁的问题，是技术本身还没到那一步。规模化的关键在于模型速度和成本，这是非常务实的判断。

## 团队分工——让长板变长
AI coding 之后，团队分工发生了哪些变化？与传统迭代模式相比，有什么不同？

梧桐说，dodo团队的分工不像传统迭代那么清晰，但有一个核心原则：让长板变长。

不是补短板，而是让每个人在自己最擅长、最容易发挥的地方，把那部分能力充分释放出来。比如王哲熟悉浏览器，浏览器相关方案就由他主导。遇到问题时，有时就是「谁有空谁去查」，大家可以互相 backup、互相支持。

梧桐觉得这个团队很有意思——有点像创业团队，早期有合伙人的感觉。没有传统意义上那么明确的分工，尤其早期大家都是 RD，设计、前端都兼着写。现在正在逐步向分工更清晰的方向过渡。

王哲补充说，每个人都有自己擅长的领域，每个模块会有一个默认的第一 owner。随着事情越来越多，工作会穿插交叉——同一个模块，可能同时有人做安全改造、有人修效果问题、有人分析 bad case。但有一个重要的底气：**强大的 coding agent 帮助拉齐了每个人对项目的理解下限**。大家即使不是自己写的代码，也能快速上手，互相 backup 的能力完全具备。

「让长板变长」是一种很有意思的团队哲学——不是平均主义，而是差异化发挥。AI coding 在这里扮演了「均衡器」的角色：它拉齐了项目理解的下限，让每个人都能参与进来；同时又不抹平个体差异，每个人依然能找到自己最闪光的位置。

## 关于热爱与技术敏感
作为「养育」dodo的研发同学，能给大家一些经验或建议吗？

梧桐没有从纯技术角度回答，而是分享了做这款产品的内心感受。

她提到一本书——《与神对话》。书中说，我们做选择时，背后往往基于两种驱动力：**爱，或者恐惧**。她觉得，dodo团队是一个充满爱的团队。做dodo，是出于对它真实的热爱，是真的希望它能帮大家解决问题。

「它现在可能是一个小而美的产品，但我更希望它是能真实帮我们解决问题的。这份热爱和兴趣，以及把它带进自己的产品里——是我这次最享受的部分。」

王哲则从技术人的视角给出了他的建议：**时刻保持对新技术的敏感和关注度。**

dodo团队能快速迭代，很重要的一个原因是：团队成员在很长一段时间里，都是 Vibe Coding 和 coding agent 的深度使用者，提前熟悉了这种工作模式。但即便如此，AI 发展之快，依然让人感到压力——稍一松懈，就可能错过重要的技术节点。

他举了一个例子：dodo刚启动一两周后，「龙虾」爆火，对团队产生了不小的冲击。他们花了很多精力分析龙虾与dodo的定位差异，提炼可借鉴的经验，帮助把dodo做得更好。

「这几年时代变化太快，保持对前沿技术的敏锐和观察，对所有人来说都是必要的。」

一个谈热爱，一个谈敏感。两个答案看似不同，其实指向同一件事：在这个 AI 工具满天飞的时代，真正稀缺的不是工具，而是内驱力——对产品的热爱，对技术的好奇，对变化的敏感。这些，才是 AI 替代不了的。

## 尾声：Vibe Coding 的真实样子
访谈结束，我在脑海中梳理了一遍dodo团队的故事。

这是一个从混乱中生长出来的产品——没有完整 PRD，没有专职前端，几个人凭着热爱和对新技术的敏感，在短短几个月里做出了一个真实可用、还在快速进化的 AI 智能体。她们踩了很多坑：代码风格不统一、前端脆弱、工程越来越复杂、线上问题频发……但她们没有回避这些，而是坦诚地说「还没有做好」，然后继续往前走。

如果用一句话总结 Vibe Coding 的真实样子，我觉得是：

**它不是银弹，但它是一种新的生产力范式。**

它让工程师从写代码者变成了设计者和评审者；让需求管理从「先想清楚」变成了「先动起来」；让测试从覆盖率驱动变成了结果导向；让问题排查从人工逐行分析变成了 AI First。它带来了速度，也带来了脆弱性；带来了自由，也带来了新的挑战。

但最打动我的，不是那些技术上的洞察，而是梧桐说的那句话：

> 「我们做dodo，是出于热爱。」
在这个 AI 工具满天飞、每周都有新模型发布的时代，热爱或许才是最稀缺的生产要素。技术会迭代，工具会升级，但一个团队对产品的真诚投入，对用户问题的真实关注，是 AI 替代不了的。

dodo还在成长，Vibe Coding 的故事还没有结束。而这场访谈，只是一个开始。
