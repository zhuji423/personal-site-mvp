# 把AI当搭档，不只是代码生成器——双写项目中的人机协同实战
> 作者：humingqing | 日期：2026-04-24 | 项目：baidu/session-box/redis-proxy
---

## 写在前面
redis-proxy 从 v1.7 走到双集群写入落地，是一场完全不同的挑战：v1.x 是从 0 搭建，AI 扮演"全能工匠"；双写是在生产系统上加装引擎，考验的是**如何在约束条件下做架构取舍**——人负责定约束，AI 负责在约束内找最优解。

本文只聚焦双写阶段，回答一个问题：**面对一个"看起来简单其实全是坑"的需求，工程师和AI怎么分工才能又快又稳地落地？**

---

## 一、需求来了——人先画牢，AI再填空
### 1.1 人定的四条铁律
双写需求一句话就能说完——"往两个集群写数据"。但工程师的第一反应不是"写代码"，而是"画边界"：

1. **客户端不能改**：上百个业务方用 jedis/lettuce/redis-py，谁也不动
2. **性能不能掉**：线上每秒数万 QPS，双写引入延迟超过毫秒级立刻被投诉
3. **数据不能丢**：备集群数据必须和主集群最终一致
4. **回滚要秒级**：万一双写出问题，必须能立刻切回单集群

**这四条就是牢笼。AI的活是在牢笼内找到最优解，而不是质疑牢笼本身。**

### 1.2 AI输出全景方案
拿到约束后，AI一次性输出了完整设计文档（DUAL_CLUSTER_DESIGN.md），包含：

* ConfigSnapshot 不可变快照 + atomic_store 原子替换——无锁热更新
* dispatch 热路径按 FLAG_WRITE 注入备集群客户端——读路径零侵入
* async_write_backup bthread 异步备写 + 指数退避重试
* 13 条命令各自的透传策略和触发条件
* 4 个 bvar 监控指标
* 本地双集群测试环境完整搭建方案（端口分配、配置差异、启动步骤）

**工程师的审核动作**：通读全文，确认三个关键决策点——

1. INCR 透传原命令而非差值（同意，多 proxy 场景差值会乱序）
2. EXPIRE 仅在主集群生效时转发（同意，key 不存在时转发毫无意义）
3. SET NX 备写时剥离条件标志（同意，主集群已判定可写，备集群无条件同步即可）

**协同模式**：人画牢 → AI填空 → 人审核关键决策点。这不是"人写伪代码、AI翻译"，而是"人定约束、AI设计架构、人做关键取舍"。

---

## 二、ConfigSnapshot——人与AI共同打磨的第一块基石
### 2.1 AI提出方案
AI提出不可变快照模式：ConfigSnapshot 包含 backup_clients[] 和 dual_write_enabled，通过 shared_ptr + atomic_store/atomic_load 实现无锁热更新。

核心逻辑：

* 请求线程拿快照，永远不加锁
* reload() 构建新快照后原子替换
* 没有 BackupClusters 配置时，dual_write_enabled=false，双写路径直接短路

### 2.2 人的追问
工程师追问了一个AI没有主动提到的问题：**reload() 时旧的 backup_clients 会不会被提前释放？**

答案是：atomic_store 后旧 shared_ptr 引用计数归零才会析构，正在使用旧快照的请求线程还持有引用，不会 UAF。AI确认了这个推理。

### 2.3 协同要点
AI 的设计能力很强，但对**运行时生命周期的微妙问题**有时需要人类追问。人不是在"改AI的代码"，而是在"追问AI没主动论证的安全边界"。

这是协同的核心模式之一：**AI画蓝图，人追问蓝图边缘的裂缝**。

---

## 三、异步备写——AI的关键洞察和人的否决
### 3.1 AI的关键洞察
AI提出了一个我没想到的调度顺序：**先提交备写，再做主写**。

理由：async_write_backup() 只是把数据打包提交到 ExecutionQueue，微秒级返回；然后主写 RPC 是同步调用，耗时毫秒级。两者天然并行，不需要额外的并发控制。

这个洞察极其巧妙——备写的提交成本几乎为零，和主写 RPC 并行执行等于"白送"并行度。

### 3.2 人的否决
AI最初建议用全局线程池管理备写。我否决了——bthread::ExecutionQueue 更适合：每备集群一个队列，天然串行化避免乱序，且 bthread 协程调度比线程池更轻量。

**AI的逻辑没有错，但人类对运行时环境的理解更深**：百度的 brpc 框架下，bthread 才是正确抽象。

### 3.3 重试策略的细节博弈
AI提出3次重试、指数退避。我追问了两个问题：

1. **成功条件为什么包含 not_found？**——因为 DEL 命令，key 不存在是合法终态
2. **退避间隔 100ms→200ms 会不会太激进？**——线上实测后确认合理，备集群正常时第一次就成功，异常时 100ms 等一次也够了

**协同模式**：AI给方案，人不改方案但追问每个参数的合理性。**不盲信，不盲改，问清楚再放行。**

---

## 四、命令转发——人否决"优雅"方案的经典案例
### 4.1 INCR 差值方案被否
AI列出了两个选项：差值方案（主集群INCR返回11，算delta=1，备写时PUT(delta)）和透传方案（备集群也执行INCR）。

差值方案更"优雅"，但在多 proxy 场景下会出问题：两个 proxy 同时 INCR 同一个 key，各自算出的 delta 到备集群可能乱序，导致数据不一致。

**人的决策**：透传原命令，保证最终一致。**优雅不等于正确，正确才是底线。**

### 4.2 EXPIRE 的条件转发
AI提出：主集群返回 integer==1 才转发。我追问为什么——因为 integer==0 表示 key 不存在，对不存在的 key 设 TTL 毫无意义，转发到备集群也是浪费。

这个条件转发避免了备集群的无效 RPC。

### 4.3 SET NX 备写剥离条件
AI提出备写时剥离 NX/XX 标志，无条件写入。理由：主集群已经用 NX/XX 判定了可以写，备集群不需要再判一次——它只需要无条件同步主集群的结果。

**这是一次"相信AI的推理"的决策**。AI的逻辑链条完整且正确，我直接采纳。

### 4.4 协同要点
命令转发这一章，展示了三种决策模式：

* **人否决AI的"优雅"方案**（INCR差值）
* **人追问后采纳AI方案**（EXPIRE条件）
* **人直接采纳AI方案**（SET NX剥离）

核心原则：**不看方案好不好看，看方案在约束条件下对不对。**

## 五、读路径零侵入——AI的系统性验证
双写最怕拖慢读路径。我的原则很明确：读命令完全不经过双写代码。

AI在 dispatch() 中只对 FLAG_WRITE 的命令注入 backup_clients，读命令的 RedisContext 里没有备集群信息——**代码路径本身就不存在**，而不是"存在但短路"。

性能实测验证了零侵入：所有读命令，单写和双写的 QPS 差异在 ±10% 以内——这就是测量噪声，不是影响。

**AI的价值**：设计零侵入架构 + 实测量化证明零侵入。人类说"不能掉性能"，AI把"不能掉"变成"可证明为零"。

---

## 六、64个E2E测试——AI穷举，人兜底
### 6.1 AI的穷举能力
AI设计了 5 大类 64 项 E2E 测试：

|类别|项数|覆盖|
|-|-|-|
|逐命令正确性|31|每个写命令主备数据一致|
|数据一致性|16|主写后读备集群、批量写一致性、TTL一致性|
|异步特性|9|备写不阻塞主写、备集群不可用不影响主集群|
|仅主读验证|6|读请求永远只走主集群|
|重试机制|2|备写失败后指数退避重试|

另有 15 个 Gtest 单元测试覆盖底层：ConfigSnapshot 字段、深拷贝安全、零备集群不崩溃、向后兼容回归。

还有一个 verify_dual_cluster.py 覆盖全部 16 种写命令做主备数据对比——上线前的"定心丸"。

### 6.2 人的兜底
AI 穷举了"正常路径"和"异常路径"，但有一个场景是工程师补的：**备集群先于主集群启动完成时，主集群还在 slot 创建中，此时写入会怎样？**

答案是：主集群写入失败返回错误，备写也不会触发（因为主写失败不触发备写）。这个边界AI没有主动测试，但人在灰度时发现了这个场景并补充了验证。

**协同模式**：AI穷举常规边界，人补充运行时环境特有的边界。两种边界能力互补。

## 七、DEL 的-76%——人发现问题，AI定位根因
### 7.1 性能灾难
|命令|单写 QPS|双写 QPS|下降|
|-|-|-|-|
|HMSET|10,552|10,239|-3.1%|
|HSET|6,260|4,090|-34.8%|
|**DEL**|**正常**|**暴跌**|**-76%**|

DEL QPS 暴跌 76%，p99 恶化 4 倍。

### 7.2 人发现，AI定位
我是在跑 benchmark 时发现这个问题的。但定位根因是 AI 的活——AI分析了完整链路：

1. DEL 用 async_write_backup_batch() 批量接口
2. WritePayload 深拷贝整个 keys 列表和 args_vec
3. 大量 key 时内存分配和拷贝开销远超主写 RPC
4. 备写 bthread 和主写 bthread 在 8 线程下竞争工作线程
5. 主写请求排队等待，延迟雪崩

### 7.3 协同要点
**人负责"发现问题"（跑benchmark），AI负责"定位根因"（全链路分析）。** 这是最典型的人机分工：人类对异常数字敏感，AI对因果链分析擅长。

DEL 优化标记为 P0 后续跟进。**知道瓶颈在哪里，比假装没有瓶颈要好得多。**

---

## 八、灰度上线——一行配置的勇气
### 8.1 AI设计的回滚方案
AI提出双写的开启/关闭只需一行配置：

```
BackupClusters: backup    # 加此行=双写，删此行=回退
```
reload 后秒级生效，不需要重新部署。

### 8.2 人定义灰度节奏
灰度流程由工程师定义：

1. 先 1 台机器，观察 bvar 指标
2. 确认备写成功率正常，扩到 5 台、20 台、全量
3. 任何异常，删配置行 reload 即可回滚

**AI设计"开关"，人决定"什么时候拨开关"。** 技术可行性和运维节奏是两件事。

---

## 九、未竟之事——AI已经设计好了
技术债清单上还躺着几项，AI已经完成了设计：

|优先级|项目|AI设计方案|
|-|-|-|
|P0|DEL 性能优化|零拷贝或增量提交方案|
|P1|备写延迟采集|backup_write_latency 框架已预留|
|P1|备集群健康检查|自动摘除不可用备集群|
|P2|CAS 双写|两个集群 value 不同步时需特殊设计|
|P2|读备降级|需要强一致，目前只有最终一致|

**协同模式**：AI的方案随时可用，人的决策决定什么时候启动。**"设计好了"和"做不做"是两件事，后者由人决定。**

## 十、方法论提炼——双写项目中的六条协同法则
从这次双写项目中，我提炼出六条人和AI协同的法则：

### 法则1：人画牢，AI填空
人定约束（性能不能掉、客户端不能改、数据不能丢、回滚要秒级），AI在约束内找最优解。不要让AI质疑约束本身——约束来自业务现实，不是技术偏好。

### 法则2：AI画蓝图，人追问裂缝
AI的设计能力很强，但对运行时生命周期的微妙问题需要人类追问。reload() 时旧 shared_ptr 会不会提前释放？主集群 slot 创建中写入会怎样？这些是AI不会主动论证的边界。

### 法则3：不看方案好不好看，看对不对
INCR 差值方案更"优雅"，但多 proxy 下会乱序。透传方案更"笨"，但正确。**正确才是底线，优雅只是加分项。**

### 法则4：人发现问题，AI定位根因
人对异常数字敏感（DEL -76%），AI对因果链分析擅长。人跑 benchmark 发现异常，AI做全链路分析定位根因。这是最典型的高效分工。

### 法则5：AI穷举常规边界，人补充环境边界
AI能穷举 64 项 E2E 测试覆盖所有正常和异常路径，但运行时环境特有的边界（备集群先于主集群启动）需要人补充。两种边界能力互补。

### 法则6：AI设计开关，人决定什么时候拨
一行配置开启双写是AI设计的开关。灰度节奏（1台→5台→20台→全量）是人决定的。技术可行性和运维节奏是两件事。

---

## 结语
如果把AI当代码生成器，你会得到一堆能跑的代码。如果把AI当搭档，你会得到：

* 人定约束、AI在约束内设计的架构（ConfigSnapshot + async_write_backup）
* 人的关键否决避免了线上事故（INCR差值→透传）
* AI的系统性验证让上线有底气（64项E2E + 15项Gtest）
* 人发现问题、AI定位根因的高效闭环（DEL -76%）
* AI设计的开关让人有勇气灰度（一行配置 + 秒级回滚）

**AI不是你的打字机，它是一个系统性思维的搭档——你定方向，它填细节；你追问裂缝，它论证边界；你发现异常，它定位根因。当你学会这样和AI协同，1+1就不再等于2，而等于5。**
