灵犀运维智能体 - 网管平台智能门户

#### 🧑‍🏫 案例作者：[@晁岳攀](https://ku.baidu-int.com?t=mention&mt=contact&id=54007220-fcde-11f0-81c6-e16fc4832a99)
#### 🎬 案例场景：运维
#### 🔧 使用工具：Model Builder，Comate
#### 📒 案例概要：百度推出的灵犀运维智能体，通过大模型技术实现了网络运维的智能化。它利用LLM进行深度分析、故障定位，并提供综合门户服务，支持自然语言交互。采用Planning、Tool Use和ReAct模式，结合多智能体协作，提高了运维效率和准确性。同时，灵犀智能体支持多种大模型，具备良好的扩展性和可重用性。


"推理任务 job-0bb39798bbfe6a4e 今天凌晨2点半的时延有问题吗？"， 这是在运维中常见的一个场景。以前，我们的同学会登录高性能网络时延平台，输入任务ID和时间返回，查询出热力图，根据经验进行人工分析，查看是否有异常的时延数据。

![](/personal-site-mvp/img/doc-placeholder.svg "")
现在，我们只需在灵犀运维智能体平台的对话框中输入这句话，灵犀智能体就能够自动进行查询和分析，给出一个全面的分析报告。从这个热力图上，我们可以看到同一Tor组中服务器(对角线上的方块)之间访问时延很少，跨Tor组的服务器之间的时延稍微大一些，跨房间的服务器之间的时延会更大，没有明显异常的时延数据。

当然这需要有经验的、熟悉网络拓扑的运维同学才能从图中解析出这些信息，其他同学并不知道这张图隐含的意义。

如果我们把时延和拓扑数据交给LLM进行分析，它会结合拓扑对时延数据进行分析，并且给出最终的结论：当前每一组的时延是否正常，时延数据是否符合实际数据、如果有异常，是哪一组或者哪些组有异常，该怎么检查，LLM会分析的明明白白的：

![](/personal-site-mvp/img/doc-placeholder.svg "")






这是智能云灵犀运维智能体的一个常见的使用场景。





我们是百度系统部物理网络黑盒监控团队，负责百度物理网络故障监控和定位。随着公司网络、机房规模的逐步扩大，尤其是最近几年云和AI网络的爆发，我们开发了十几个网络监控平台、覆盖了数十个网络监控场景。针对物理网络精细化的监控，为运维同学提供及时和准确的告警和定位信息，并且联动自动止损平台进行自动化的止损能力，可以说，现在的网管平台为百度网络的稳定性提供了全面的快速的「监控-定位-止损」能力。



随着大模型技术的应用，尤其是2025年各种通用智能体和垂类智能体的不断涌现，我们也针对的我们物理网络网管方向，探索和推出了针对网管和运维方法的智能体 - **灵犀运维智能体**，并且针对实际的场景，针对性的实现了比较适合大模型应用的AI场景：

* 针对各种场景的深度分析：利用网管平台的各种采集的数据，使用大模型进行深度分析，生成有深度的分析报告。
* 针对长尾故障的定位分析：因为大模型推理的时效性比较慢，不太适合秒级的告警。但是对于长尾的故障，比如不容易定位的改包、未知的轻微的丢包行为等，可以利用大模型，结合网管平台的各种数据，让大模型进行细致的分析和故障定位。
* 网络故障综合门户：我们的平台不仅仅为运维同学使用，公有云、业务等等同学都可以使用。但是这些同学不了解物理网络的内部细节，他们更希望能够通过自然语言进行咨询，利用大模型，可以将用户的自然语言生成物理网络的概念，进而调用相应的网管平台的服务，生成查询的结果，然后图文并茂的将结果以更容易理解的方式返回给用户。



## 回顾
![](/personal-site-mvp/img/doc-placeholder.svg "")
最早我们的物理网络运维更多的通过人工的方式进行排障，基本依赖业务的保障和业务提供的现象，进行人工的分析登录设备进行检查，或者通过经验积累编写了一些脚本半自动的进行故障定位，这是网管最原始的一种状态，也是物理网络建设之初的必经之路。因为是手工处理，故障的发现、定位和处理都需要耗费非常长的时间。



随着公有云的快速发展和集团云对网络稳定性的需求越来越高，我们针对各种场景开发了各种监控平台，并逐渐演化处理了黑盒和白盒两个方向：白盒方法主要针对交换机等网络设备的日志进行分析、对网络的设备的指标进行采集和告警、对流量进行监控、对高性能网络和服务器的指标进行采集等等；黑盒方式主要通过探测的方法，通过PingMesh、雷达扫描等方式对骨干网、机房、网关等场景进行秒级的故障监控和定位、对改包、大包、回切等特殊场景进行监控、提供各种定位工具进行分析、提供时延数据进行性能分析。通过近几年的网管平台建设，百度物理网络已经建设了稳定可靠的监控和定位平台。



去年我们引入AI的能力，尝试通过大模型进行故障的综合定位，相关的公众号文章可以参考：[百度智能云将大模型引入网络故障定位的智能运维实践](https://mp.weixin.qq.com/s/bUNMvP2vZajRZSRHor46aQ?t=mention&mt=doc&dt=sdk)。今年我们更进一步，结合当前炙手可热的智能体的概念，开发了灵犀运维智能体，期望利用大模型和智能体的技术，深度挖掘物理网络网管和运维的能力，提供更智能更便捷的运维功能。



灵犀智能体采用流行的chat模式，和用户的交互通过一个对话框完成。用户在对话框中输入网管运维相关的问题，灵犀智能体制定「推理-计划-行动」计划，按照计划调用相应的工具，最终输出一个推理的结果：

## 架构设计
![](/personal-site-mvp/img/doc-placeholder.svg "")
整个灵犀智能体采用 Planning pattern、Tool Use pattern 和 ReAct pattern实现。智能体接收到用户的prompt后，调用LLM进行推理和计划(planning)，得到下一步Action。在执行下一步的Action，通过MCP调用相应的外部服务(tool use)，得到服务器的结果，再交给LLM进行观察和分析(ReAct)，然后确定是否进行下一步计划，或者已经完成任务返回给用户。



让我们以文章最开始的时延任务为例，逐步介绍整个的流程：

* ① 用户输入『推理任务 job-0bb39798bbfe6a4e 今天凌晨2点半的时延有问题吗？』，提交给灵犀智能体。
* ② 灵犀智能体让大模型进行推理和计划，以便确定下一步的Action。
    * 这一步我们会把我们实现的Thinking Tool以及其它的MCP工具的信息、系统提示词和用户的prompt提交给LLM
    * 大模型会返回整个任务的计划，需要的步骤以及下一步要执行的Action。
    * 灵犀智能体会把Thinking Tool的信息附加在消息中，再次请求LLM，获取到下一步要调用的MCP 工具(时延MCP)和参数(job ID和时间戳)

* ③ 灵犀智能体调用时延MCP,并传入job ID和时间戳参数，这里使用的是MCP协议
* ④ 时延MCP工具首先查询网管时延平台，得到此任务在查询时间点的时延数据
* ⑤ 时延MCP工具再根据job ID, 查询拓扑信息，包括网络信息以及房间信息
* ⑥ 这里有两种处理方式，我们采用b方式处理。一是容易进行业务隔离，负责时延的小组有相关的经验，可以让他们去实现时延MCP，而是下文会介绍的前端优化，避免让LLM生成HTML代码，优化体验。

    1. 直接把时延数据和拓扑信息返回给灵犀智能体，灵犀智能体调用LLM进行分析，再调用报告生成MCP
    2. 时延MCP拿到job的时延数据和拓扑数据后，自己调用LLM进行分析，生成分析报告，返回只灵犀智能体

* 智能体拿到MCP工具的返回结果后，再调用LLM，确定是否完成任务，还是再执行下一步的Action
* 如果任务已经执行完或者达到最大的执行步骤，灵犀智能体把结果返回给用户



下面是几个具体点的设计。

### LLM大模型
在“灵犀智能体”的设计中，我们并没有将其绑定到某一个特定大模型上，架构之初便确立了“模型无关”的核心设计，使其能够无缝集成并智能调用业界最前沿的大语言模型。

目前，平台已全面支持并深度集成了包括 **文心一言、DeepSeek、通义千问、全系列OpenAI模型（如GPT-4o、GPT-3.5-Turbo）以及最新的Claude 3.7 Sonnet** 等当前最流行的大语言模型。

我们线上运行的灵犀智能体采用OpenAI API兼容的接口，使用[百度千帆大模型平台](https://cloud.baidu.com/product-s/qianfan_modelbuilder)支持的各种模型和API。实践中，我们采用 [deepseek-v3 模型](https://console.bce.baidu.com/qianfan/modelcenter/model/buildIn/detail/am-a5by98lum8se)作为智能体的主要模型进行推理，使用 [ernie-4.5-turbo-128k](https://console.bce.baidu.com/qianfan/modelcenter/model/buildIn/detail/am-xpgukxjf6s0r?tab=version) 进行特定场景(在MCP Server中，架构图看看看是否需要扩充)的数据分析，使用 tao-8k embeddings模型进行RAG相关的探索。

### 设计模式
Planning pattern、Tool Use pattern、ReAct pattern 和 Multi-Agent pattern是常用的智能体设计中的模式，而且经常会被组合起来使用。在灵犀智能体中，也采用了这几种模式。



**Multi-Agent pattern**

Multi-Agent pattern 涉及多个智能体协作，每个智能体可能有不同角色，智能体组合起来处理大型复杂的任务。灵犀智能体通过A2A实现接入其它智能体、比如智能网关智能体、变更操作智能体等，用来处理网关类问题和变更操作的问题。



**ReAct pattern**

ReAct pattern（Reasoning and Acting，推理与行动）也是一种智能体实现的常见模式，它将大型语言模型（LLM）的推理能力与使用工具执行动作的能力结合在一起。它通过迭代式地进行**推理、行动和观察**来运作，以模仿人类解决问题的方式。这种方法使得代理能够通过利用外部工具并保留先前步骤中的信息，来动态地调整其处理复杂任务的方法。

**ReAct 的工作原理：**

1. **推理 (Reasoning):**代理分析一个任务，并将其分解为更小的步骤，根据可用的信息和工具来决定采取何种行动。
2. **行动 (Action):**代理使用工具（如搜索引擎、数据库或其他API）与外部环境互动，以收集信息或执行特定任务。
3. **观察 (Observation):**代理观察其行动的结果，并将相关信息存储在记忆中以备将来使用。
4. **迭代 (Iteration):**代理重复“推理、行动、观察”的循环，直到达成预期目标或找到满意的解决方案。



我们通过在单次Action的执行中应用ReAct模式，将Action的执行结果提交给LLM观察分析，并保存在记忆中将来使用。



**Planning pattern**

planning pattern是当前智能体处理复杂任务的使用的一种模式，Anthropic公司发现了一种特别有效的方法：一种“think”工具，在复杂任务中为结构化思考创建专门的空间。Anthropic后来开发了一个专门用来实现Think的MCP Tool，也就是大名鼎鼎的 [Sequential Thinking](https://github.com/modelcontextprotocol/servers/tree/HEAD/src/sequentialthinking)，这个工具旨在通过结构化的思维过程帮助用户解决复杂问题，支持动态调整和分支推理。

事实上灵犀智能体自己实现了一个更简单的Thinking Tool, 因为我们只需要一个简单的推理和规划工具，所以我们使用Go语言实现了一个简单的工具如下：

```
package mcp

import (
    "context"

    "github.com/kataras/golog"
    "github.com/mark3labs/mcp-go/mcp"
)

func (s *Server) thinkAndPlan(_ context.Context, req mcp.CallToolRequest) (*mcp.CallToolResult, error) {
    golog.Infof("thinkAndPlan report start")
    defer golog.Infof("thinkAndPlan report end")

    return mcp.NewToolResultText("think_stop"), nil
}

    s.Server.AddTool(mcp.NewTool("think_and_plan",
        mcp.WithDescription("这是用于系统化思考与规划的工具，支持用户在面对复杂问题或任务时，分阶段梳理思考、规划和行动步骤。工具强调思考（thought）、计划（plan）与实际行动（action）的结合，通过编号（thoughtNumber）追踪过程。该工具不会获取新信息或更改数据库，只会将想法附加到记忆中。当需要复杂推理或某种缓存记忆时，可以使用它。"),
        mcp.WithString("thought",
            mcp.Required(),
            mcp.Description("当前的思考内容，可以是对问题的分析、假设、洞见、反思或对前一步骤的总结。强调深度思考和逻辑推演，是每一步的核心。"),
        ),
        mcp.WithString("plan",
            mcp.Required(),
            mcp.Description("针对当前任务拟定的计划或方案，将复杂问题分解为多个可执行步骤。"),
        ),
        mcp.WithString("action",
            mcp.Required(),
            mcp.Description("基于当前思考和计划，建议下一步采取的行动步骤，要求具体、可执行、可验证，可以是下一步需要调用的一个或多个工具。"),
        ),
        mcp.WithString("thoughtNumber",
            mcp.Required(),
            mcp.Description("当前思考步骤的编号，用于追踪和回溯整个思考与规划过程，便于后续复盘与优化。"),
        )),
        s.thinkAndPlan)
```
这个工具引导了大模型进行推理和拆解任务，我们会在前端把大模型的思考、计划和行动打印出来：

**Tool Use pattern**

Tool Use pattern 应用在MCP工具的调用上。模型上下文协议（MCP）是一种标准化协议，将 AI 代理连接到各种外部工具和数据源，提供了一种扩展智能体能力的模式，允许智能体调用外部工具或 API，如搜索引擎、计算器或数据库。想象一下，它就像 USB-C 端口——但针对 AI 应用程序。

![](/personal-site-mvp/img/doc-placeholder.svg "")


MCP（模型上下文协议）最初是由 Anthropic 发起的一个项目，旨在让像 Claude 这样的 AI 模型更容易与工具和数据源进行交互。MCP 提供了统一的方式让 AI 模型与不同的数据源和工具进行交互，无论是文件系统、数据库、API 还是其他服务。尤其是今年，它发展迅速，不仅被OpenAI、Google等顶级厂商锁接纳，而且在众多的新的智能体实现中广泛采用，大量的类似claude桌面版客户端如cherry studio、deepchat等桌面版客户端都可以方便的集成、而且类似 cursor等智能编程工具也都支持，虽然目前还有安全、流式支持不广泛等一些担忧，但是它的前景还是非常光明的。



我们逐步将我们各种的网管平台的服务封装成MCP工具，可以为灵犀智能体提供访问网管平台的能力、也能为其它智能体提供服务器。比如我们将我们的大模型时延平台的数据提供为MCP服务，我们将骨干网网络监控的服务提供为MCP服务、我们将后羿综合定位系统提供为MCP服务...



灵犀智能体所有和外部资源交互的场景都通过MCP Server来实现:

* 扩展性好：新的MCP服务都可以通过一行配置引入到灵犀智能体,比如下面四行配置了 4 个MCP工具。新增加一个MCP工具，只需在配置文件中增加一行，key是工具的名称，value值是MCP工具的地址：

```
{
    "lingxi_basic": "http://xxx.xxx.xxx.xxx:8890/sse",
    "3a":"http://xxx.xxx.xxx.xxx:8889/sse",
    "cr7-server":"http://xxx.xxx.xxx.xxx:8090/sse",
    "cover-server":"http://xxx.xxx.xxx.xxx:8393/sse"
    ...
}
```
* 便于工程管理和实现：整个的网管和运维涉及到多个组，如果组织这些组围绕一个智能体项目开发，其实是一件非常难于管理的事情，但是通过使用MCP协议，每个组各自可以开发自己的业务服务，通过MCP Server方式提供出来，这和各个组日常的工作内容保持yi一致，并且组之间能够独立的进行开发，极大的减少了组之间的沟通成本。
* 可重用性：通过使用MCP协议，可以把我们既有的网管和运维服务封装成一个个的MCP服务，不但可以被灵犀智能体使用，而且还可以被其它MCP Server调用，甚至可以被其它的智能体所调用。

### 前端开发
灵犀智能体的前端都是通过[comate zulu](https://cloud.baidu.com/doc/COMATE/s/vm66asjm4)实现的，现在利用AI可以很好的实现前端的需求。



对于展示MCP Tool的结果，我们也希望能够使用漂亮的网页展示，比如下面的查询IP地理信息的页面：

![](/personal-site-mvp/img/doc-placeholder.svg "")




这些前端的实现并不是通过『报告生成MCP工具』生成的。原因在于实际在运行中，我们发现将数据展示出复杂和漂亮的网页，大模型需要2分钟以上的时间，并且会耗费大量的输出Token。为了优化数据的展示，我们采用先将数据扔给大模型，使用『报告生成MCP工具』相同的提示词， 生成一个漂亮的网页，并且网页中的数据是以json格式提供，动态渲染。这样我们在时延MCP这样的工具中，把这个网页作为模板，它的json数据每次都以MCP Tool返回的结果填充，这样就可以快速(秒级)生成一个漂亮的网页了。这也是我们工程实践中做的一个优化。

## 展望
我们在开发灵犀智能体时候，也对目前流行的其它技术进行了探索，比如A2A、RAG等技术。

### A2A
可以预见，在公司未来的生态中，会存在这各种各样的智能体，每个部门都会在这方面进行探索和开发。部门时间跨度越大，智能体之间的交流也越困难。最近，谷歌联合Atlassian、Box、Cohere、Intuit、Langchain、MongoDB、PayPal、Salesforce、SAP、ServiceNow、UKG 和 Workday 等 50 多家技术合作伙伴以及埃森哲、BCG、Capgemini、Cognizant、德勤、HCLTech、Infosys、毕马威、麦肯锡、普华永道、TCS 和 Wipro 等领先服务提供商，发布了名为 Agent2Agent (A2A) 的全新开放协议。凭借 A2A 协议，AI 智能体将能够在各种企业平台或应用程序之上相互通信、安全地交换信息和协调操作。



A2A 是一个开放协议，是对 Anthropic 的模型上下文协议 (MCP) 的补充，MCP 为智能体提供了有用的工具和上下文。 A2A 协议应对为客户部署大规模、多智能体系统时遇到的挑战。借助 A2A 协议，开发者可以构建能够与使用该协议构建的任何其他智能体建立连接的智能体，让用户能够灵活地组合来自各种提供商的智能体。



比如我们正在构建故障问答的智能体，一旦故障问答的智能体上线，灵犀智能体就可以和它交互，任何提交给灵犀智能体的网络故障问题，都转交给故障问答智能体来处理。

### 结束语
时光回溯到2009年8月18日， “**框计算**”（Box Computing）诞生日，百度董事长兼首席执行官[李彦宏](https://baike.baidu.com/item/%E6%9D%8E%E5%BD%A6%E5%AE%8F/125160?fromModule=lemma_inlink)在[2009百度技术创新大会](https://baike.baidu.com/item/2009%E7%99%BE%E5%BA%A6%E6%8A%80%E6%9C%AF%E5%88%9B%E6%96%B0%E5%A4%A7%E4%BC%9A/8957988?fromModule=lemma_inlink)上提出『框计算』的概念。用户只要在”[百度框](https://baike.baidu.com/item/%E7%99%BE%E5%BA%A6%E6%A1%86/9789875?fromModule=lemma_inlink)”中输入服务需求，系统就能明确识别这种需求，并将该需求分配给最优的内容资源或应用提供商处理，最终精准高效地返回给用户相匹配的结果。这种高度智能的互联网需求交互模式，以及“最简单可依赖”的信息交互实现机制与过程，称之为“框计算”。  



时间来到了2025年，这已经是『大模型的世界、应用的天下』。如何利用大模型，为框计算插上AI的翅膀，为框的计算赋能人工智能的能力，为用户提供更准确、更丰富、更多元化的查询结果？这是『灵犀智能体』尝试探索的方向。 结合我们自身的网管运维工作方向，我们尝试在网络运维领域实现 了**『AI加持的框计算』**，进行了有益的实践。
