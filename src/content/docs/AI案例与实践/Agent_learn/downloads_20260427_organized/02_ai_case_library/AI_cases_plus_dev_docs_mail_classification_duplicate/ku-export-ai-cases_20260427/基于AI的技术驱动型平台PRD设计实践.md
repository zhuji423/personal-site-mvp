## 1.1 技术平台的特殊性
对于特征平台、数据平台等技术基建类平台，与业务系统相比有其独特性。这类平台服务于公司内部的技术团队，业务属性弱、技术属性强，用户本身就是技术人员，需求往往来源于技术演进和架构优化，而非业务方的功能诉求。

|**特点**|**说明**|
|-|-|
|用户即开发者|平台使用者以算法工程师、数据分析师等技术人员为主，具备专业技术认知，对产品功能和使用目标有清晰明确的预期。|
|需求与实现高度匹配|功能边界由底层技术能力决定，研发人员既是需求提出方也是落地实现方，对技术实现路径与可行性有最直接的判断。|
|领域专业门槛较高|需求涉及特征工程、模型训练等大量专业领域知识，知识体系复杂，全面掌握需要投入较多时间成本，整体学习投入产出比有限。|
|痛点感知存在视角差异|底层基建相关痛点多来自研发日常技术工作中的实际积累，研发团队对这类问题天然更为敏感，产品侧较难从常规视角直接感知。|
|交互模式标准化|界面以表单、列表、配置页等标准化交互形式为主，交互逻辑统一规范，无需进行复杂的个性化体验设计。|

## 1.2 传统研发流程的问题
```
业务 → PM需求澄清 → PM画原型 → PM写PRD → RD参与评审 → ...
```
|**痛点**|**具体表现**|
|-|-|
|**信息传递链路长，易出现理解偏差**|多方协作沟通下，信息在传递过程中容易产生偏差，最终导致方案与实际诉求不匹配|
|**原型手工制作效率有限，迭代成本偏高**|单个页面制作需耗时 0.5-1 天，修改调整成本较高，存在较多重复性工作|
|**技术可行性验证环节偏后置**|方案推进至研发评审阶段，才发现部分设计存在技术落地难度，易引发反复调整返工|
|**专业技术领域的需求设计门槛较高**|涉及算法、特征工程等专业性较强的领域，开展需求设计时需要投入较多时间学习业务与技术背景，快速切入难度较大，整体周期偏长|

# 3.实践详解
## 3.1 需求澄清
例如在**特征挖掘平台**等技术性的改造项目中，需求比较多元。一部分来自算法组的一线同学，他们对业务场景和技术痛点非常清楚，但表达出来的需求通常比较简短，比如"希望基线能支持版本管理"等。另一部分需求则是RD在深挖代码和梳理系统逻辑时主动发现的——比如某个流程存在隐患, 哪些点可以结合业内工程实践优化等，这类需求更偏技术驱动，需要RD自己定义问题边界。

无论哪种来源，这类需求背后都涉及大量技术细节：基线与特征簇的关联关系、样本实验的定版逻辑、版本间的数据继承策略等。如果不主动深挖，很容易停留在表面理解，开发到一半才发现方案对不上。

传统模式下，PM来做需求澄清会面临双重门槛：一是**领域知识门槛**——什么是特征簇？定版是什么意思？实验继承的边界在哪里？二是**技术理解门槛**——很多问题需要深入代码才能搞清楚，而PM通常不具备读代码的能力。这些问题不深入理解底层逻辑很难问到点上。**而RD虽然懂技术，但往往缺乏结构化提问的经验，容易遗漏关键维度****。**

因此我们让RD主导需求澄清并承担PRD设计:RD直接对接业务方，将技术调研和方案设计前置到需求阶段，减少中间环节的信息传递偏差；在RD完成业务对齐和技术调研后，借助大模型系统化地生成澄清问题清单，帮助非产品背景的RD做更全面的思考和验证。这些本该由PM把控的维度，现在通过Prompt模板让RD也能覆盖到。这样既能发挥RD的技术理解优势，又能弥补RD产品经验的不足。**需要注意的是，AI的作用是辅助而非替代**，与业务方反复对齐、调研业界同类产品的功能设计、梳理技术可行性——这些工作仍然需要RD完成，无法被AI替代，因为它们涉及真实的业务场景理解和技术判断。

### 3.1.1 阶段目标
借助AI生成结构化的澄清问题清单，希望：

* 覆盖更全面：从多个维度检查，减少遗漏
* 问题更有深度：不只是表面提问，挖掘隐藏需求
* 沟通更高效：避免重复和业务方确认，减少来回沟通成本
* 经验可复用：模板化沉淀，保证输出质量稳定

### 3.1.2 Prompt模板设计
#### 设计思路
|设计要点|说明|
|-|-|
|角色设定|"产品经理+技术专家"双重身份，既关注业务价值也考虑技术可行性|
|结构化输出|5个固定模块，保证每次输出质量稳定、维度完整|
|问题分级|区分"必须澄清"和"建议澄清"，聚焦关键决策点|
|选项引导|每个问题给出可能选项，减少开放式讨论的沟通成本|
|风险前置|主动识别隐含假设和潜在风险，避免后期返工|
|历史文档输入|支持上传历史PRD、架构文档、会议纪要等，帮助大模型理解上下文，生成更精准的澄清问题|

#### Prompt模板
```
你是一个资深的产品经理 + 技术专家，擅长从模糊需求中挖掘关键信息。

请帮我对以下需求进行全面澄清分析，目标是：
1. 理解需求本质，避免表面理解
2. 识别模糊点和歧义，生成高质量澄清问题
3. 发现隐藏需求和潜在风险
---
【原始需求】
{输入原始需求}
【补充背景】（可选）
- 所属系统：
- 现有功能：
- 需求来源：

【历史文档】（可选）
{上传文档并粘贴文档名或粘贴关键内容}
---
请输出：
## 1. 一句话理解

## 2. 已明确的信息

## 3. 待澄清问题清单
按优先级分类，每个问题说明「为什么要问」和「可能的答案选项」

### 必须澄清（影响需求边界）
| 问题 | 为什么要问 | 可能的选项 |
|------|-----------|-----------|

### 建议澄清（影响实现方案）
| 问题 | 为什么要问 | 可能的选项 |
|------|-----------|-----------|

## 5. 潜在风险
可能的坑点
```
#### 为什么这样设计？
**传统流程的问题**：业务方提需求 → PM理解 → PM澄清 → PM转述给RD → RD再理解。每个环节都有信息损耗。

**这个模板的价值**：RD直接对接业务方，用结构化的问题清单一次性完成澄清。AI辅助覆盖产品视角，RD补充技术判断，两者结合减少遗漏。

### 3.1.4 效果评估
此步骤ai的作用更多类似于辅助分析,帮助查缺补漏, 正确性和可执行性依旧依赖于人工对齐.

|**评估维度**|**结果**|
|-|-|
|结构完整性|5个模块全覆盖，层次清晰|
|问题深度|挖掘出6个待澄清问题，覆盖边界、方案、数据模型等维度|

（1）从输出结果可以看到，仅两句话的原始需求，AI输出了结构化的澄清分析。特别是"子版本与父版本的数据关系"、"发布流程"、"版本嵌套层级"等问题，如果没有提前澄清，很可能在开发阶段才发现理解偏差。

（3）通过Prompt模板，即使是缺乏产品经验的RD，也能快速生成专业的澄清问题清单，大幅降低沟通成本和返工风险。

### 3.1.5 多轮调优技巧
Prompt模板能帮我们快速生成结构化的澄清问题清单，但一次对话往往不够。实际场景中，我们会拿到业务方的回答需要继续深挖，会发现新的技术约束需要重新评估，会担心某些视角有遗漏需要交叉检查。

以特征挖掘平台为例，基线子版本这个需求涉及版本关系、实验继承等多个维度，业务方的第一轮回答往往只覆盖主流程，边界情况和异常处理需要通过多轮对话逐步挖掘。

以下是我们沉淀的5个调优技巧：


#### 技巧1：追加业务方回答，让AI继续深挖
**使用场景**：拿到业务方的回答后，让AI分析是否还有遗漏

**特征平台实践**：业务方回答"子版本可以继承父版本的实验"，但没说清楚继承的是实验数据还是实验状态、继承后能否修改、多个子版本之间是否共享。追加回答让AI深挖，能把这些模糊点暴露出来。

**Prompt示例**：

```
业务方对上述问题的回答如下：

Q1: 子版本如何继承父版本的实验？
A1: 勾选需要继承的实验，继承后直接标记为已定版

请基于这些回答：
1. 这些回答中有哪些点本身还不够清晰，需要进一步追问？
2. 基于这些回答，是否能推断出之前没想到的新问题？
```
#### 技巧2：补充约束条件，重新分析
**使用场景**：发现新的限制条件，让AI重新评估

**特征平台实践：** 在特征挖掘平台中，算法同学会基于基线进行建模实验，实验完成后需要生成建模报告（包含模型效果指标），并支持不同版本之间的效果对比。和算法同学沟通后明确了两个约束——建模报告直接复用原有建模平台，版本对比需要突出KS、AUC指标。这些约束会影响需求边界：报告复用意味着不用考虑报告生成逻辑，但版本对比需要进一步明确对比维度、展示形式（表格还是趋势图）等。补充给AI后能聚焦真正需要澄清的问题。

**Prompt示例**：

```
补充以下约束条件，请重新分析需要澄清的问题：

- 建模报告直接复用原有建模平台
- 版本对比需要重点突出KS、AUC指标对比
```
#### 技巧3：切换视角，发现盲区
**使用场景**：担心遗漏，让AI从不同角色视角检查

**特征平台实践**：RD容易聚焦在数据模型和接口设计上，但可能忽略前端的交互细节（比如版本树怎么展示）、测试的边界场景（比如并发创建子版本）、算法同学的使用习惯（比如是否需要批量继承）。切换视角能补齐这些盲区。

**Prompt示例**：

```
请分别从以下角色视角，检查是否有遗漏的澄清点：

1. 后端RD视角：数据存储、接口设计、性能瓶颈
```

### 3.2.3 多轮调优技巧

### 技巧1：深化功能分析
**使用场景**：某个功能需要更详细的拆解

**特征平台实践：** 需求澄清输出的"创建子版本"只是一个功能点，但实际开发时发现细节不够：创建时继承父版本配置是自动完成还是可选？样本定版状态的继承是全部继承还是逐个勾选？继承后的子版本能否再修改配置？让AI对这个功能深度拆解，能输出完整的子功能清单和交互流程，避免开发到一半才发现逻辑没想清楚。

**Prompt示例**：

```
请对功能「创建子版本」进行深度分析：
1. 拆解为更细粒度的子功能
2. 详细描述每个步骤的交互逻辑
3. 列出所有边界条件和异常场景
```
### 技巧2：技术方案深化
**使用场景**：需要更详细的技术评估

**特征平台实践：** 基线列表要支持树形展示父子版本关系，但具体怎么实现还没想清楚——是前端一次性加载全部数据做树形渲染，还是后端分层查询按需加载？现有的基线列表接口能不能直接扩展，还是要新建接口？让AI从技术角度深入分析，能提前暴露方案选择和改造成本。

**Prompt示例**：

```
请从技术实现角度，深入分析：

1. 树形列表的数据加载方案有哪些选择？各有什么优缺点？
2. 现有基线列表接口能否复用？需要哪些改造？
3. 大量子版本场景下有哪些性能风险？
```
### 技巧3：切换视角检查完整性
**使用场景**：担心分析有遗漏

**特征平台实践：** RD做需求分析容易偏重后端逻辑，但前端同学拿到后发现树形表格的展开收起交互没定义清楚、版本类型标识怎么展示没说明；测试同学发现边界场景没覆盖（比如父版本下有多个子版本时的排序规则、筛选条件和树形展示的联动逻辑）。让AI从多视角检查，能在评审前补齐这些盲区。

**Prompt示例**：

```
请分别从以下视角检查需求分析是否完整：

1. 前端视角：树形表格交互、筛选联动是否清晰
2. 后端视角：接口设计、数据结构是否明确
3. 测试视角：边界条件、异常场景是否覆盖
```
## 3.3 原型设计
需求分析阶段输出了功能清单、页面规划、核心字段和业务规则，但这些仍是文字描述，距离可落地的开发还有一段距离。原型设计阶段要做的是将这些抽象描述转化为可视化的界面——让业务方看到"未来产品长什么样"，让RD明确"具体要开发什么"。

在技术驱动型平台场景下，原型设计涉及复杂的数据结构展示和专业的交互逻辑（如实验继承）。这类技术细节需要熟悉系统的人来表达.

我们延续"RD能力前延"的思路——由RD直接主导原型设计，借助大模型辅助生成初版原型，再通过多轮对话完善交互、字段、数据和规则。RD既懂技术边界又了解用户场景，能在原型阶段就将技术约束融入设计，避免后期返工。

**整体流程**


**为什么要分步骤、多Skill协作完成原型设计？**

 原型设计不是简单的"画个界面"，而是一个从粗到细、逐步完善的过程：先确定整体布局和交互流程，再细化字段定义和数据结构，最后明确业务规则和接口契约。如果试图用一个Prompt一次性生成完整原型，会面临几个问题：

### 3.3.3 **原型初稿生成**

#### 3.3.3.1 Skill设计思想
原型初稿生成Skill的核心设计理念是"**团队统一 + 结构化输入 + 风格可配置 + 渐进式输出**"，让不同技术背景的RD都能快速生成符合规范的页面原型。


**Skill文件说明**

**SKILL.md - 主技能定义文件**

这是 Skill 的核心入口文件，定义了技能的基本信息、触发条件和执行流程。文件头部的元信息（name、description、allowed-tools）决定了何时激活该 Skill；Instructions 部分则定义了从输入确认到原型输出的完整步骤。

流程拆分为"确认输入与格式 → 加载配置 → 分析结构 → 生成代码"四个步骤，让用户在每个关键节点都有确认的机会，避免一次性生成后大幅返工。其中第一步新增了**输出格式选择**，用户可以选择：

* **React**：生成 `.jsx` artifact，在 对话界面右侧直接渲染，可实时交互预览
* **HTML**：生成独立 `.html` 文件，可在浏览器中打开查看

两种格式的生成逻辑在 Step 4 中分支处理，各有对应的技术规范和常用模块写法参考。格式选择是必问项，不可省略。

**component_reference.md - 组件参考文档**

这个文件定义了模块识别规则和控件类型映射表。模块识别规则告诉 AI 如何从需求描述中识别出筛选区、列表区、表单区等常见模块；控件类型映射表建立了字段类型与控件的对应关系（例如"状态：下拉单选"对应 `<select>`）。

该文件对 React 和 HTML 两种输出格式均适用——控件的语义和映射关系是通用的，AI 会根据用户选择的格式将其转换为对应写法（React JSX 或原生 HTML）。组件规范相对稳定，独立维护的好处是：团队规范有更新时只需修改这一个文件，即可全局生效。

**style_config.md - 风格配置文件**

这是用户可自定义的配置文件，定义原型的视觉风格，包括主色调、圆角大小、组件库选择等。该文件同样对两种输出格式通用——React 模式下颜色配置会转换为 Tailwind 工具类或内联 style，HTML 模式下则转换为 CSS 变量或内联样式。

团队可将约定好的 UI 规范写入配置文件，所有成员生成的原型都会遵循同一套风格。不同项目可以维护不同的配置文件，同一个 Skill 即可适配多种风格需求。

**examples.md - 使用示例文档**

这个文件提供了典型场景的输入输出示例，覆盖列表页、树形结构、带业界参考等常见页面类型。更新后的示例**同时包含 React 和 HTML 两种格式**的完整对话流程，其中 React 示例（订单管理列表页）提供了包含筛选区、表格、详情抽屉的完整可运行 JSX 代码，作为 AI 输出的格式参考标准。

每个示例都展示了格式选择的对话节点，帮助 AI 理解在何处询问、如何根据用户选择分支处理。团队可将自己项目中的优秀原型案例补充进来，持续优化输出效果。

### 3.3.4 交互确认
原型初稿生成阶段输出了一个静态的页面骨架，但"骨架"只是视觉呈现，用户点击按钮会发生什么、状态如何流转、异常情况如何处理，这些交互逻辑都还没有定义。

传统模式下，交互逻辑往往散落在脑子里或口头沟通中，RD开发时经常遇到"这个按钮点了跳哪里"、等问题，反复确认导致效率低下。更麻烦的是，有些交互细节在评审时没人提，上线后才发现遗漏。


#### 3.3.4.1 阶段目标
通过Prompt模板引导，系统化梳理原型中的所有交互逻辑，希望：

* **交互完整**：覆盖几乎所有按钮、链接、可点击元素的交互行为
* **状态清晰**：明确不同状态下的显示规则和联动逻辑
* **异常覆盖**：定义异常场景的处理方式和提示文案
* **一次梳理**：减少后续开发过程中的反复确认

#### 3.3.4.4 多轮调优技巧

**技巧1：深化特定区域交互**

**使用场景：** 某个区域的交互逻辑比较复杂，需要更详细的梳理

**特征平台实践：** 新建Baseline弹窗涉及三种特征关联方式的Tab切换，每种方式的交互逻辑不同（列表多选、场景多选、文件上传），初次梳理可能只覆盖了主流程，Tab切换时的数据保留、切换确认等细节容易遗漏。让AI深化这个区域的交互，能把这些细节补齐。

**Prompt示例：**

```
请深化"新建Baseline弹窗"的交互逻辑：

1. 三种特征关联方式Tab切换时，已选数据是否保留？
2. 切换Tab时是否需要二次确认？
3. 每种方式的搜索、选择、清空交互细节
4. 文件上传的进度展示、失败重试、格式校验
```
**技巧2：补充状态组合**

**使用场景：** 发现有遗漏的状态组合情况

**特征平台实践：** 基线有发布状态、实验状态，版本有应用中/未应用/历史版本状态，这些状态的组合情况很多。初次梳理可能只覆盖了常见组合，一些边界组合（如"已发布+实验中+历史版本"）容易遗漏。让AI补充状态组合，能确保所有情况都有定义。

**Prompt示例：**

```
请补充以下状态组合的交互规则：

1. 发布状态=已发布 且 实验中=是 时，编辑按钮如何处理？
2. 版本状态=历史版本 时，哪些操作可用？
3. 基线下没有任何版本时，"创建子版本"按钮如何显示？
4. 所有样本都未定版时，"应用版本"按钮如何处理？
```
**技巧3：细化异常场景**

**使用场景：** 需要更完整的异常处理定义

**特征平台实践：** 初次梳理的异常场景通常是"网络异常"、"校验失败"等通用场景，但特征平台有一些业务特有的异常情况，比如"特征簇被删除后基线如何处理"、"上传的特征ID文件中有无效ID"等。让AI细化异常场景，能覆盖这些业务特有的情况。

**Prompt示例：**

```
请补充以下异常场景的处理方式：

1. 上传的特征ID文件中包含无效ID，如何提示用户？
2. 选择的特征簇在保存前被其他用户删除，如何处理？
3. 并发编辑：两个用户同时编辑同一基线，后保存的如何提示？
4. 创建子版本时，父版本被其他用户取消发布，如何处理？
```
**技巧4：生成交互流程图**

**使用场景：** 复杂交互需要可视化展示，便于评审和沟通

**特征平台实践：** "创建子版本"功能涉及多个判断节点（父版本是否已发布、是否选择继承样本、继承哪些样本的定版状态），用文字描述不够直观。让AI生成交互流程图，能清晰展示完整流程和分支逻辑，便于和业务方确认。

**Prompt示例：**

```
请为"创建子版本"功能生成交互流程图：

1. 从点击按钮到创建成功的完整流程
2. 标注每个步骤的判断条件和分支
3. 标注异常情况的处理节点
4. 使用Mermaid格式输出
```
**技巧5：确认交互优先级**

**使用场景：** 交互点较多，需要明确哪些是MVP必须实现的

**特征平台实践：** 交互梳理可能输出了20+个交互点，但排期紧张时不可能全部实现。让AI区分交互优先级，明确哪些是核心流程必须的、哪些是体验优化可以后做的，便于对齐排期。

**Prompt示例：**

```
请对已梳理的交互逻辑进行优先级划分：

1. P0-核心交互：主流程必须，缺失会导致功能不可用
2. P1-重要交互：常见场景需要，影响用户体验
3. P2-优化交互：锦上添花，可以二期实现

请说明划分理由。
```
**调优技巧速查表**

|场景|使用技巧|关键词|
|-|-|-|
|某区域交互需细化|深化特定区域|"深化XX弹窗/区域的交互逻辑"|
|状态组合有遗漏|补充状态组合|"补充以下状态组合的交互规则"|
|异常处理不完整|细化异常场景|"补充以下异常场景的处理方式"|
|复杂交互需可视化|生成交互流程图|"为XX功能生成交互流程图"|
|需要区分优先级|确认交互优先级|"对交互逻辑进行优先级划分"|

#### 3.3.4.5 效果评估
|评估维度|结果|
|-|-|
|交互覆盖度|覆盖筛选区、列表区、弹窗三大区域的主要交互点|
|状态联动|明确了发布状态、实验状态、版本状态对按钮显示/隐藏/禁用的影响规则|
|弹窗交互|新建/编辑弹窗的表单校验、Tab切换、文件上传等交互逻辑完整|
|异常处理|识别出网络异常、数据校验失败、名称重复、文件格式错误等8个异常场景|
|待确认项|主动提出5个需要与业务方确认的细节问题|

1. **从静态到动态**：原型从"只能看"变成"有交互定义"，每个按钮点击后的响应都有明确描述
2. **状态规则清晰**：不同状态组合下的按钮显示规则一目了然，开发时无需反复确认
3. **异常有兜底**：常见异常场景都有对应的处理方式和提示文案，避免上线后才发现遗漏

**待后续步骤完善的内容：**

交互确认让原型"动起来"了，但还有一些内容需要在后续步骤中完善：

|待完善项|当前状态|完善步骤|
|-|-|-|
|字段定义|交互已确认，但字段类型、长度、校验规则未明确|→ 字段确认|
|示例数据|仅3条基础数据，边界场景（空状态、超长文本、特殊字符）未覆盖|→ 假数据设计|
|业务规则|状态联动已定义，但详细业务规则（如名称唯一性校验时机）待补充|→ 规则限制|

交互确认阶段的职责是"让原型有交互定义"，而非"输出完整PRD"。通过分步骤的设计，每个阶段聚焦特定任务，既保证了单步输出质量，又为用户提供了逐步确认和调整的机会。
