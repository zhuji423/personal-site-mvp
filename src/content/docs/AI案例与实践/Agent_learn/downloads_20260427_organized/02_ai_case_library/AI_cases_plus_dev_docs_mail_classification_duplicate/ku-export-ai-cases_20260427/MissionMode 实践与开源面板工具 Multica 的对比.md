## 执行摘要
两个工具，两种方法，两种结果。当我们用同一个重构项目（BGW-Proxy Python→Go）对比测试 MissionMode 与 Multica 时，得到的数据出人意料：

|维度|MissionMode|Multica|
|-|-|-|
|任务完成率|11/11 = 100% |13/50 = 26% |
|总耗时|607 min|1079 min |
|测试覆盖率|82.2% |未统计|
|Token 消耗|~500k（估算）|8,045.4k（精确）|
|崩溃/阻塞时间|极少|271 min（25%）|
|设计文档|强制 doc.md|缺失（根因）|



**最反直觉的发现**：Multica 消耗了 MissionMode **13.8 倍**的 Token，却只完成了 **26%** 的任务。这不是工具差距，是**方法论差距**。

**核心结论**：设计文档（doc.md）前置，是 AI Coding 成功率的决定性因素，不是加分项，是零号先决条件。

## 1. 为什么 AI Coding 需要工程方法论？
### 1.1 两个工具，两种方法论假设
过去 6 个月，AI Coding 工具从"代码补全"演进到"自主执行"，但一个核心问题始终未被解决：

> **当 AI Agent 开始"自主"执行任务时，谁来保证它在做正确的事？**
两种工具代表了两种不同的回答：

**MissionMode：**用规范约束 Agent，让它沿着正确轨道跑

* 强制 doc.md → tasks.md → 实现 → 审批 → 循环
* 上下文边界明确，任务粒度可控

**Multica：**用调度器协调 Agent，让 Agent 团队自组织

* 看板式 Issue 管理，Agent 认领并发执行
* 并发是优势，但前提条件被严重低估了



### 1.2 AI 加速了什么，也放大了什么
```
传统开发 vs AI 开发的失败模式对比

传统开发:
  设计失误 → 实现浪费 → 发现时已返工 3 天
  浪费比: 1:3

AI 开发（有设计文档）:
  设计 47% 时间 → 实现几乎零浪费 → MissionMode 100% 完成率
  浪费比: 1:0

AI 开发（无设计文档）:
  跳过设计 → AI 自行推断接口 → 42% 任务取消 + 25% 时间崩溃
  浪费比: 1:8（Multica 实测）

结论: AI 加速了执行速度，也等比例放大了方向错误的代价
     "AI 越快，错误越贵"
```
**国际化输入法团队实践数据**（参考文档）：通过引入 AI 全流程，迭代周期从 9 天缩短到 5 天，缩短 44%——但这一成果的前提，是严格执行了设计前置和角色并行协作规范。

## 3. 深度解析：设计优先原则
### 3.1 Multica 的 42% 取消率——真正的根因
Multica 实验共涉及 50 个 Issue，结果令人震惊：

```
Multica 50 个 Issue 最终结果分布

  Done        ████░░░░░░░░░░░░░░  13 个（26%）
  Cancelled   ████████░░░░░░░░░░  21 个（42%）←——根因在这里
  In-progress ███░░░░░░░░░░░░░░░   8 个（16%）
  Blocked     ██░░░░░░░░░░░░░░░░   5 个（10%）
  其他        ░░░░░░░░░░░░░░░░░░   3 个（ 6%）
```
**21 个 Cancelled 任务的直接原因**：

> 第一批 21 个 Issue 在未准备设计文档的情况下被创建并分配给 Agent。Agent 在缺少共享接口定义的情况下开始并行执行，每个 Agent 各自推断接口定义，导致接口不兼容；当某个上游任务失败时，所有依赖该任务的下游任务进入死锁状态，最终被批量取消。
**关键发现**：这 21 个任务的取消，不是因为 AI 能力不足，而是因为**人类跳过了设计阶段**。

```
Multica 失败的因果链

跳过设计文档
    │
    ▼
Agent 各自推断接口（并行）
    │
    ├─► Agent A: 假设 BaseConn.Write([]byte) error
    ├─► Agent B: 假设 BaseConn.Send(Packet) bool
    └─► Agent C: 假设 BaseConn.Transmit(ctx, data) (n, error)
    │
    ▼
接口不兼容 → 集成层无法组装
    │
    ▼
上游任务失败 → 依赖链断裂
    │
    ▼
21 个任务批量取消（42% 取消率）+ 8 个任务卡死（16%）
    │
    ▼
为修复重新规划 → 新增任务 → 总 Token 翻倍（8045.4k）
```

阶段时间分配 ROI 分析：

  设计阶段   287 min (47.3%) → 为后续所有阶段提供"单一真相来源"
  实现阶段   130 min (21.4%) → 0% 返工（接口预定义，消除歧义）
  测试阶段   150 min (24.7%) → 82.2% 覆盖率（超出 80% 目标）
  部署阶段    40 min  (6.6%) → 完整归档

  设计的 ROI = 节省的浪费 / 设计投入
             = 参考 Multica：901 min 返工 / 287 min 设计
             ≈ 3.1x 回报

### 3.3 有/无设计文档的 Agent 行为差异
```
┌─────────────────────────────┬──────────────────────┬──────────────────────┐
│ Agent 行为维度               │ 有设计文档            │ 无设计文档            │
├─────────────────────────────┼──────────────────────┼──────────────────────┤
│ 接口理解                     │ 精确（来自 doc.md）   │ 推断（高错误率）       │
│ 依赖感知                     │ 完整（依赖图明确）    │ 盲目（运行时发现）      │
│ 完成标准                     │ 明确（验收标准定义）  │ 模糊（Agent 自行决定） │
│ Token 利用率                 │ 高（专注实现）        │ 低（大量用于推断）      │
│ 跨 Agent 接口一致性           │ 强（共享 doc.md）     │ 弱（各自定义不兼容）    │
│ 任务完成概率                  │ ~100%                │ ~26%                  │
│ 人工介入频率                  │ 低（阶段性审批）      │ 高（频繁卡点解锁）      │
└─────────────────────────────┴──────────────────────┴──────────────────────┘

核心认知：

  设计文档对人类工程师: "有了更好"
  设计文档对 AI Agent: "没有就失败"
  
  AI Agent 没有跨会话记忆，无法从代码库全貌推断意图。
  设计文档是 Agent 的"外部大脑"——
  没有它，Agent 只能猜测；有了它，Agent 才能执行。
```

## 5. 踩坑实录
### 坑 #1：跳过设计文档，直接启动多 Agent
```

问题现象:
  Multica 第一批 21 个 Issue 创建后，Agent 开始并行执行。
  执行 ~2 小时后，接连出现接口不兼容、依赖链断裂，
  21 个任务被批量取消，42% 的工作成果归零。

根本原因:
  多 Agent 并行时，每个 Agent 独立推断接口定义，
  互相不知道对方的假设，导致接口不一致。
  这不是 AI 能力问题，是信息架构问题：
  没有"单一真相来源"，Agent 无法保持接口一致性。

解决方案:
  停止所有 Agent 执行 → 补写 doc.md → 重新规划依赖图
  → 按依赖拓扑序重新分配任务 → 重启执行

预防措施:
  工程化强制 G1 卡点：doc.md 无 APPROVED 标记，
  任何 Agent 任务不允许创建/启动。
  在 CI 流水线中执行 doc.md 完整性检查脚本。
  
数据: 21/50 任务取消，浪费约 ~2200k Token（估算）
```


### 坑 #2：多 Agent 依赖链管理失控
```
严重程度: ████████░░  8/10   阶段级阻塞

问题现象:
  基础设施层（Task B）延迟交付后，8 个依赖它的业务任务
  全部进入 in_progress 并卡死。Multica 的任务调度器
  持续重试，无法识别"上游未就绪"与"上游失败"的区别。
  最终人工介入花费 ~120 min 逐一解锁。

根本原因:
  依赖声明存在于 Issue 元数据中，但调度器的依赖检查
  粒度不够细——它只检查"上游 Issue 已关闭"，
  未区分"成功关闭"和"取消关闭"，导致错误的依赖状态传播。

解决方案:
  手动检查所有 in_progress 任务的上游状态，
  将依赖被取消任务的下游任务重新标记为 blocked，
  补充上游任务后再批量解锁。

预防措施:
  依赖图可视化审查（在 tasks.md 中用 ASCII 图显式标注）。
  调度器添加"上游状态校验"规则：
  上游 Cancelled → 下游自动 Blocked（而非 in_progress）。
  
数据: 8 个任务卡死，人工介入 ~120 min，消耗额外 ~600k Token
```


### 坑 #3：AI 产物分散，集成成本超出预期
```
严重程度: ██████░░░░  6/10   集成阶段高摩擦

问题现象:
  3 个 Agent 分别实现了 HTTP/HTTPS/CONNECT 三种协议的解析器。
  最终集成时发现：
  · 错误类型命名不一致（ErrConn / ConnError / ConnectionError）
  · 日志格式各异（3 种不同的结构化日志方案）
  · 中间件接口签名有轻微差异
  集成工作量远超预期，耗时 ~3 倍于单 Agent 实现的集成成本。

根本原因:
  doc.md 虽然定义了接口，但未定义"实现规范"：
  错误类型命名规范、日志格式规范、中间件约定
  这些"隐性标准"被不同 Agent 各自实现。

解决方案:
  补充 doc.md 的"工程规范"章节，明确：
  错误类型命名规则、日志格式（JSON + 固定字段）、
  中间件接口签名模板。
  
预防措施:
  doc.md 模板标准化，增加"工程规范"必填章节。
  集成验证应作为 G3 卡点的额外检查项。
  
数据: 集成额外耗时 ~45 min，需 3 次 diff+修复循环
```


### 坑 #4：上下文窗口满溢，Agent "失忆"
```
严重程度: ██████░░░░  6/10   静默失败，难以察觉

问题现象:
  某个大任务执行到后半段，Agent 开始"忘记"
  前半段定义的接口约束，重新定义了不一致的类型。
  问题直到集成测试才被发现，此时已完成了大量错误实现。

根本原因:
  单任务 Token 超出上下文窗口，触发自动会话压缩。
  会话压缩会"摘要化"早期对话，丢失精确的接口定义细节。
  Claude Code 每次启动有 5 类固定开销
  （token计算/会话摘要/健康检查/topic提取/bash命令提取），
  大任务中这些开销被多次触发，进一步压缩有效上下文。

解决方案:
  发现不一致后，停止任务 → 读取 doc.md 重新初始化上下文
  → 在任务描述中显式粘贴关键接口定义
  → 重新执行后半段

预防措施:
  大任务（>3个模块）必须拆分为多个小任务。
  每个任务完成时，把关键接口实现写入文件（而非仅停留在对话中）。
  任务描述模板增加"上下文锚定"章节：
  在每个任务开头显式声明"本任务使用的接口定义来自 doc.md §X.X"。
  
数据: 静默失败 ~2h，集成发现后额外修复 ~40 min
```
