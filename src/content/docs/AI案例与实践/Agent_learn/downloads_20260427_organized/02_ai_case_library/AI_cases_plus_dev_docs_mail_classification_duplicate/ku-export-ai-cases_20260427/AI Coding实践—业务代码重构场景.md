# 一、背景介绍
## 1.1 业务背景
搜索主干模块历经十几年迭代，存在以下**问题**：

* 规模庞大：代码量巨大（**100W行**以上）、类 / 文件 / 数据结构关系复杂（**数千个**），全年超过**1500次**提交，活跃开发者超过**100人**。
* 逻辑复杂：涵盖通搜、视频、百科、文库、学术等十多条业务线逻辑，策略、架构、产品逻辑耦合，深度交织，模块开发成本高
* 文档缺失：代码库注释稀少，文档缺失 / 陈旧，导致开发上手慢，协作效率低，值周提供咨询人力消耗大
* 研发模式：垂类检索（视频、图片、商品、热议）已经完成图化改造，但由于通搜业务的体量更大、复杂度更高，传统重构路径资源消耗过大，周期不可控

同时，随着搜索个性化、AI搜、多模态融合业务对通搜架构提出了更高的**要求**：

* 速度：毫秒级的响应延迟
* 弹性：灵活的扩展能力
* 稳定性：更高的服务可用性

因此，搜索百万图化项目应运而生。我们希望能够对通搜业务完成全图化改造，代码行数从百万行精简到五十万行以下，利用图框架的特点赋予架构更高的灵活度和稳定性，同时支持更高的计算效率。

---

那么，如何**更快、更好**的完成这项任务？

我们发现，从2024年开始，AI编程工具迎来了全球爆发性增长，从代码生成、问题调试、项目构建，AI正在升级成为开发者的关键协作角色。

因此，我们将AI Coding作为一项重要技术引入我们的业务重构场景，作为突破编码效率困境的关键路径。

---

在实际引入前，我们分别调研了业界工具、厂内工具：

* 业界工具：业界已有DeepWiki、Devin等基于代码理解的产品案例，但由于闭源、成本、安全性等问题；开源复刻方案功能有限，难以解决复杂的业务问题。
* 厂内工具：Comate、Zulu、Baidu CC等工具在2024年尚未成熟，模型能力不足。

基于上述问题，现有工具并不能很好的适配我们的业务场景，我们需要自主可控、本地化、业务适配的代码理解重构方案。

# 三、让重构『飞起来』
## 3.1 单任务prompt
[流程图]
传统重构流程是由开发人员以人工的方式逐步完成编码任务的。我们从最初引入AI Coding能力，到实际应用，经历了两次技术迭代。

* 第一次迭代（朴素prompt方式）
    * 方式：通过穷举转换重构场景、反复修改规则，期望大模型能覆盖所有的业务场景
    * 问题：1）总有遗漏规则；2）需要反复review prompt，本身需要投入成本

* 第二次迭代（启发式prompt方式）
    * 方式：将人工迁移改写前后的对比文件发送给模型，让模型自行总结改写规则，再结合业务定义的少量新增规则，共同完成prompt
    * 问题：受限于2024年GPT-4o的模型能力，效果不佳（规则覆盖率不足65%）


随着2025年年初，DeepSeek发布，在公开数据集上的各项能力显著优于gpt-4o。

|**对比维度**|**deepseek**|**gpt-4o**|
|-|-|-|
|**MBPP+（补全代码任务）**|**76.2%**|**73.5%**|
|**Aider（漏洞修复）**|**73.7%**|**29%**|
|**RepoBench（跨文件仓库补全）**|**表现优于 CodeLlama、StarCoder**|**未公开对比**|

在我们的业务场景下，规则提取覆盖率从65%提升到92%，并且能部分识别代码间隐藏的、语义上的联系，使得我们的启发式prompt方案得以工程化落地，验证此方案可行性。

然而，在我们重构大型文件时，遇到了新的问题：将 **提取规则 + 待重构代码** 作为**单个prompt**发送给模型时，会发生 **超token** 的问题。

因此，我们引入了新的解决方案：**多任务prompt**。

## 3.2 多任务prompt
为了解决超token的问题，我们将原始的大型任务分解为多个子任务，每个子任务构造独立的prompt进行处理。

[流程图]
在业务重构场景，大型任务即处理行数超过4000行的大型代码文件，任务分解需要对文件进行合理的拆分处理。

任务分解：

* 脚本处理部分：1）将大型文件的 .h 文件和 .cpp 文件分开处理；2）基于静态语法分析，分别提取 .h 文件和 .cpp 文件的类/结构声明以及成员函数；
* LLM子任务：将提取后的函数逐个发送给LLM进行处理
* 全部处理结束后，再通过脚本拼接处理完成后的各个函数

通过任务分解，我们解决了大型任务超token的问题。

但是，我们发现基于多任务prompt重构后的代码仍有不少问题，具体如下：

* **代码质量问题**（存在编译报错、风格混乱）；
* **无法批处理**，重构效率没有质的变化；
* **模型幻觉问题**，如生成代码里乱入了『极客时间』

![](/personal-site-mvp/img/doc-placeholder.svg "")
此外，我们在重构后的编译、检查、LLM交互部分仍需投入人力，人工介入的次数并没有达到预期『**无人值守**』的状态：

![](/personal-site-mvp/img/doc-placeholder.svg "")
## 3.3 Coding Agent
针对上述问题，我们开发了一套自研的Coding Agent框架。Agent工作流大致分为三个部分：

1. 规则提取：1）用户执行脚本，扫描待重构的源文件列表；2）输入源文件，通过Agent拆分类和数据结构的声明、定义；3）进行语法分析，提取完整的 函数/作用域 代码块；
2. 代码改写：1）改写prompt + 逐函数发送给LLM进行改写处理；2）单文件完成后，进行后处理，生成完整代码；
3. 编译反思：1）Agent对生成的完整文件进行编译，如果编译报错，则提取报错信息，发送给模型进行反思改写（矫正幻觉）；2）达到通过状态，或者重试超过最大次数后终止任务
4. 输出文件

[流程图]
在Agent的辅助下，用户重构目标代码只需『一键调用』：

```
# 用户执行脚本
python batch.py

# ---- 输出结果：重构后的文件列表
```


Agent上线后，我们在试点的业务场景下显著提升了重构的效率：

**效率提升**：从『3策略/人/天 』提升到『Agent 8h完成70+策略』

**人工编码量**：< 5%（仅需少量调试）

**编译通过率**：> 85%

**流程沉淀**：探索出AI Coding重构范式，从框架设计到推全上线全流程打通

# 四、让模块『会说话』
除了在重构场景下借助 AI 的生成能力提高研发效率，我们还希望 AI 能更懂业务，能帮我们回答日常值周常见的问题，减轻值周同学的人力负担。

## 4.1 前期方案：知识图谱
前期，我们期望构建一份**业务知识图谱 / 代码图谱**，能将业务内复杂的数据结构之间的关系可视化地描述，调研了以下三个工具：

* CodeDB：厂内工具，应用在业务库后发现由于代码库太庞大，生成的调用链不完整（无法捕获动态信息），部分关系有缺失情况
* CodeQL：开源工具，使用过程中存在内存溢出问题，应用困难；
* Clang工具链：数据量过大，需要大量定制逻辑，且导入图数据库性能过低；

[流程图]
**核心挑战**

**1、链路缺失**：无法捕获动态行为（运行时多态、外部库调用），无法呈现完整调用链，实用性不足

**2、性能瓶颈**：函数调用关系数据量过大，导入知识图谱耗时过长（超过一周）
