## 二、项目全貌
我需要批量采集豆包、通义千问、文心一言等多个平台的对话数据。一个人做，代码全靠 AI 写。

整个采集链路是这样的：
接收采集请求 → 存数据库（方便异常恢复）→ 连接云手机 → 打开 App 开始采集
→ 采集数据 → 拉回我们需要的结果 → 发送到 Kafka

看起来链路不长，但涉及的技术栈跨度很大：后端服务、数据库、云手机管理、SSH 隧道、Android 系统操作、SQL 查询（FastAPI / MySQL / Kafka / uiautomator2 / adb）。最终项目代码 58 个文件、18000+ 行，每一环都是我的盲区。

## 四、我的方法论：设计驱动，AI 执行
代码全靠 AI 写，但不是直接让 AI 写代码。

我的流程是这样的：
想清楚要做什么
↓
写技术设计文档（模块、接口、数据结构、异常处理）
↓
把设计文档喂给 AI，让它按设计生成代码
↓
跑起来，发现问题
↓
回头改技术设计，再让 AI 重新生成
↓
循环

这个循环最关键的一步是第一步——**想清楚**。AI 生成代码的质量，完全取决于你的设计质量。设计模糊，代码就乱；设计清晰，代码基本能直接用。

以状态管理为例，我在技术设计文档里把每种状态的写入时机、是否终态、说明都列清楚：

|状态|写入时机|终态？|说明|
|-|-|-|-|
|`pending`|批次启动，所有题目落库时批量写入|否|等待采集线程处理|
|`running`|采集线程取到题目，正式开始前|否|进程崩溃时会永久停留，需孤儿恢复|
|`completed`|采集成功，答案已推送 Kafka|**是**|正常终态|
|`pending_retry`|设备不可用，或进程崩溃后孤儿恢复|否|探测线程自动恢复后补采|
|`failed`|自动重试耗尽、探测超时|**是**|可通过接口人工触发重试|

把这份表格连同整个设计文档一起喂给 AI，它生成的状态机代码基本不需要改。**设计越细，AI 越准。**

**AI 负责实现，我负责判断。** 知道要做什么、做到什么程度、哪里有问题——这些是这个项目里真正花时间的地方。

## 五、系统真正的复杂度在哪里
### 5.1 多个平台，多套坑
表面上是"采集多个平台的对话数据"，但每个平台的底层实现完全不同，每个都要单独处理。

文心一言用自己的 WebView 渲染页面，UI 方案完全失效，试了各种办法都拿不到数据。走投无路问 AI 还有没有别的方式，才发现了一个完全不同方向的方案——引用提取成功率从 40% 升到 99%，速度从 4-5 分钟缩到 15 秒。

但新方案也不是开箱即用的。豆包换个账号数据来源就变了，要动态发现。千问的数据结构跟豆包不一样，要分别解析。每个平台都是单独的一套。

### 5.2 引用历史隔离
采集引用时有一个隐蔽的问题：如果当前问题没有触发联网搜索，直接取最新一条引用记录，拿到的可能是上一轮对话的历史引用。

解决方式是在问题发出前做一次数据快照，问题发出后只取快照之后的新数据。这样无论历史数据怎么累积，当前问题只会拿到属于自己的引用。

不做这个，数据看起来正常，但实际上是错的。这种问题跑一段时间才会暴露，排查起来很难定位。

### 5.3 状态管理
采集过程中随时可能出问题：设备断联、登录过期、界面卡住。每个问题×平台的组合都要维护独立的状态——五种状态，每种有对应的处理路径。任何一个状态没处理好，要么数据丢失，要么重复采集，要么系统卡死。

边界情况是最麻烦的。进程崩溃后，数据库里会留下"孤儿记录"——状态停在 running 但实际上没人处理。服务重启后要自动识别这些孤儿、把它们拉回补采队列。

更细的地方在于补采顺序。重启后队列要跟原始提交顺序一致，为此专门设计了 `question_order` 字段持久化顺序。但还有一个兜底：这个字段引入之前落库的历史记录 `question_order` 全为 0，这时用 `id ASC` 次级排序自动补位——因为批次落库时 INSERT 串行执行，`id` 序号跟原始顺序天然一致。

这种细节不考虑不会报错，但数据会乱。

### 5.4 断联排查
系统跑了一段时间后，云手机开始频繁断联。排查了很久，AI 判断是云手机本身的问题，去找供应商，供应商不回复。

自己继续查，排查下来发现是数据传输量的问题，随着数据积累传输量越来越大，直接把连接撑断了。找到原因后改了传输方式，断联彻底消失。

### 5.5 云手机连接与隧道管理
连接云手机不是插根线这么简单。服务商文档不完整，没有现成的代码方案，从 API 列表到打通隧道摸索了整整一天。

连上之后问题才真正开始。云手机会不明原因断联，断联不报错，采集线程直接卡死。所以每一步操作都要有超时控制——数据提取超时、dump 界面超时、等待回复超时，任何一个环节卡住都要能主动退出，而不是傻等。

断联之后不是直接放弃，而是多维度逐级升级恢复。连接失败时，系统会按以下顺序逐级尝试：

|层级|恢复方式|说明|
|-|-|-|
|1|SSH 隧道重建 + ADB 重连|常规重试 3 次，处理临时网络抖动|
|2|云 API 重启 adbd 守护进程|手机端 ADB 服务挂了，远程重启后再连|
|3|设备重启|云 API 重启优先，失败降级为 ADB 命令重启|
|4|重启后重连|等待设备启动，再尝试 3 次完整连接|

采集过程中断联的处理也一样——先尝试立即重连（走同样的逐级升级），成功就继续采集当前问题。如果立即重连也失败，才交给后台探测线程，探测线程还会再尝试最多 2 轮完整的设备恢复。只有所有层级全部失败，才需要人工介入。

### 5.6 并发设计
多个平台同时跑，但同一台设备不能被并发操作，多个 batch 任务同时进来也要排队。登录过期的时候，当前平台的 worker 要阻塞等待，但不能影响另一个平台继续采集。

这些并发边界全部要靠代码显式控制。

### 5.7 防风控
全程模拟真人操作：点击加随机偏移、输入分段进行模拟打字节奏、操作之间随机停顿、问题之间随机休息、每隔 N 个问题来一次长休息。

### 5.8 登录检测
判断 App 有没有登录，听起来简单，实际上要叠四层，每层准确率不同：

|方法|准确率|说明|
|-|-|-|
|UI 特征检测|85%|检查界面关键词|
|Activity 检测|80%|检查当前页面是否登录页|
|引导文案检测|75%|输入框不存在时检查欢迎文案|
|数据库检测|95%+|直接读 App 本地数据库确认登录态|

还有一个容易踩的坑：要区分"App 在桌面"和"App 在登录页"。两种状态 UI 上都没有聊天界面，但处理方式完全不同——前者要拉起 App，后者要等待登录。识别错了，采集线程要么卡死要么误判。

## 六、三次转折
### 6.1 快放弃了，随口一问救了整个方案
UI 方案在豆包和千问上能跑起来，但引用 URL 的提取成功率只有 40% 左右，很多拿不到。更麻烦的是文心一言——它用自己的 WebView 渲染页面，UI 方案完全失效，试了各种办法都不行。

那个时候整个方案都在摇摇欲坠。我几乎觉得文心这个平台要放弃了。

走投无路，我随口问了一句：**"还有什么其他方式能采集到数据？"**

AI 给出了一个完全不同方向的方案，它从没主动提过。

方案改了之后，三个平台引用提取成功率全部接近 100%，速度提升了十几倍。

但 AI 只在文心的场景下给了这个方案，没有说豆包和千问也能用。**是我自己判断这个方案更好，主动把三个平台全部切换过去。** 这个推广的决策，AI 不会替你做。

**AI 不会反思自己之前给的方案。** 发现更好的方案之后，回头推广这件事，只能是你来做。

### 6.2 不信 AI 的判断，自己继续排查
方案切换之后，采集跑得很顺利。但随着数据积累，云手机开始频繁断联——基本每分钟都在断。

AI 的第一个判断是：线上没问题说明代码没问题，应该是云手机本身的问题。我信了，去找云手机供应商，但供应商直接不回复了。

等不来答案，我没有就此放弃。把被 AI 判定为"有问题"的云手机放到线上环境——结果也不断联了。说明云手机没问题，**AI 判断错了，我自己把方向拉回来。**

不停地打日志、读日志，一项一项排除。最终定位到是数据传输量的问题。找到原因后，我自己先想了解决方向，反问 AI 可不可行，答案是可以。改完之后断联问题彻底解决。

**你比 AI 更了解你自己的系统。** AI 会判断错，定方向是你的事。

### 6.3 坚持自动化，不接受将就的方案
云手机服务商提供了一个现成方案——手动执行一条连接命令就能连上云手机。但每隔 24 小时会自动断联，每天都得有人手动去跑一遍这条命令。

**这个方案我直接否掉了。** 采集系统必须自动运行，人工介入不是工程解法。

但服务商的文档不完整，没有现成的代码方案。而我不懂云手机，不懂隧道，也不懂安卓——三个领域全是盲区。

AI 没法直接读官方文档，也给不出现成答案。但它告诉我：去找什么范围的接口、用什么关键字搜。

我拿着这些线索，去官方的 API 列表里一点点翻、一点点试。这个过程花了大概一整天。每找到一个接口、每推进一小步，AI 都会确认方向对不对、下一步该看哪里。最终两个人一起把隧道方案摸索出来了。

**知道什么方案不能接受，和知道什么方案可行一样重要。**

## 七、AI 会骗人，而且骗得很有说服力
用 AI 写代码一个月，最深的体会不是"AI 多强"，而是**AI 会反复给出错误答案，并且每次都能自圆其说**。

### 7.1 不了解自己的系统，就会被 AI 牵着走
代码是 AI 写的，但你不能因此就不了解代码。恰恰相反——**你必须清楚系统每一步是怎么做的**，否则 AI 说什么你就只能信什么。

举个例子。接入新平台 DeepSeek 时，采集拿不到数据。AI 的判断是：DeepSeek 没有做本地持久化存储，这条路走不通。

但我之前明确探测过，DeepSeek 是有持久化存储的。我把这个事实告诉 AI，它没有纠正自己，而是换了一个角度继续劝退——说即使有存储，也无法读取，给了一堆看似合理的技术解释：设备端缺少必要工具、兜底方案也被禁用、这条路两头都断了。

听起来很专业，每一条都有根据。但实际上**全是错的**——缺工具可以推送上去，兜底方案可以启用，根本不是死路。如果我不了解系统的实现细节，就会在这里放弃。

更离谱的是，它还会对已有方案做出错误总结。比如它说豆包和千问的某个提取路径是主方案，但实际上那只是兜底。AI 对着自己写的代码，给出了错误的结论。

### 7.2 项目越到后期，AI 越吃力
这一个月下来有一个明显的感受：**项目前期 AI 又快又准，后期反而越来越吃力。**

前期系统简单，上下文少，AI 生成的代码基本能直接用。但随着代码量增长到 18000 行、58 个文件，AI 开始频繁出现这些问题：

* **记不住之前的设计决策**，同一个问题反复讨论，给出互相矛盾的方案
* **对已有代码做出错误判断**，把兜底方案当成主方案，把已实现的功能说成不存在
* **改一个地方破坏另一个地方**，因为它无法同时理解所有模块的关联
* **遇到复杂问题倾向于绕路**，给一个"看起来能用"的方案，而不是解决根本问题

到后期，我花在"纠正 AI"上的时间，有时比花在"让 AI 写代码"上的还多。

### 7.3 应对方式
1. **必须了解自己的系统**。代码可以不手写，但实现方案必须清楚。AI 说"这条路不通"的时候，你要能判断它说的对不对。
2. **不要把 AI 的话当结论**。把它当成一个能力很强但经常记错的同事——它给的信息需要你自己验证。
3. **维护好技术设计文档**。项目越大，AI 的上下文越容易丢失。设计文档是你和 AI 之间的"共享记忆"，每次对话前先把相关文档喂给它，能大幅减少它胡说的概率。
4. **警惕"看起来合理"的解释**。AI 最危险的不是给错答案，而是给错答案的同时附上一套逻辑自洽的解释。越是听起来有道理，越要自己验证。
