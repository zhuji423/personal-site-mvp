#### 四、详细评估标准
##### 1. 功能效果评估 (Functional Effectiveness)
##### 1.1 任务完成率 (Task Completion Rate) - 权重30%
**1）评估标准：**

•优秀 (90-100分)：成功完成率≥95%，能够准确理解并完成各类复杂任务

•良好 (80-89分)：成功完成率85-94%，大部分任务能够正确完成

•合格 (70-79分)：成功完成率75-84%，基本任务完成良好

•待改进 (60-69分)：成功完成率65-74%，存在明显的任务完成问题

•不合格 (<60分)：成功完成率<65%，任务完成能力严重不足

**2）评估方法：**

      任务完成率 = (成功完成的任务数 / 总任务数) × 100%

**3）评估要点：**

•统计不同类型任务的完成情况

•分析失败案例的原因和模式

•评估复杂任务和简单任务的完成差异

•考虑任务完成的质量和效率

##### 1.2 响应准确性 (Response Accuracy) - 权重30%
1）评估标准：

•优秀 (90-100分)：回答内容准确率≥95%，事实错误极少

•良好 (80-89分)：回答内容准确率85-94%，偶有小错误

•合格 (70-79分)：回答内容准确率75-84%，准确性基本可接受

•待改进 (60-69分)：回答内容准确率65-74%，存在较多错误

•不合格 (<60分)：回答内容准确率<65%，错误率过高

2）评估方法：

•事实准确性检查：核实关键事实、数据、概念的正确性

•专业知识验证：评估专业领域知识的准确程度

•逻辑推理正确性：检查推理过程和结论的合理性

•引用来源可靠性：验证引用信息的权威性和时效性

##### 1.3 信息完整性 (Information Completeness) - 权重25%
**1）评估标准：**

•优秀 (90-100分)：回答信息全面完整，覆盖用户需求的各个方面

•良好 (80-89分)：回答信息较为完整，基本满足用户需求

•合格 (70-79分)：回答信息基本完整，有少量遗漏

•待改进 (60-69分)：回答信息不够完整，存在明显遗漏

•不合格 (<60分)：回答信息严重不完整，无法满足基本需求

**2）评估要点：**

•关键信息覆盖度：是否包含用户问题的核心要素

•信息深度评估：回答是否具有足够的深度和细节

•相关信息补充：是否主动提供有价值的相关信息

•结构化程度：信息组织是否清晰有序

##### 1.4 逻辑一致性 (Logical Consistency) - 权重15%
**1）评估标准：**

•优秀 (90-100分)：逻辑严密，前后一致，推理清晰

•良好 (80-89分)：逻辑基本一致，偶有小的逻辑跳跃

•合格 (70-79分)：逻辑大体一致，有少量不一致之处

•待改进 (60-69分)：存在明显的逻辑不一致问题

•不合格 (<60分)：逻辑混乱，前后矛盾严重

**2）评估要点：**

•前后逻辑连贯性：检查回答内部的逻辑一致性

•多轮对话一致性：评估多轮交互中的逻辑连贯性

•推理逻辑正确性：验证推理步骤的合理性

•立场观点一致性：确保表达的观点前后一致

##### 2. 用户体验评估 (User Experience)
##### 2.1 响应速度 (Response Speed) - 权重30%
**1）评估标准：**

•优秀 (90-100分)：平均响应时间≤2秒，95%分位数≤3秒

•良好 (80-89分)：平均响应时间2-4秒，95%分位数3-6秒

•合格 (70-79分)：平均响应时间4-6秒，95%分位数6-10秒

•待改进 (60-69分)：平均响应时间6-10秒，95%分位数10-15秒

•不合格 (<60分)：平均响应时间>10秒，95%分位数>15秒

**2）评估方法：**响应速度得分 = max(0, 100 - (平均响应时间 - 1) × 20)

##### 2.2 交互友好性 (Interaction Friendliness) - 权重25%
**评估标准：**

•对话自然度：语言表达是否自然流畅

•理解用户意图准确性：是否能准确理解用户真实需求

•主动澄清能力：遇到模糊问题时是否主动澄清

•情感表达适宜性：情感表达是否恰当得体

##### 2.3 语言适宜性 (Language Appropriateness) - 权重25%
**评估标准：**

•目标用户群体适配度：语言风格是否符合目标用户特征

•语言风格一致性：整体语言风格是否保持一致

•专业术语使用恰当性：专业术语使用是否准确适度

•年龄适宜性：语言内容是否适合目标年龄群体

##### 2.4 易用性 (Usability) - 权重20%
**评估标准：**

•学习成本：用户掌握使用方法的难易程度

•操作便捷性：交互操作是否简单便捷

•功能发现性：用户是否容易发现和使用各项功能

•错误恢复能力：用户操作错误后的恢复便利性

##### 3. 系统稳定性评估 (System Reliability)
##### 3.1 可用性 (Availability) - 权重40%
**评估标准：**

•优秀 (90-100分)：系统正常运行时间≥99.9%

•良好 (80-89分)：系统正常运行时间99.0-99.8%

•合格 (70-79分)：系统正常运行时间98.0-98.9%

##### 3.2 错误处理 (Error Handling) - 权重25%

## 二：智能体评价规则演变
随着智能体业务的发展，智能体的评价标准和方式也经历着不断的更迭。智能体将如何为搜索及开发者服务，是一个重要而持续的课题。下面主要简单介绍下AgentBuilder对智能体的几个价值评判阶段，希望作为“抛砖引玉”，收获一些想法和建议。

### 阶段一：创意至上
智能体创建门槛低，“一句话”即可。多数开发者较少主动编辑配置、上传知识库、自研插件，官方插件有限。

智能体效果更多体现为模型自身能力，体验差异小，趋同明显。

![平台现有500+“算命先生”和160+“李白”，部分甚至抄袭](/personal-site-mvp/img/doc-placeholder.svg "平台现有500+“算命先生”和160+“李白”，部分甚至抄袭")
早期智能体评估主要关注基础体验，如名称头像统一，无违规抄袭，对话响应稳定，不偏离人设等。

![某大赛评审规则](/personal-site-mvp/img/doc-placeholder.svg "某大赛评审规则")
![早期评判标准是对比eb4](/personal-site-mvp/img/doc-placeholder.svg "早期评判标准是对比eb4")
在此基础上对“好”的判断，一种是关注其对话效果是否优于eb4。

另一种则是看重“创意”，例如早期参赛获奖智能体曾涌现出一批如“合成种地吧”、“00后疯感工牌”等娱乐、工具向作品。

几种创意判断依据：

* 交互方式（拟人化对话/游戏化互动，如海龟汤）
* 内容呈现形式（markdown）
* 功能服务（对话外的工具/服务属性，如生成口播、工牌）
* 独特视角（如毒舌李清照）

![00后疯感工牌，通过自研插件&工作流结合网络热梗设计出工牌图片](/personal-site-mvp/img/doc-placeholder.svg "00后疯感工牌，通过自研插件&工作流结合网络热梗设计出工牌图片")
![赛事主题突出“创意”](/personal-site-mvp/img/doc-placeholder.svg "赛事主题突出“创意”")
但以上种种评价方式依赖人工构造query，主观交叉评估，拟合分数，缺少统一标准，效率低。

“ai百科”、“旅游助手”等知识问答或攻略类智能体通常较难评出优劣，差异主要体现在语气是否“个性化”，有无markdown格式输出。

### 阶段二：内容满足
随智能体流量场景逐渐丰富完善（尤其是占比最高的q2c），“搜索内容供给”成为重要评价因素，内容质量（尤其是首轮qu得分）成为评估关注重点。

## 1. 自动评估方法与范式
### 1.1 结果导向评估（Outcome-based Evaluation）
* **定义**：只关注Agent是否完成了最终目标。
* **适用场景**：有明确终止条件和目标的任务，如问答、网页操作、代码修复等。
* **优点**：实现简单，评测标准客观。
* **局限**：无法反映Agent决策链条的合理性、效率和中间过程中的潜在风险。
* **代表性论文/工具**：
    * [AgentBench](https://arxiv.org/abs/2308.03688)
    * [TESTAGENT](https://arxiv.org/abs/2410.11507)
    * [MiniWob](https://github.com/Microsoft/MiniWoB)
    * [SWE-bench](https://arxiv.org/abs/2310.06770)
    * [GAIA](https://arxiv.org/abs/2312.06681)
    * [Tau-Bench](https://arxiv.org/abs/2403.05530)


### 1.2 轨迹级评估（Agent Trajectory Evaluation）
* **定义**：关注Agent在任务执行过程中的每一步动作、工具调用、状态转移和决策链条，进行细粒度分析。
* **适用场景**：需要分析推理过程、工具选择、异常行为、效率等的复杂任务。
* **评估手段**：
    * **规则判分（Rule-based Judge）**：
        * **定义**：基于预设规则、模板或自动脚本对每一步进行判分。
        * **优点**：客观、可控，适合标准化流程和可自动化的任务。
        * **局限**：灵活性和泛化性有限，难以覆盖复杂或开放性场景。
        * **代表性论文/工具**：
            * [Autonomous Evaluation and Refinement of Digital Agents](https://arxiv.org/abs/2404.06474)
            * [AgentRewardBench](https://arxiv.org/abs/2504.08942)（[HuggingFace数据集](https://huggingface.co/datasets/McGill-NLP/agent-reward-bench)）
            * LangChain Trajectory Evaluator


    * **LLM判分（LLM-as-a-Judge）**：
        * **定义**：利用大语言模型（如GPT-4、Mixtral等）对Agent的行为轨迹进行自动化主观判分。
        * **优点**：高效、可扩展，能结合思维链提示提升解释性，适合复杂推理、对话、代码等主观性较强的任务。
        * **局限**：一致性和客观性依赖于LLM本身能力，存在主观性。
        * **代表性论文/工具**：
            * [Agent-as-a-Judge](https://arxiv.org/abs/2312.06683)
            * [AgentRewardBench](https://arxiv.org/abs/2504.08942)
            * [Autonomous Evaluation and Refinement of Digital Agents](https://arxiv.org/abs/2404.06474)
            * AgentBench




### 1.3 对抗性/安全性自动评估
* **定义**：通过仿真多样化工具和对抗性场景，自动发现Agent在真实世界中的潜在安全风险和故障点。
* **代表性论文/工具**：
    * [ToolEmu](https://arxiv.org/abs/2403.04132)


### 1.4 端到端与模块化评估器
* **端到端**：如GPT-4V等多模态大模型直接对轨迹进行整体判分。
* **模块化**：先用VLM生成每步描述，再用LLM推理判分，兼顾可解释性与灵活性。
* **代表性论文/工具**：
    * [Autonomous Evaluation and Refinement of Digital Agents](https://arxiv.org/abs/2404.06474)

## 二、Agent的业务规则要怎么设计（才能难住模型）？
继续榨干tau-bench！

tau-bench有两个场景：零售和航空。零售场景的业务规则偏通用，没有特殊的行业内部规则，主要靠user的需求来考察agent能力；但航空场景非常不同，**它有很多通用世界所不了解的“私有规则”，所以我们可以通过学习它的设计思路，来指导偏b端智能客服类评测场景的system prompt，从而可以设计出贴合实际、且足够有难度的样本！**

以下这7条设计思路，从各个角度考察agent能力，非常值得借鉴。

## 1. 引言
传统评测往往只关注 Agent 是否能"完成"任务，而 `tau-bench` 的设计理念则更进一步，致力于评估 Agent 在模拟真实世界复杂约束下的**推理能力、规划能力、风险意识和程序遵循能力**。本文档将这些隐性设计提炼为可复用的设计模式，供其他场景的设计者参考。

## 2. 参考范例：航空预订场景业务规则 (Wiki)
以下是 `tau-bench` 中航空场景的完整业务规则，是后续所有设计点分析的"事实基础"。

```
# Airline Agent Policy

The current time is 2024-05-15 15:00:00 EST.

As an airline agent, you can help users book, modify, or cancel flight reservations.

- Before taking any actions that update the booking database (booking, modifying flights, editing baggage, upgrading cabin class, or updating passenger information), you must list the action details and obtain explicit user confirmation (yes) to proceed.

- You should not provide any information, knowledge, or procedures not provided by the user or available tools, or give subjective recommendations or comments.

- You should only make one tool call at a time, and if you make a tool call, you should not respond to the user simultaneously. If you respond to the user, you should not make a tool call at the same time.

- You should deny user requests that are against this policy.

- You should transfer the user to a human agent if and only if the request cannot be handled within the scope of your actions.

## Domain Basic

- Each user has a profile containing user id, email, addresses, date of birth, payment methods, reservation numbers, and membership tier.

- Each reservation has an reservation id, user id, trip type (one way, round trip), flights, passengers, payment methods, created time, baggages, and travel insurance information.

- Each flight has a flight number, an origin, destination, scheduled departure and arrival time (local time), and for each date:
  - If the status is "available", the flight has not taken off, available seats and prices are listed.
  - If the status is "delayed" or "on time", the flight has not taken off, cannot be booked.
  - If the status is "flying", the flight has taken off but not landed, cannot be booked.

## Book flight

- The agent must first obtain the user id, then ask for the trip type, origin, destination.

- Passengers: Each reservation can have at most five passengers. The agent needs to collect the first name, last name, and date of birth for each passenger. All passengers must fly the same flights in the same cabin.

- Payment: each reservation can use at most one travel certificate, at most one credit card, and at most three gift cards. The remaining amount of a travel certificate is not refundable. All payment methods must already be in user profile for safety reasons.

- Checked bag allowance: If the booking user is a regular member, 0 free checked bag for each basic economy passenger, 1 free checked bag for each economy passenger, and 2 free checked bags for each business passenger. If the booking user is a silver member, 1 free checked bag for each basic economy passenger, 2 free checked bag for each economy passenger, and 3 free checked bags for each business passenger. If the booking user is a gold member, 2 free checked bag for each basic economy passenger, 3 free checked bag for each economy passenger, and 3 free checked bags for each business passenger. Each extra baggage is 50 dollars.

- Travel insurance: the agent should ask if the user wants to buy the travel insurance, which is 30 dollars per passenger and enables full refund if the user needs to cancel the flight given health or weather reasons.

## Modify flight

- The agent must first obtain the user id and the reservation id.

- Change flights: Basic economy flights cannot be modified. Other reservations can be modified without changing the origin, destination, and trip type. Some flight segments can be kept, but their prices will not be updated based on the current price. The API does not check these for the agent, so the agent must make sure the rules apply before calling the API!

- Change cabin: all reservations, including basic economy, can change cabin without changing the flights. Cabin class must be the same across all the flights in the same reservation; changing cabin for just one flight segment is not possible.

- Change baggage and insurance: The user can add but not remove checked bags. The user cannot add insurance after initial booking.

- Change passengers: The user can modify passengers but cannot modify the number of passengers. This is something that even a human agent cannot assist with.

- Payment: If the flights are changed, the user needs to provide one gift card or credit card for payment or refund method. The agent should ask for the payment or refund method instead.

## Cancel flight

- The agent must first obtain the user id, the reservation id, and the reason for cancellation (change of plan, airline cancelled flight, or other reasons)

- All reservations can be cancelled within 24 hours of booking, or if the airline cancelled the flight. Otherwise, basic economy or economy flights can be cancelled only if travel insurance is bought and the condition is met, and business flights can always be cancelled. The rules are strict regardless of the membership status. The API does not check these for the agent, so the agent must make sure the rules apply before calling the API!

- The agent can only cancel the whole trip that is not flown. If any of the segments are already used, the agent cannot help and transfer is needed.

- The refund will go to original payment methods in 5 to 7 business days.

## Refund

- If the user is silver/gold member or has travel insurance or flies business, and complains about cancelled flights in a reservation, the agent can offer a certificate as a gesture after confirming the facts, with the amount being $100 times the number of passengers.

- If the user is silver/gold member or has travel insurance or flies business, and complains about delayed flights in a reservation and wants to change or cancel the reservation, the agent can offer a certificate as a gesture after confirming the facts and changing or cancelling the reservation, with the amount being $50 times the number of passengers.

- Do not proactively offer these unless the user complains about the situation and explicitly asks for some compensation. Do not compensate if the user is regular member and has no travel insurance and flies (basic) economy.
```
## 3. 高价值设计点汇总
|设计点|核心挑战|航空场景示例|
|-|-|-|
|**动态应用规则 (Dynamic Rule Application)**|基于查询到的状态，从多个选项中选择正确的规则|根据会员等级+舱位，计算免费行李额度|
|**复杂约束满足 (Complex Constraint Satisfaction)**|在单个操作中满足多个限制条件|支付时组合使用证书、信用卡、礼品卡的数量限制|
|**Agent 端责任制 (Agent-Side Responsibility)**|事前规划与自我纠错，验证自身行为的合法性|在调用 API 前，自己先判断基础经济舱能否修改|
|**上下文敏感决策 (Context-Sensitive Decision)**|根据上下文的细微差异，选择完全不同的行动分支|根据是"延误"还是"取消"的抱怨，决定不同的补偿金额|
|**复杂布尔逻辑 (Complex Boolean Logic)**|组合多个独立信息，进行逻辑运算以做出决策|判断`(24小时内 或 航司取消 或 有保险)`来决定能否退票|
|**整体与局部约束 (Holistic vs. Local Constraints)**|理解规则是作用于整体还是局部|升舱必须针对预订中的所有航班，而不能只升一段|
|**能力边界识别与拒绝 (Boundary Recognition & Refusal)**|知道能力的极限，并能合理解释地拒绝|明确拒绝"增加/减少乘客数量"的请求|

## 4. 设计点详解与示例
### 4.1 动态应用规则 (Dynamic Rule Application)
* **核心挑战**: Agent 不能依赖静态的、一成不变的规则，必须先通过工具获取一个或多个"状态变量"，然后根据这些变量的值，从规则手册中动态选择并应用正确的条款。这考验 Agent 将信息获取和规则执行联系起来的能力。
* **清晰示例**: **计算免费行李额度。**
    * **规则**: `Checked bag allowance: If the booking user is a regular member, 0 free checked bag for each basic economy passenger... If the booking user is a silver member, 1 free checked bag...`
    * **执行分析**: 免费行李额不是一个固定的数字。要正确回答"我能带几个免费行李？"，Agent 必须：


        1. 先调用 `get_user_details` 获取用户的 `membership_tier` (状态变量1)。
        2. 再调用 `get_reservation_details` 获取订单中乘客的 `cabin_class` (状态变量2)。
        3. 最后在脑中或通过计算工具，根据这两个变量在复杂的规则矩阵中定位到唯一的正确答案（比如：Silver 会员 + Economy 舱位 = 2个免费行李）。

### 4.2 复杂约束满足 (Complex Constraint Satisfaction)
* **核心挑战**: Agent 在执行单个操作（特别是调用工具）时，需要同时满足多个看似无关的限制条件。这要求 Agent 在生成工具调用参数时，有非常强的精确性和全面的信息整合能力。
* **清晰示例**: **组合支付。**
    * **规则**: `Payment: each reservation can use at most one travel certificate, at most one credit card, and at most three gift cards.`
    * **执行分析**: 当用户说"我有一张旅行证书，两张礼品卡，剩下的用信用卡支付"时，Agent 在最终调用 `book_reservation` 工具时，其 `payment_methods` 参数必须是一个严格遵守上述数量限制的列表。如果它错误地构造了包含两张信用卡的支付列表，即使总金额正确，也违反了约束。


### 4.3 Agent 端责任制 (Agent-Side Responsibility)
* **核心挑战**: 考验 Agent 的"事前规划"和"自我审查"能力。规则明确指出某些校验工作后端 API 不会做，责任完全在 Agent。Agent 必须在行动前，先用已有的知识和规则来验证自己计划的下一步是否"合法"，而不是盲目尝试，依赖外部系统的报错来纠正自己。
* **清晰示例**: **修改一个未知舱位的航班。**
    * **规则**: `Change flights: Basic economy flights cannot be modified... The API does not check these for the agent, so the agent must make sure the rules apply before calling the API!`
    * **执行分析**: 这是一个非常典型的、考验 Agent 责任心的场景。
        * **用户的请求**: "你好，请帮我修改一下我的航班，订单号是 #12345。" (注意：用户未提供关键的"舱位"信息)
        * **一个失败的 Agent** 会直接尝试调用 `update_reservation_flights` 工具，因为它盲目地假设航班可以修改。这将导致任务失败，因为最终的系统状态与标准答案不符。
        * **一个优秀的 Agent** 的正确行为路径是：



            1. 它首先意识到"修改航班"这个动作有一个**前置检查条件**：必须确认舱位不是"基础经济舱"。
            2. 它检查当前已知信息，发现"舱位"是**未知的**。
            3. 为了履行"我必须自己检查"的责任，它**主动规划并执行一个信息补全步骤**：调用 `get_reservation_details(order_id="#12345")`。
            4. 从工具返回结果中，它得知舱位是 `basic_economy`。
            5. 此时，它才拥有了决策所需的所有信息，于是它应用规则，回复用户："抱歉，我查到您的订单是基础经济舱，根据规定，这类机票无法修改。"

    * 这个过程清晰地展示了 Agent 如何在信息不完备时，主动承担起校验责任，通过规划额外的步骤来确保自己的行为是合法且正确的。

### 4.4 上下文敏感决策 (Context-Sensitive Decision)
* **核心挑战**: Agent 需要识别出用户请求中细微但关键的语义差异，并根据这些差异选择完全不同的行动分支和参数。这考验 Agent 对自然语言深层意图的理解能力。
* **清晰示例**: **根据抱怨类型决定补偿金额。**
    * **规则**: `...complains about cancelled flights...amount being $100 times the number of passengers. ...complains about delayed flights...amount being $50 times the number of passengers.`
    * **执行分析**: 两个场景都包含"抱怨"和"补偿"的意图，但触发的后果完全不同。
        * 用户说："我的航班被**取消**了，你们得给我个说法！" -> Agent 必须计算 `$100 * N` 并调用 `send_certificate`。
        * 用户说："我的航班**晚点**了，害我错过了会议，太糟糕了！" -> Agent 必须计算 `$50 * N` 并调用 `send_certificate`。

    * 如果 Agent 混淆了这两个关键词，导致补偿金额错误，评测就会失败。


### 4.5 复杂布尔逻辑 (Complex Boolean Logic)
* **核心挑战**: Agent 需要在一个决策点上，综合考虑多个独立的、通过不同方式获取的信息，并对它们进行逻辑运算（与、或、非），才能得出最终结论。这纯粹考验其逻辑推理能力。
* **清晰示例**: **判断能否免费取消航班。**
    * **规则**: `All reservations can be cancelled within 24 hours of booking, or if the airline cancelled the flight. Otherwise, basic economy or economy flights can be cancelled only if travel insurance is bought...`
    * **执行分析**: 当用户要求"取消航班"时，Agent 需要像程序员写 `if` 语句一样进行判断：


```
IF ( (currentTime - bookingTime < 24h) OR (flightStatus == 'cancelled') )
  THEN can_cancel = true
ELSE IF ( (cabinClass == 'basic' OR cabinClass == 'economy') AND (hasInsurance == true) )
  THEN can_cancel = true
ELSE IF ( cabinClass == 'business' )
  THEN can_cancel = true
ELSE
  can_cancel = false
```
    * 这要求 Agent 能够主动规划并获取所有判断所需的信息（预定时间、航班状态、舱位、保险情况），然后执行正确的逻辑运算。

### 4.6 整体与局部约束 (Holistic vs. Local Constraints)
* **核心挑战**: Agent 需要理解一个规则是应用于一个更大的实体（如整个"预订"），还是其内部的某个部分（如单个"航班"）。这考验 Agent 是否有"全局观"，能否在正确的层级上应用规则。
* **清晰示例**: **升舱。**
    * **规则**: `Cabin class must be the same across all the flights in the same reservation; changing cabin for just one flight segment is not possible.`
    * **执行分析**: 用户的请求通常是局部的，例如："我想把我从纽约到洛杉矶的**这段**升到商务舱。"（假设这是一个往返预订的一部分）。
    * Agent 必须认识到，即使请求是针对"局部"的，规则却是应用于"整体"的。它需要向用户解释："根据规定，升舱需要对您预订中的所有航班（包括返程）一同操作，不能只升单程。您希望继续吗？"


### 4.7 能力边界识别与拒绝 (Boundary Recognition & Refusal)
* **核心挑战**: Agent 必须准确识别出哪些请求超出了它的能力范围或违反了系统的"硬性规定"，并能够清晰、坚定且礼貌地拒绝，而不是尝试变通或产生幻觉。
* **清晰示例**: **增减乘客数量。**
    * **规则**: `Change passengers: The user can modify passengers but cannot modify the number of passengers. This is something that even a human agent cannot assist with.`
    * **执行分析**: 当用户提出"我能给我的订单加一个我的孩子吗？"的请求时，一个成功的 Agent 会：


        1. **识别意图**: 将请求分类为"改变乘客数量"。
        2. **匹配边界规则**: 命中"不能修改乘客数量"这条硬性规定。
        3. **优雅地拒绝**: 回复道："非常抱歉，根据航空公司的政策，我们无法在已创建的预订中增加或减少乘客数量。这需要您取消原预订后重新为您创建包含所有乘客的新预订。您希望我帮您看看重新预订的选项吗？"

    * 这样的回复既遵守了规则，又提供了建设性的下一步方案，是高质量 Agent 的表现。
