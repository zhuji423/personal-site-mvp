Coding Agent 再进化：云端并行交付——一次把 AI“内化进工作流”的实践

#### 🧑‍🏫 案例作者：[@吴玮琦](https://ku.baidu-int.com?t=mention&mt=contact&id=422c2e80-f2cb-11f0-80f0-91056ee5134c)
#### 🎬 案例分类：开发、全流程
#### 🔧 使用工具：Comate、Comate Stack
#### 📒 案例概要：我的日常开发里，真正折磨人的不是写业务逻辑，而是反复出现的“支线任务”。为此，我基于Comate Zulu，开发了一个Remote Agent 工具：Jinx Code。这个项目不仅能帮我并行处理任务，自动提交CR，显著提升研发效率，还是一次大胆的尝试：Agent 自举，用AI开发AI工具。仅仅用了1周，完成了项目上线，并且在开发过程中，总结了一些于AI Agent的5个最佳实践。
这不是一篇“AI 一键生成完美代码”的故事。更像一段很现实的心路历程：当我开始真正在项目里长期和 Agent 协作，我发现决定效率上限的，早就不是“模型够不够强”，而是**你有没有把协作方式、代码组织、可检索信息、可验证环境**这些基础设施搭好。

我最初的动机很简单：想写得更快、切换更少、并行更多。后来我发现，真正的升级不是“我写得更快”，而是“我把一部分工作从主线注意力里移走”——让 Coding Agent 在云端沙盒里并行跑起来，交付可审查的结果，而我把精力放在目标定义、验收与风险控制上。并且这次尝试很有意思，他是一个AI自举的项目：用AI工具开发AI工具。

## **Jinx Code 云端并行的可审查交付**
![](/personal-site-mvp/img/doc-placeholder.svg "")


🍀**快来尝试 -> **[https://web-agent-next.baidu-int.com/](https://web-agent-next.baidu-int.com/)



为了让“Agent 并行跑支线”变成一种低打断的日常动作，我把入口做得非常短：**只填两项**，然后把执行、验证、产出都放到云端沙盒里跑完。

**1）Repo Name：一句话指向项目，让远端把环境拉起来**

我只需要填一个仓库名，Jinx Code 就会在远端并行完成一串准备动作：拉代码、装依赖、建立可运行工作区。

这件事的关键不是“省几分钟”，而是**不占用我本机、不打断我主线心流**——我可以继续写当前任务，让 Agent 在云端把另一条任务线跑起来。

**2）Your Task：写愿望，而不是写 PRD**

Your Task 是派工的核心，我会把它写得更像“可验收工单”而不是长需求。典型格式是：

* 你要它做什么（改哪块、达成什么效果）
* 最好顺手带上你们内部的卡片/需求 ID（例如 ⁠CARD-1234 / ⁠FE-5678）

带 ID 的好处是 Jinx 不需要额外猜测icafe卡片，任务更准确。当然也可以不填写卡片内容，直接提交任务，Jinx会去自动关联相关卡片



**3）Try Your Luck：按下按钮后，交付物不是“建议”，而是一套现场**

点一次按钮之后，Agent 会在云端跑完整个链路，最后给我的不是“怎么写”，而是我能直接接手验收的结果集合：

* 一个**云端沙盒工作区**（VS Code + Terminal + Browser/DevTools）
* 一份可 review 的 **diff / CR（变更记录）**



我最常用的方法是：

**让它先跑到七八成**（实现 + 自检 + 产出变更），然后我进沙盒补最后几刀：边界条件、注释、以及那些“改完需求之后才会出现的神秘兼容逻辑”。

这就是我为什么说瓶颈不在“模型够不够强”，而在“你有没有把执行与验证的基础设施搭好”：当交付物默认是可审查、可回滚、可复盘的，Agent 才真正进入工作流，而不是停留在编辑器里给建议。

## 为什么做一个Remote Agent？一线开发的“并行焦虑”
我的日常开发里，真正折磨人的不是写业务逻辑，而是反复出现的“支线任务”：

* 一个小修复要拉起一整套工程验证
* 一个页面调整需要找很多分散的样式与组件用法
* 一个需求卡片夹带着隐性约束（埋点、灰度、兼容、权限、监控）
* 想“先试一把”，但试一把意味着开分支、装依赖、跑测试、处理本地残留

这些任务并不一定难，但会持续打断主线心流。久而久之，你会开始抗拒尝试，或者把事情堆着等整块时间——而整块时间在大多数团队里是一种稀缺资源。

所以我希望有一种工作方式：**我继续主线，Agent 并行去做支线；成功就收下，失败也留证据，不影响我当前状态。**

## 为什么“编辑器里的 AI”不够用
我用过很多 AI Coding 的形态：补全、解释、生成片段、基于上下文改文件。它们能让“写代码”更快，但很难让“交付”更快，因为真正的瓶颈往往不在编辑器里，而在完整的工程链路里，我需要的不是更聪明的“建议”，而是更完整的“执行与交付能力”，所以尝试了扩展整个链路：让 Agent 在隔离环境里并行完成安装/运行/测试/定位，把过程证据沉淀成可审查的产物（diff、log、报告），最后以一个 CR 的形式交付给我。

之所以要强调这一点，原因主要有三条：

* **我的本地 IDE 必须继续推进主线**：我不希望被依赖安装、构建、跑测试、起服务这些耗时环节阻塞；执行放到远端并行跑，才能把等待变成后台产出。
* **沙盒不是“多备份”那么简单**：备份只能兜底误改，但无法约束 Agent 的非安全预期行为（环境污染、越权读写、执行危险脚本等）。沙盒提供最小权限、可观测、可销毁、可复现的边界，更适合作为默认执行场。
* **我想要的是 CR-first 的工作流**：最终结果应该直接是一个可 review 的 CR，我来决定是否合入；不希望把时间花在繁琐的提交、搬运、重复验证与补证据上。

## 依托的新工具/平台：Comate Zulu + 远端沙盒
这个实践的抓手仍然是两类能力，但关键点在于：**以 Comate Zulu 的强 Agent 能力为核心编排层，底层执行直接复用 AI Tools 体系里既有、私有的远端基础设施**。我做的不是从零搭一套“云端 IDE / Runner / 环境管理”，而是把现成能力串成一条可交付的链路。

* **Comate Zulu 的 Agent 能力（核心）**：把“对话”升级为“多步行动”。Zulu 不只是生成建议，而是能在仓库上下文里自主拆解任务、连续迭代、自我纠错，并最终收敛到可交付的变更（diff/CR）。它负责把意图变成行动序列，并对结果负责。
* **远端沙盒（复用 **[One Tool](https://console.cloud.baidu-int.com/onetool)** 的私有基础设施）**：执行层不重复造轮子，直接借助既有的云端工作区能力，提供接近本地的工作环境（VS Code/Terminal/Browser/DevTools）。Agent 在云端完成依赖安装、脚本运行、服务拉起、验证与问题定位；必要时我再接管沙盒做人工补刀，把“最后一公里”成本压到最低。

两者结合，才真正落地我想要的关键词：**云端、并行、交付**——Zulu 负责“能把事情做成”，既有沙盒基础设施负责“能安全稳定地把事情跑起来并留下证据”，最终产出物以可审查的 CR/变更集交付，而不是一堆停留在编辑器里的建议。

## 我是怎么和 Agent 协作的：从“写需求”到“做验收”的重心迁移
我现在更像是在“派工”，而不是在“从零写实现”。典型协作节奏是：

* 我提供：目标、约束、验收标准、关联卡片/issue、风险点提醒
* Agent 负责：检索代码、定位入口、实现改动、跑验证、整理变更说明
* 我回收：review diff、补业务边界、做取舍、决定是否合并

这背后有一个很关键的认知变化：**我的工作中心从“需求实现”迁移到“Agent Harness（驯化与验收）”**。也就是：我不再把大量时间花在“亲自实现每个步骤”，而是把时间花在：

* 让 Agent 更容易做对（输入与知识暴露）
* 让 Agent 更容易自证正确（可测试、可检查）
* 让结果更容易被团队接纳（可 review、可回滚、可追溯）

要做到这一点，仅靠提示词不够，需要一些工程与流程上的最佳实践。

## 最佳实践（我踩坑后总结的 5 个关键点）
### 代码库尽量 All in One：把“上下文”变成可检索的
**做法**：尽量把相关代码放到同一个仓库/同一可访问的目录结构中（前端、后端、协议、脚本、Mock、文档、组件库……能聚合就聚合）。**原因**：Agent 最擅长的是在一个可见空间内做检索、比对、引用与跨文件修改。上下文越集中，它越不容易跑偏。

**体感收益**：

* 少了“找不到入口文件/不知道调用链”的来回试探
* 跨模块改动（比如埋点 + UI + API）更容易一次到位
* 代码 review 也更聚焦：变更集中、引用可追溯

> 这点有点反直觉：很多人以为模型越强越不需要上下文。我的经验是相反的——**上下文组织得越好，模型越像一个靠谱同事**。


### 三方库接口/文档尽量“明文暴露”：让 Agent 查得到、用得对
**做法**：能放在仓库里的文档就放进来（哪怕是摘录版），尤其是团队常用三方库的关键接口、约定、范式。像一些 UI/组件体系（例如 shadcn 这类），我的偏好是：**不要只依赖“外部包 + 记忆中的用法”**，而是把源码/组件模板拉下来，作为项目代码的一部分。

**原因**：Agent 的行为模式高度依赖检索证据。

* 文档只在外网/内部 wiki、或只有人脑记得 → Agent 只能猜
* 文档/源码在仓库里可搜索 → Agent 能引用、能对齐风格、能遵循约定

**体感收益**：

* UI 组件使用更一致，减少“看起来能跑但不符合规范”的返工
* 复杂组件改造时，Agent 能直接看源码做定向修改，而不是盲改调用



### 及时总结形成“Memory”：把专业名词与阶段性结论固化下来
**做法**：定期把项目里的专业名词、关键约束、历史决策、常见坑、前置结论整理成一个可检索的“记忆文件”或知识页（例如 `docs/memory.md`、`CONTRIBUTING.md`、`project-glossary.md`）。内容可以包括：

* 业务名词解释与字段含义
* 关键链路的入口与调用路径
* 之前任务做过什么、为什么这么做
* 常见失败原因与解决方案
* 验收口径（哪些算完成，哪些不算）

**原因**：Agent 很会“短期努力”，但很容易在跨任务协作中丢失上下文。你把结论固化下来，它就能复用，而不是每次从零推理。

**体感收益**：

* 同类需求越做越快（Agent 的“复利”出现了）
* 新成员/换人接手也更顺（人也能读这个 Memory）



### 4. 模型分工：让不同模型干自己擅长的活
**做法**：别指望一个模型从设计到排查到架构全都最强。我的实践分工大致是：

* **Gemini**：更擅长前端页面开发、图片/设计稿转代码、UI 生成与布局调整
* **Claude**：更擅长架构设计、复杂文件变更、跨模块重构、长上下文推演
* **Codex**：更适合 Bug 修复、深度问题排查、对现有代码进行精确修改与回归验证

**原因**：这不是“哪个更强”的问题，是“强项不同”。把任务按类型路由，整体速度和质量都会更稳定。



### 5. 给 Agent 可检查/可测试的环境：你描述结果，它负责自证
让项目具备全自动的自检能力。虽然写在最后，但我认为是未来Agent使用者最需要发力的方向，当 Agent 有能力自己跑验证，它才可能真正做到“交付”。：

* 有可运行的启动命令（dev/build）
* 有可执行的测试（单测/集成测试/最小回归脚本）
* 有 lint/format（让风格一致减少 review 摩擦）
* 有可观察性（日志、报错、关键指标输出）

总结就是

**认知升级点**：这就是我前面说的 **Agent Harness**——未来使用者的重心会越来越偏向“提供可验证的约束与环境”，而不是“亲自把每个步骤做完”。



## 效果与变化：提效、协作模式、组织认知的升级
### 个人层面：并行带来的体感提升
* 主线任务不再被打断：Agent 在云端跑支线
* “先试试”的成本明显下降：不需要为了一个想法把本地环境折腾一遍
* 失败不尴尬：失败是日志和可复盘的现场，不是你电脑里一堆残留状态

### 协作层面：交付物从“建议”变成“可审查结果”
* 讨论从“你帮我看看怎么写”变成“你 review 一下这份 diff”
* 任务推进更像流水线：派工 → 并行执行 → 自证 → review → 合并
* 对团队而言更可控：有 CR、有记录、有回滚点

### 组织层面：AI 时代的工作方式变化
* 资源分布迁移：从本地算力/本地环境迁移到云端沙盒
* 工程资产变得更重要：文档明文、脚本可跑、测试可执行、约定可检索
* 角色重心变化：更多人会变成“高质量约束与验收”的提供者（不止是工程师，PM 也可以参与）

## 可复用的方法论
如果只带走三句话，我会选这三句：

* **把“验证”做成默认能力**：先给 Agent 一个可运行、可测试、可自证的环境与链路（起服务、跑脚本、跑测试、留日志/报告）。验证一旦成为默认动作，既有自动化才能真正转化为智能化；人只需要做验收与决策。
* **把“上下文”显式化、可检索化**：把规则、约束、接口契约、目录规范、运行方式、验收标准等以明文沉淀在 Agent 可检索的位置（仓库内文档/注释/README/ADR/Playbook）。让 Agent “查得到、引用得上”，减少猜测与反复确认。
* **把“并发”当作工作方式**：将可拆分的任务（环境准备、修复、验证、回归、文档补齐）并行推进，用云端执行与可审查产物承接结果，最大化缩短端到端交付时间。

AI Native 软件的交互输入不像传统软件那样能被表单与流程完全枚举；可输入空间更开放、路径更多样。因此阶段性来看，能力上限确实更依赖使用者对 Agent 的理解与对约束/证据链的设计。但随着模型与工具链持续演进，许多“技巧”会逐渐内化为默认能力，用户的重心会更多回到：**定义目标、约束边界、制定验收标准，并对合入做最终决策**。
