REFACTOR SIMULATION: Replace legacy token system with OAuth2.0 + JWT (JWKS)

Summary and Assumptions

- Goal: Move from current heterogeneous token formats (QAMate-Token opaque per-module tokens; QAMate-U-Token / Kami-U-Token uuap JWT-like tokens; comateAuthToken generation via cookies) to a consolidated OAuth2 + JWT model.
- Chosen model (recommended): Central OAuth2 Authorization Server that issues signed JWTs (RS256) with JWKS discovery endpoint. Services obtain tokens via client_credentials; automated username/password flows use Resource Owner Password Credentials (ROPC) for internal test accounts. All services validate JWTs via JWKS. A compatibility adapter will accept legacy headers for a configurable transition period.
- Signed JWTs will include standard claims (iss, sub, aud, exp, iat) and custom claims (user, module_id, scopes).
- JWKS (JSON Web Key Set) configuration will be cached and refreshed automatically.

High-level approach (phased)

Phase 0 — Discovery & Docs (no code changes)
- Create developer manual and mapping of auth code points (done).
- Run a full grep/semantic search of auth headers and token utilities to enumerate all modification points.

Phase 1 — Add OAuth config & libraries
- Add Spring Security resource-server and OAuth2 client dependencies to pom.xml for core and apiExecutor.
- Add configuration properties (oauth.jwks-uri, oauth.issuer-uri, oauth.client-id, oauth.client-secret, oauth.token-uri, oauth.introspection-uri) to application-*.yml.
- Implement a new JwtVerifier service that wraps Nimbus JWKS and provides verify(token)=>claims.

Phase 2 — Compatibility adapter in RequestFilter (feature-flagged)
- Modify RequestFilter.doFilter to first attempt Authorization: Bearer <JWT> verification via JwtVerifier.
- If missing or invalid and compatibility.enabled=true, fallback to existing OpenApiToken / UuapToken logic.
- Map JWT claims to request attribute "qamate_user" and "QAMate-ModuleId" consistently.

Phase 3 — Feign Interceptor updates
- Replace all code that sets QAMate-Token header with Authorization: Bearer <access_token> (for internal service-to-service calls) using client_credentials flow.
- Implement a reusable OAuth2ClientCredentialsManager (cached token per client_id+scope) to avoid repeated token fetches.

Phase 4 — Service-by-service migration
- Convert a low-risk service to use new Authorization semantics (update Feign config and caller). Run integration tests.
- Migrate other services in groups; keep compatibility fallback on.

Phase 5 — Cleanup
- Disable fallback after canary success; remove legacy token acceptance and legacy token generation logic.
- Migrate any DB-stored opaque tokens to a dedicated metadata table or remove them when no longer needed.

Detailed file-by-file change list (precise)

NOTE: The following list is produced after initial scans and covers high-confidence modification points. A full exhaustive list will be generated by automated scanning (grep/semantic). The following entries include file paths and method names that must be modified or inspected.

Core (primary changes)

- core/src/main/java/com/baidu/qamate/core/components/config/RequestFilter.java
  - Methods to modify:
    - doFilter(ServletRequest, ServletResponse, FilterChain)
      - New: Attempt Authorization header parsing and verify via JwtVerifier.verifyToken
      - Keep: When compatibility.enabled=true and Authorization header absent/invalid, fallback to existing logic that checks QAMATE_UUAP_TOKEN, QAMATE_TOKEN, KAMI_TOKEN etc.\n      - Ensure qamate_user attribute is set from token claim "user" or legacy logic.
    - injectComateAuthToken(HttpServletRequest)
      - No change to intent; but consider replacing the comateAuth token acquisition to accept a service-level JWT instead of cookies where applicable.
  - Feature flags/config:
    - auth.compatibility.enabled (boolean)
    - oauth.jwks-uri
    - oauth.issuer

- core/src/main/java/com/baidu/qamate/core/components/config/UuapToken.java
  - Methods to modify:
    - checkFromToken(String token, HttpServletRequest request)
      - New: Use JwtVerifier.verify(token) which can validate standard JWTs using JWKS; map claims to qamate_user.

- core/src/main/java/com/baidu/qamate/core/components/common/JwtWrap.java
  - Replace or adapt to use Nimbus JOSE/JWT or Spring Security's JwtDecoder backed by JWKS URL rather than symmetric secret. Methods:
    - getToken(Map params)
    - verifyToken(String token)
  - Note: current JwtWrap uses uuap JwtUtils that depends on a secret. This will be extended to support JWKS-based RS256 validation or left as legacy for compatibility if needed.

- core/src/main/java/com/baidu/qamate/core/components/config/OpenApiToken.java
  - Methods to modify:
    - checkFromToken(String qamateToken, String qamateModuleId, HttpServletRequest request)
      - Strategy: For transition, if token equals legacy module token or special super tokens, accept. Otherwise, if incoming is a Bearer JWT, verify via JwtVerifier and map claims to module ownership. Consider removing token equality checks after migration.

- core/src/main/java/com/baidu/qamate/core/apismartmgt/manager/FeignConfig.java
  - Methods to modify:
    - authInterceptor() lambda
      - For workerClient requests: instead of calling getWorkerToken() which returns an opaque token, inject Authorization: Bearer <client_credentials_token>
    - getWorkerToken()
      - Implement new OAuth client_credentials flow (use RestTemplate/WebClient or Spring OAuth client) to call oauth.token-uri with client_id & client_secret; cache token with expiry.
  - Introduce new helper class OAuthTokenManager with thread-safe caching.

- core/src/main/java/com/baidu/qamate/core/apismartmgt/manager/client/WorkerClient.java
  - Endpoint mapping remains the same. However, ensure getToken() usage is replaced where used by FeignConfig; getToken static stub may be kept for legacy uses.

- core/src/main/java/com/baidu/qamate/core/v2/lumosgmt/common/feign/* and core/v2/kamixmgt/manager/feign/ForwardClientConfig.java
  - Specifically: ForwardClientConfig.java (QAMATE_TOKEN_NAME constant) and KamiServerClientConfig.java that set QAMate-Token header. Replace these header injections to Authorization: Bearer <token> when calling internal services.

- core/src/main/java/com/baidu/qamate/core/v2/kamixmgt/service/impl/KamiUserTokenService.java
  - Ensure persistence logic for comate/ugate tokens is compatible with new JWT claims. The service can remain, but be mindful of claim mapping.

Executor (apiExecutor) changes

- apiExecutor/executor-server/src/main/java/com/baidu/qamate/server/common/conf/feign/QAMateCoreClientConfig.java
  - Replace requestTemplate.header("QAMate-Token", "...") with Authorization: Bearer <token>. Implement a small local OAuthTokenManager that obtains client_credentials token for executor service.

- apiExecutor/executor-server/src/main/java/com/baidu/qamate/server/common/conf/feign/QAMateDeviceClientConfig.java

- apiExecutor/executor-server/src/main/java/com/baidu/qamate/server/service/impl/AuthServiceImpl.java

Rollback & compatibility

- A single boolean feature flag auth.compatibility.enabled controls whether RequestFilter will accept legacy headers when Authorization header is missing/invalid. Set to true during rollout; then set false to stop legacy acceptance and remove code later.
- Keep tests for legacy tokens around until final removal.

Potential chain reactions and pitfalls

- Any code relying on qamate_user or module id being set from OpenApiToken must be validated to ensure that the new JWT claims use the same attribute names.
- External integrations that expect QAMate-Token header will break if the header is removed — provide translation proxy or keep compatibility.
- WorkerClient.getToken usage must be carefully replaced; if the worker login endpoint still returns opaque tokens expected by worker service, ensure the worker accepts Authorization: Bearer tokens.
- Storage of secrets: client_secret must be stored securely and not checked into VCS.
