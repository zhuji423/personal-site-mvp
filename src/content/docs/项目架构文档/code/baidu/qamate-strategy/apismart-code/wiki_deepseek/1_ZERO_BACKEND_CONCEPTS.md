# 零基础后端概念说明

> **写给谁看**: 完全没有任何后端开发经验的小白。你可能连"服务器"、"API"、"数据库"这些词都只是听过但不理解具体含义。
> **怎么读**: 从第 1 节开始顺序阅读，像爬楼梯一样一步步来。每个概念先用生活类比让你"秒懂"，再给出它在技术世界中的真实含义。
> **读完能得到什么**: 理解 QAMate 系统的三份文档中出现的所有核心概念，不再被"后端黑话"吓到。

---

## 1. 最基础的基础——计算机之间怎么"说话"？

### 1.1 什么是"后端"？

**生活类比**: 你去餐厅吃饭，**前端**是菜单+服务员——你看到的东西、你交互的东西。**后端**是厨房——你看不到的地方，厨师在切菜、炒菜、洗碗。没有厨房，菜单就是一张废纸。

**技术解释**:
- **前端** = 你在浏览器里看到的页面、按钮、输入框（比如百度首页的搜索框）
- **后端** = 服务器上的程序，接收前端发来的请求，处理业务逻辑（比如搜索关键词），读写数据库，再把结果返回给前端
- **QAMate 的后端** = 这个代码仓库里的所有 Java 程序，它们负责管理 API 测试用例、执行测试、返回测试结果

---

### 1.2 什么是"服务器"？

**生活类比**: 一台 24 小时不关机的电脑，放在专门的机房里，一直开着网，随时等人来访问。

**技术解释**:
- 你的个人电脑可能晚上会关机、会休眠。但**服务器**不会——它一年 365 天、一天 24 小时都在运行
- 服务器可能是一台物理电脑，也可能是"云服务器"（在别人的机房里的虚拟电脑，比如阿里云、腾讯云）
- **QAMate 的服务器**：这个项目的代码会被部署到百度内部的服务器上，持续运行，供公司内部的人使用

---

### 1.3 什么是 HTTP？

> HTTP = HyperText Transfer Protocol（超文本传输协议）

**生活类比**: 两个人写信交流——信纸的**格式**是固定的：抬头写"亲爱的XX"，结尾写"此致敬礼"。HTTP 就是互联网上计算机之间通信的"信纸格式"。

**技术解释**:
- HTTP 定义了请求（request）和响应（response）的格式
- **请求**包含：方法（GET=获取、POST=创建、PUT=修改、DELETE=删除）+ 地址（URL）+ 数据（body）
- **响应**包含：状态码（200=成功、404=找不到、500=服务器出错了）+ 数据
- 你在浏览器地址栏输入网址按回车，浏览器就发了一个 HTTP GET 请求

---

### 1.4 什么是 URL？

> URL = Uniform Resource Locator（统一资源定位符）

**生活类比**: 一个人的家庭地址——"北京市海淀区XX路XX号" 完整地告诉了你"这个人住在哪儿"。URL 就是互联网上的地址。

**技术解释**:
```
https://qamate.baidu.com:8542/core/api/plan/list
|______|  |_______________| |__| |_______________|
  协议         域名         端口      路径
```
- **协议**: `https` — 通信规则（可以理解为"寄信方式"，https 是加密的）
- **域名**: `qamate.baidu.com` — 服务器的名字（像"百度大厦"这个名称）
- **端口**: `8542` — 服务器上的具体"门牌号"（一台服务器可以有多个服务，通过端口区分）
- **路径**: `/core/api/plan/list` — 具体要找的资源

---

### 1.5 什么是"端口"？

**生活类比**: 一栋大楼（服务器）有很多门（端口）。**门 8542 号**进去是 Core 管理后台，**门 8995 号**进去是 apiExecutor 执行引擎。不同门通向不同房间。

**技术解释**:
- 端口是一个 0-65535 之间的数字
- 一台服务器上可以运行多个程序，每个程序占用一个端口
- 常见默认端口：HTTP=80, HTTPS=443, MySQL=3306, Redis=6379

---

### 1.6 什么是 API？

> API = Application Programming Interface（应用程序编程接口）

**生活类比**: 餐厅的**菜单**——你不需要知道厨房里怎么炒菜的，你只需要看菜单点菜。API 就是程序之间的"菜单"。

**技术解释**:
- 一个程序提供 API，别的程序（或前端页面）通过 HTTP 请求调用它
- API 定义了"你能请求什么"以及"你会得到什么"
- 例如：前端页面调用 `POST /api/plan/create` 这个 API → 后端创建一个测试计划 → 返回创建结果

---

## 2. 数据的"仓库"——数据库与缓存

### 2.1 什么是"数据库"？

**生活类比**: 一个巨大的**文件柜**，里面有很多文件夹（表），每个文件夹里有按格式填写的表格（数据行）。

**技术解释**:
- 程序需要"记住"东西——用户信息、测试用例、执行结果。这些数据不能只存在内存里（断电就没了），需要持久化存储
- **关系型数据库（MySQL）** = 数据按"表"组织，表有固定的列（比如 `id`、`name`、`create_time`），行就是一条条数据
- **非关系型数据库（MongoDB）** = 更灵活，不需要固定列，存的是 JSON 文档
- **QAMate 使用 MySQL** 存储所有核心业务数据：测试计划、用例、执行结果等

### 2.2 什么是 SQL？

> SQL = Structured Query Language（结构化查询语言）

**生活类比**: 跟文件柜管理员说的话："给我查一下 file_2024 这个文件夹里，所有 status 是 'done' 的记录"

**技术解释**:
- SQL 是操作数据库的语言
- 基本操作：`SELECT`（查询）、`INSERT`（插入）、`UPDATE`（修改）、`DELETE`（删除）
- 例如：`SELECT * FROM plan WHERE status = 'RUNNING'` — 查询所有状态为"运行中"的计划

---

### 2.3 什么是"缓存"？

**生活类比**: 你桌上贴着一张便利贴，上面记着你同事的内线号码——这样你就不用每次去翻厚厚的电话本了。**便利贴就是缓存，电话本就是数据库**。

**技术解释**:
- 缓存把常用的数据放在**更快的地方**（内存而非磁盘），让读取速度大幅提升
- **Redis** 是一个流行的缓存系统，数据存在内存中（就像便利贴），读写速度比 MySQL（像电话本）快 10-100 倍
- **QAMate 使用 JetCache + Redis**：先查本地缓存（就像自己的大脑记住了），没找到再去 Redis（同事告诉你的），再没找到才去 MySQL（查电话本）

---

## 3. 什么是 Web 框架？

### 3.1 为什么需要"框架"？

**生活类比**: 你要开一家餐馆——
- **从零开始** = 自己砌灶台、自己烧砖、自己种菜（原始但控制力强）
- **用框架** = 租一个装修好的铺面，灶台、水槽、排烟都装好了，你只需要炒菜（省事儿但受限于框架设计）

**技术解释**:
- 写一个 Web 后端程序，需要处理 HTTP 请求、路由分发、参数解析、JSON 序列化、数据库连接……每样从零写太累
- **Web 框架** = 一个半成品，把这些基础设施都做好了，你只需要写"你的业务逻辑"
- **Spring Boot** = QAMate 使用的 Java Web 框架（类似 Python 的 FastAPI 或 Django）
- **FastAPI** = 一个流行的 Python Web 框架（如果你懂 Python，可以认为 Spring Boot 是 Java 版的 FastAPI）

---

### 3.2 什么是"路由"？

**生活类比**: 餐厅前台的接待员——客人说"我要找经理"，接待员就把客人带到经理办公室；客人说"我要结账"，接待员就把客人带到收银台。

**技术解释**:
- 路由 = 根据 URL 和方法（GET/POST）把请求分发到对应的处理函数
- 在代码中体现为注解或装饰器：
  ```java
  @PostMapping("/api/plan/create")
  public Result createPlan(@RequestBody PlanDto dto) {
      // 处理创建计划的逻辑
  }
  ```
  这句话的意思是：如果有人访问 `POST /api/plan/create`，就执行 `createPlan` 这个方法

---

### 3.3 什么是"依赖注入"（DI）？

> DI = Dependency Injection

**生活类比**:
- **不用 DI** = 你要开餐厅，自己种菜、自己养猪、自己酿酒——所有事情自己做
- **用 DI** = 你打电话给供应商："送10斤猪肉、20斤白菜过来"——你只管"要什么"，不用管"怎么来的"

**技术解释**:
- 传统方式：`ServiceA service = new ServiceA()` — 你自己 new 出来
- DI 方式：声明 `private final ServiceA service;`，由框架自动给你注入
- **Spring IoC 容器** = 一个超级大管家，负责创建和管理所有对象（Bean），谁需要什么就给什么
- 好处：解耦、便于测试、便于替换实现

---

## 4. 什么是微服务？

### 4.1 单体 vs 微服务

**生活类比**:
- **单体应用（Monolith）** = 一个小吃摊——一个人同时负责点单、做菜、收钱、洗碗。人少的时候效率高，但是客人一多就忙不过来
- **微服务（Microservices）** = 一个美食广场——每个档口只做一种菜，各管各的。A 档口做汉堡，B 档口做奶茶，C 档口做寿司。可以分别扩张（比如汉堡摊生意好，可以多加一个人手）

**技术解释**:
- **单体**：所有功能写在一个程序里，部署一次。优点是简单，缺点是牵一发而动全身
- **微服务**：把系统拆成多个独立的小服务，每个服务独立部署、独立扩展。优点是灵活，缺点是服务之间通信复杂
- **QAMate 采用 3 个微服务**：
  - **Core** — 管理后台（类似餐厅经理）
  - **apiExecutor** — 执行引擎（类似后厨）
  - **api-smart-dispatch** — 调度中心（类似订餐系统）

---

### 4.2 微服务之间怎么通信？

**生活类比**: 美食广场里，A 档口需要 B 档口的食材——A 派一个传菜员直接走到 B 那边去拿。这就是"直接通信"。

**技术解释**:
微服务之间通信的常见方式：

1. **REST API (HTTP 请求)** — 一个服务直接发 HTTP 请求到另一个服务（就像直接打电话）
2. **Feign（Spring Cloud 组件）** — Java 中一种"声明式"的 HTTP 客户端。你只需要定义一个接口，加个注解，Feign 自动帮你发 HTTP 请求（像一个"自动打电话机器人"）
3. **消息队列（如 RabbitMQ）** — 通过一个中间人传递消息（A 把消息放信箱，B 自己去信箱拿），QAMate 目前没用消息队列

**QAMate 的服务通信**：
- Core → Dispatch: Feign（Java 的声明式 HTTP）
- Core → Executor: Feign
- Dispatch → Executor: XXL-JOB 的直接 HTTP 调用

---

## 5. 任务与调度概念

### 5.1 什么是"任务调度"？

**生活类比**: 你每天早上 7 点闹钟响，闹钟叫醒你，你去刷牙洗脸。这个"闹钟"就是任务调度器——它在指定时间触发指定动作。

**技术解释**:
- 有些任务不需要人操作，系统自动按时间执行
- 例如：每天早上 8 点跑一次回归测试、每 5 分钟检查一次任务状态、每月 1 号生成报告
- **Cron 表达式**：一种描述"什么时候执行"的语法，例如 `0 0 8 * * ?` = 每天早上 8 点

---

### 5.2 什么是 Celery？

> Celery 是一个 Python 的**分布式任务队列**

**生活类比**: 你去餐厅吃饭，点完菜后服务员把订单挂在厨房的"订单夹"上（任务队列），厨师有空就从夹子上取一个订单开始做（消费任务）。

**技术解释**:
- Celery 允许你把任务"丢"到一个队列里，然后由 Worker 进程异步处理
- 包含三个部分：
  - **消息中间件（Broker）** — 存任务的"队列"，通常是 Redis 或 RabbitMQ
  - **Worker** — 真正干活的人，从队列里取任务执行
  - **Beat** — 定时触发器，到点了自动往队列里丢任务

**为什么 QAMate 文档提到 Celery**?
因为 QAMate 的架构和 Celery 的架构非常像，只是用 Java 实现了。文档用 Celery 做类比帮助有 Python 背景的人理解。

---

### 5.3 什么是 Celery Worker？

**生活类比**: 后厨的**厨师**——前台（调度器）把订单贴在架上，厨师从架上取订单，开始炒菜（执行任务），炒完了把菜端到出餐口（返回结果）。

**技术解释**:
- Worker 是真正"干活"的进程
- 它监听任务队列，有新任务就取出来执行
- 可以启动多个 Worker 并行处理任务（多开几个灶台同时炒菜）
- **QAMate 的 apiExecutor** = 相当于 Celery Worker 的角色——它监听调度分发的任务，执行测试用例，然后返回结果

---

### 5.4 什么是 Celery Beat？

**生活类比**: 一个**智能闹钟**——你设置"每天早上 8 点"和"每周五下午 3 点"，到点了它自动把任务放到队列里。

**技术解释**:
- Beat 是一个定时调度器进程
- 你配置好"什么时间执行什么任务"的规则（Cron 表达式或固定间隔）
- Beat 到点就自动创建任务并发送到 Broker
- **QAMate 的 api-smart-dispatch** = 相当于 Celery Beat + 调度管理的角色

---

### 5.5 什么是 Airflow？

**生活类比**: 一个**工厂的流水线**——第一步是"切菜"，第二步是"炒菜"，第三步是"装盘"。这些步骤有依赖关系，必须按顺序执行，且可以设置不同的触发条件。

**技术解释**:
- Airflow 是 Python 的一个工作流调度平台，比 Celery Beat 更强大
- 它用 **DAG（有向无环图）** 来描述任务之间的依赖关系
- 比如任务 B 必须在任务 A 完成后才能开始
- **QAMate 的 api-smart-dispatch 包含一些类似 Airflow 的功能**：它可以编排复杂的测试计划，一个计划可能包含多个有关联的测试任务

---

### 5.6 什么是 XXL-JOB？

> XXL-JOB 是一个 Java 的**分布式任务调度平台**

**生活类比**: 一个**项目管理白板**——白板上列着所有"待办任务"，谁有空谁认领，做完后打勾标记完成。白板本身还负责"这件事应该几点做"、"做失败了要不要重试"。

**技术解释**:
- XXL-JOB = Celery Beat + Celery Worker 的 Java 版本，但合并在一个平台中
- 包含两个角色：
  - **调度中心（Admin）** = 管理所有任务定义、Cron 配置、调度逻辑（对应 QAMate 的 **api-smart-dispatch**）
  - **执行器（Executor）** = 注册到调度中心，接收调度中心分发的任务并执行（对应 QAMate 的 **apiExecutor**）
- 核心特性：Cron 调度、任务分片、失败重试、日志追踪

**关键区别**:
| 特性 | Celery (Python) | XXL-JOB (Java) |
|:---|:---|:---|
| 消息传递 | 通过 Redis/RabbitMQ | 直接 HTTP 调用 |
| 调度方式 | Beat 定期检查 | 调度线程每秒扫描 |
| 任务分片 | 手动实现 | 内置支持 |
| 管理界面 | Flower（第三方） | 内置 Admin Web 页面 |

---

## 6. 其他重要概念

### 6.1 什么是 ORM？

> ORM = Object-Relational Mapping（对象关系映射）

**生活类比**: 你的"通讯录"有两份——一份写在纸上（数据库的表），一份存在手机里（程序中的对象）。ORM 就是一个"自动抄写员"，把纸上内容抄到手机里，修改手机里的内容时自动同步到纸上。

**技术解释**:
- 数据库存的是"表"，程序里用的是"对象"
- ORM 自动在这两者之间转换
- 例如你操作一个 `Plan` 对象（Java 类），ORM 自动把它转成 MySQL 中的一条 `plan` 记录
- **MyBatis-Plus** = QAMate 使用的 Java ORM 框架（类似 Python 的 SQLAlchemy）

---

### 6.2 什么是"连接池"？

**生活类比**: 一家快餐店有 5 个取餐窗口——每个窗口一次只能服务一位顾客。**连接池**就是这 5 个窗口。如果有第 6 位顾客，他需要等某个窗口空出来。

**技术解释**:
- 程序访问数据库需要建立"连接"（TCP 连接）
- 每次访问都新建连接 → 销毁连接，开销很大
- **连接池** = 预先创建一批连接，用的时候拿一个，用完归还，避免反复创建销毁
- **Druid** = QAMate 使用的数据库连接池（阿里开源，Java 中最流行之一）

---

### 6.3 什么是"线程"？

**生活类比**: 一个厨师（进程）有 10 只手臂（线程）——每只手臂可以同时做不同的事，一只手切菜，一只手炒菜，一只手装盘。

**技术解释**:
- 程序执行的最小单位
- 多线程 = 一个程序里多条执行路径同时运行
- **Java Virtual Threads（虚拟线程）** = Java 21 的新特性，可以创建非常多的轻量级线程，类似 Python 的 `asyncio` 协程

---

### 6.4 什么是 Feign？

**生活类比**: 你有一张"自动点菜机"——你按一下"红烧肉"按钮，点菜机自动把订单传给厨房，厨房做好后自动通知你。你不需要自己走到厨房去喊"来一份红烧肉"。

**技术解释**:
- Feign 是 Spring Cloud 生态中的一个 HTTP 客户端
- 你只需要定义一个 **Java 接口**，用注解声明请求方式和路径
- Feign 在启动时自动生成接口的实现代码（动态代理）
- 调用接口方法 = 发送 HTTP 请求，方法返回 = 收到响应
- **QAMate 使用 Feign** 做 Core 与 Executor、Core 与 Dispatch 之间的通信

```java
// 你只需要写这个接口
@FeignClient(name = "dispatch-service")
public interface DispatchClient {
    @PostMapping("/api/plan/create")
    Result createPlan(@RequestBody PlanDto dto);
}

// 然后直接调用——Feign 自动发 HTTP 请求
dispatchClient.createPlan(dto);
```

---

### 6.5 什么是"服务发现"？

**生活类比**: 一个大型商场里有一个"服务指南"电子屏——你想找奶茶店，在电子屏上搜一下就知道它在几楼几号铺位。**服务发现**就是这个电子屏。

**技术解释**:
- 在微服务架构中，服务 A 调用服务 B，但服务 B 的 IP 地址可能会变（扩缩容、重启）
- **服务发现组件** = 维护一个"服务名 ↔ IP 地址"的映射表
- 服务启动时自动注册，服务下线时自动注销
- **Gravity** = 百度内部的服务发现组件（类似 Eureka / Consul / Nacos）

---

### 6.6 什么是"SSO"（单点登录）？

> SSO = Single Sign-On（单点登录）

**生活类比**: 你进了一个大型园区，在门口刷一次工卡拿到通行证（登录）。之后你去 A 栋、B 栋、C 栋都不用再刷卡——通行证通用。下班走的时候不需要额外操作。

**技术解释**:
- 公司内部通常有多个系统（OA、邮箱、项目管理、QAMate...）
- SSO 让你登录一次，所有系统都自动认证通过
- **UUAP** = 百度内部的 SSO 认证系统（类似 Okta / Auth0 / 飞书登录）
- QAMate 通过集成 UUAP，让百度的员工直接用公司账号登录

### 7.2 三个服务的角色速查

| 服务 | 一句话理解 | 具体做什么 | 生活类比 |
|:---|:---|:---|:---|
| **Core** | 管理后台 | 管理测试计划、用例、用户、AI 生成测试、展示结果 | 餐厅经理——接单、排班、协调 |
| **api-smart-dispatch** | 调度中心 | 按定时规则把任务分发给执行器，失败重试 | 店长+排班系统——到点了叫厨师干活 |
| **apiExecutor** | 执行引擎 | 实际执行测试（发 HTTP 请求、查数据库等），返回结果 | 后厨厨师——真正动手做菜 |

### 7.3 一个测试任务的完整流程

用餐厅类比来看一条测试任务的执行过程：

```
1. 用户在前端页面点"执行测试计划"
    → 相当于客人对经理说："我要一份红烧肉"

2. Core 收到请求，通知 Dispatch
    → 经理在排班表上登记："3 号桌要红烧肉"

3. Dispatch 按规则分派任务给 Executor
    → 店长看哪个厨师有空，指派："王师傅，做一份红烧肉"

4. Executor 执行测试（发 HTTP 请求、检查返回结果）
    → 王师傅开火、炒菜、装盘

5. Executor 把结果回传给 Core
    → 王师傅喊："做好了"，传菜员端给经理

6. Core 保存结果，前端展示给用户
    → 经理记录"已完成"，告诉客人："您的菜来了"
```

## 8. 快速术语表

| 术语 | 一句话解释 | 生活类比 |
|:---|:---|:---|
| **后端** | 在服务器上运行的程序，处理业务逻辑和存储数据 | 餐厅厨房 |
| **前端** | 用户在浏览器里看到的页面 | 餐厅菜单+服务员 |
| **服务器** | 24 小时不关机的远程电脑 | 永不关门的餐厅 |
| **API** | 程序之间约定好的调用方式 | 餐厅菜单 |
| **HTTP** | 互联网上通信的"信纸格式" | 写信的格式规范 |
| **URL** | 互联网上的地址 | 家庭住址 |
| **端口** | 服务器上的"门牌号"，区分不同服务 | 大楼的不同门 |
| **数据库** | 持久化存储数据的地方 | 文件柜 |
| **MySQL** | 一种流行的关系型数据库 | 按固定格式整理的文件柜 |
| **SQL** | 操作数据库的语言 | 跟文件柜管理员说的话 |
| **缓存 / Redis** | 临时存数据在内存中，加速读取 | 便利贴 |
| **Web 框架** | 帮你处理 HTTP 基础设施的半成品 | 装修好的厨房 |
| **Spring Boot** | Java 的 Web 框架 | Java 版的"装修好的厨房" |
| **FastAPI** | Python 的 Web 框架 | Python 版的"装修好的厨房" |
| **依赖注入** | 框架自动给你需要的东西，不用自己创建 | 供应商送货上门 |
| **微服务** | 把一个系统拆成多个独立小程序 | 美食广场 |
| **Feign** | Java 中"声明式" HTTP 客户端 | 自动点菜机 |
| **路由** | 根据 URL 决定谁来处理请求 | 前台接待员 |
| **ORM** | 自动在"数据库表"和"程序对象"之间转换 | 自动抄写员 |
| **连接池** | 预先创建的数据库连接，用的时候拿一个 | 餐厅的取餐窗口 |
| **线程** | 程序里同时执行多条路径 | 厨师的多只手臂 |
| **任务调度** | 按时间自动触发任务执行 | 闹钟 |
| **Celery** | Python 的任务队列系统 | 订单夹+厨师+排班表 |
| **XXL-JOB** | Java 的任务调度平台 | 项目管理白板 |
| **SSO** | 登录一次，所有系统通用 | 园区一卡通 |
| **Cron** | 描述"什么时候执行"的表达式 | 日程表的简写方式 |
| **DAG** | 有依赖关系的任务流程图 | 工厂流水线 |
