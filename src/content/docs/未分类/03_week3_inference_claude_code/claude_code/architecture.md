# Claude Code 整体架构

> Claude Code 是 Anthropic 官方推出的 CLI Agent，专注于编程场景。它的核心价值不是"能调工具"，而是将工具、上下文、权限和执行环境整合为一套可控的本地 Agent Runtime。

## 2. 核心组件详解

### 2.1 Agent Core — 消息循环

> **Message Loop（消息循环）**: Agent 的核心运行机制，循环执行"接收消息 → 调用模型 → 执行工具 → 写回结果"直到模型输出最终回复。

Agent Core 本质上是一个 REPL（Read-Eval-Print Loop），但它不是一次性的，而是一个持续运转的消息循环。每一轮循环的工作流程如下：

```
┌──────────────────────────────────────────────┐
│              Message Loop (单轮)               │
│                                              │
│  1. READ    : 从用户或上一轮获取消息            │
│  2. BUILD   : 组装 context + tool schema      │
│  3. CALL    : 调用 Anthropic Messages API     │
│  4. CHECK   : 响应是否包含 tool_use?          │
│     ├─ 否 → 输出最终回复，结束本轮             │
│     └─ 是 → 进入工具执行子循环                 │
│  5. EXECUTE : 逐个执行工具调用                  │
│  6. WRITE   : 将工具结果写回 context            │
│  7. LOOP    : 回到第 3 步，带新 context 再调模型 │
│                                              │
└──────────────────────────────────────────────┘
```

用 Python 伪代码表达：

```python
async def message_loop(user_input: str, context: Context, tools: list[Tool]):
    """Agent Core 的核心消息循环"""
    context.add_user_message(user_input)

    while True:
        # 2. 组装请求：system prompt + 历史 + 工具 schema
        request = build_api_request(context, tools)

        # 3. 调用模型
        response = await anthropic.messages.create(**request)

        # 4. 检查是否有工具调用
        if not response.has_tool_calls():
            # 没有工具调用 → 输出最终回复
            print_to_user(response.text)
            context.add_assistant_message(response)
            return response

        # 5. 执行所有工具调用
        for tool_call in response.tool_calls:
            # 5a. 权限检查
            if not permission_system.is_auto_allowed(tool_call):
                approved = await ask_user_permission(tool_call)
                if not approved:
                    context.add_tool_result(tool_call, "用户拒绝了此操作")
                    continue

            # 5b. 执行工具
            result = await tool_registry.execute(tool_call)
            context.add_tool_result(tool_call, result)

        # 6. 将 assistant 消息（含 tool_calls）写入 context
        context.add_assistant_message(response)

        # 7. 带着新的 context 回到循环开头
```

这个循环的关键设计点：

1. **多轮工具调用**：模型可以在一次响应中返回多个 `tool_use` 块，循环会逐个执行。
2. **Context 累积**：每次工具结果都会追加到 context 中，模型基于完整历史做下一步决策。
3. **终止条件**：当模型不再调用工具、而是返回纯文本时，本轮循环结束。

### 2.2 Tool Layer — 工具层

> **Tool Layer（工具层）**: Agent 与外部世界交互的唯一接口。所有"做事"的动作都必须通过工具完成，模型本身不能直接操作文件系统或执行命令。

Claude Code 内建了以下核心工具：

| 工具 | 功能描述 | 风险等级 | 典型使用场景 |
|------|----------|----------|-------------|
| `Bash` | 在 shell 中执行任意命令 | 高 | 安装依赖、运行测试、git 操作 |
| `Read` | 读取文件内容（含图片、PDF、notebook） | 低 | 查看代码、读取配置、查看截图 |
| `Write` | 创建或覆盖整个文件 | 中 | 创建新文件、生成配置、写入代码 |
| `Edit` | 对文件做精确的字符串替换 | 中 | 修改现有代码、修 bug、重构 |
| `Glob` | 按文件名模式匹配搜索文件 | 低 | 查找项目文件、定位模块 |
| `Grep` | 按正则表达式搜索文件内容 | 低 | 查找引用、搜索错误信息 |
| `NotebookEdit` | 编辑 Jupyter notebook 单元格 | 中 | 数据分析、notebook 交互 |

工具执行的完整链路：

```
模型输出 tool_use
       │
       ▼
┌─ Parameter Validation (参数校验) ─┐
│  - schema 校验                     │
│  - 路径合法性检查                   │
└──────────┬────────────────────────┘
           │ 通过
           ▼
┌─ Permission Check (权限检查) ─────┐
│  - auto-allow / ask / restricted   │
└──────────┬────────────────────────┘
           │ 通过
           ▼
┌─ PreToolUse Hook ─────────────────┐
│  - 用户自定义前置逻辑               │
└──────────┬────────────────────────┘
           │ 通过
           ▼
┌─ Tool Execution (实际执行) ────────┐
│  - Bash: 启动子进程执行命令          │
│  - Read: 读取文件内容               │
│  - Write/Edit: 修改文件             │
│  - Glob/Grep: 搜索文件系统          │
└──────────┬────────────────────────┘
           │ 完成
           ▼
┌─ PostToolUse Hook ────────────────┐
│  - 自动格式化、日志记录、reward 采集  │
└──────────┬────────────────────────┘
           │
           ▼
    结果写回 Context Window
```

### 2.3 Permission System — 权限系统

> **Permission System（权限系统）**: 控制模型对本地资源操作权限的安全机制，确保"模型不会乱动代码库"。

权限系统按照风险等级对工具操作进行分层：

| 权限级别 | 行为 | 涵盖的工具 | 示例 |
|----------|------|-----------|------|
| **Auto-allow** | 自动通过，不问用户 | `Read`、`Glob`、`Grep` | 读取代码、搜索文件 |
| **Ask User** | 每次询问用户确认 | `Write`、`Edit`、普通 `Bash` | 修改文件、执行命令 |
| **Restricted** | 需要显式授权 | 删除文件、危险 shell 命令 | `rm -rf`、网络访问 |

用户可以通过以下方式配置权限：

- **全局配置** (`~/.claude/settings.json`)：对所有项目生效
- **项目配置** (`.claude/settings.json`)：仅对当前项目生效
- **命令行参数**：临时调整权限策略
- **`allowedTools`**：预授权特定工具，减少交互打断

### 2.4 Context Window — 上下文窗口

> **Context Window（上下文窗口）**: 一次 API 请求中能容纳的 token 总量上限。包括 system prompt、对话历史、工具 schema、工具结果和当前用户输入。

Context Window 管理是 Agent Runtime 中最关键的工程挑战之一。它负责：

- **维护 System Prompt**：包括 `.claude/rules/` 中的用户自定义规则
- **累积对话历史**：用户消息、助手回复、工具调用和结果
- **记录工具执行轨迹**：每次工具的输入和输出都会写入历史
- **触发上下文压缩**：当 token 接近上限时自动压缩，为新请求腾出空间

```
┌─────────────────────────────────────────┐
│            Context Window (200K tokens)  │
│                                         │
│  ┌─────────────────┐                    │
│  │ System Prompt   │  ← 规则、角色定义   │
│  │ (~5-10K)        │                    │
│  ├─────────────────┤                    │
│  │ Tool Schemas    │  ← 工具定义        │
│  │ (~3-5K)         │                    │
│  ├─────────────────┤                    │
│  │ 对话历史        │  ← 累积的消息       │
│  │ (动态增长)      │    和工具结果       │
│  │  ╔═════════╗    │                    │
│  │  ║ 最早历史 ║    │  ← 压缩优先区域     │
│  │  ║ ...      ║    │                    │
│  │  ║ 最近对话 ║    │  ← 原文保留        │
│  │  ╚═════════╝    │                    │
│  ├─────────────────┤                    │
│  │ 当前用户输入     │  ← 本轮请求        │
│  └─────────────────┘                    │
│                                         │
│  ████████████░░░░░░░░░  使用率 60%      │
└─────────────────────────────────────────┘
```

## 3. 与其他 Agent 框架的架构对比

> **Agent Framework（Agent 框架）**: 用于构建 LLM Agent 应用的软件开发框架，提供工具编排、上下文管理、Agent 通信等基础能力。

| 维度 | Claude Code | LangChain | AutoGen | CrewAI |
|------|-------------|-----------|---------|--------|
| **定位** | 编程专用 CLI Agent Runtime | 通用 LLM 应用开发框架 | 多 Agent 对话框架 | 角色协作型 Agent 框架 |
| **核心抽象** | Tool + REPL Loop | Chain / Agent / Tool | Agent + Conversation | Crew + Agent + Task |
| **运行形态** | 本地 CLI，绑定工作区 | 库/服务，灵活部署 | 服务端/实验，偏研究 | 库/服务，偏业务流程 |
| **上下文管理** | 内建，强 Context Manager | 应用方自行组织 | 每个 Agent 自管 | 应用方自行组织 |
| **权限系统** | 内建三级权限 | 通常不内置，需自行添加 | 通常不内置 | 通常不内置 |
| **工具执行** | 强绑定本地文件系统和 Shell | 抽象化，可对接任意后端 | 灵活但更抽象 | 通过 Tool 接口抽象 |
| **Agent 通信** | 主 Agent + SubAgent（Task Tool） | 多种模式（链式、路由、并行） | 对话式多 Agent 通信 | 角色之间顺序/并行协作 |
| **扩展机制** | Hook + Skill + Settings | 自定义 Chain/Tool/Agent | 自定义 Agent/工具 | 自定义 Tool/流程 |

关键差异总结：

1. **Claude Code 不是通用框架**：它不做 Chain、不做 RAG、不做 Agent 路由，而是把"用 LLM 写代码"这一个场景做到极致。
2. **权限内建是独特优势**：其他框架通常把权限留给应用方，而 Claude Code 在 Runtime 层面就做了三级权限控制。
3. **本地优先**：Claude Code 的所有执行都在用户本地，不需要远程服务器，这让权限和隐私控制更直接。

## 4. Claude Code 作为 Harness 的理解

> **Harness（训练脚手架）**: 在 RL 训练中，为模型提供交互环境的系统。它定义了模型的 Action Space（能做什么）、Observation Space（能看到什么）和 Reward Signal（做得好不好）。

从 RL 训练的视角看，Claude Code 的每个组件都可以映射到 Harness 中的经典角色：


这个映射关系揭示了 Claude Code 的深层设计逻辑：

- **Tool = InputAdapter**：模型只能输出结构化的工具调用 JSON，Tool Layer 将其翻译为实际的文件操作或 Shell 命令。这就像 RL 中 Policy 输出离散动作 ID，Environment 将其翻译为实际执行。
- **Hook = RewardCollector**：PostToolUse Hook 可以在每次工具执行后收集结果、计算 reward、写入训练日志。这就像 RL 中每步执行后收集 (state, action, reward, next_state) 四元组。
- **Agent Core = Policy**：模型本身就是策略函数，根据当前 context（观测）决定下一步做什么（动作）。Message Loop 就是策略执行循环。
- **Sandbox = Executor**：本地文件系统和 Shell 就是环境执行器，模型不能直接操作，必须通过工具间接执行。
- **Context = ObservationBuffer**：Context Window 就是模型的观测缓冲区，管理着策略能看到的所有历史信息。

## 5. 设计哲学总结

Claude Code 的架构设计可以提炼为五个核心原则：

1. **工具优先（Tool-First）**：模型不能直接操作任何资源，所有动作都必须通过工具完成。这保证了安全性和可审计性。
2. **本地执行（Local Execution）**：工具在用户的本地机器上执行，而非远程服务器。这让权限控制更直接，也尊重了用户对代码的完全所有权。
3. **渐进信任（Progressive Trust）**：通过三级权限系统，低风险操作自动通过，高风险操作需用户确认。随着用户信任建立，可以逐步放宽权限。
4. **可观测性（Observability）**：所有工具调用都通过 Hook 系统暴露给外部，支持日志记录、质量检查和 reward 采集。
5. **上下文经济（Context Economy）**：通过 Context Manager 和自动压缩机制，在有限的 token 预算内最大化保留关键信息。

## 面试高频问题

### Q1: Claude Code 和 LangChain 这种通用 Agent 框架有什么本质区别？

**A**: Claude Code 不是一个"抽象优先"的通用框架，而是一个为编程场景深度优化的 Agent Runtime。核心区别在于三点：（1）权限系统内建在 Runtime 层面，不是事后添加的；（2）工具直接绑定本地文件系统和 Shell，不是抽象接口；（3）上下文管理由 Runtime 统一负责，不是交给应用方自己组织。用一句话概括：LangChain 是"造 Agent 的积木"，Claude Code 是"一个已经造好的、专为编程设计的 Agent"。

### Q2: 如果让你从零重新实现一个类似 Claude Code 的系统，最核心的模块是什么？

**A**: 最核心的是 Message Loop + Tool Execution Loop。模型负责决策（调用什么工具、传什么参数），工具负责执行（操作文件系统、运行命令），Context Manager 负责记忆管理（保留什么、压缩什么），Permission System 负责风险约束（哪些操作自动通过、哪些需要确认）。这四个组件构成一个闭环，缺一不可。

### Q3: 为什么 Claude Code 选择把工具执行放在客户端本地，而不是放在服务端？

**A**: 三个原因。第一，安全性：代码库、凭证、配置文件都在用户本地，放服务端意味着要传输大量敏感数据；第二，灵活性：用户本地有完整的开发环境（git、docker、数据库），这些不可能在服务端复制；第三，延迟：本地执行没有网络往返开销，工具调用的响应速度更快。

### Q4: 用 RL 训练的视角解释 Claude Code 的架构，它如何作为训练 Harness 使用？

**A**: Claude Code 的架构天然适配 RL 训练范式。Tool Layer 充当 InputAdapter，将模型的工具调用 JSON 映射为环境的实际操作；Hook System（特别是 PostToolUse）充当 Reward Collector，收集每步执行的反馈信号；Agent Core 的 Message Loop 就是策略执行循环；Sandbox（本地环境）充当 Executor，执行动作并返回观测；Context Window 充当观测缓冲区。整个系统就是一个完整的"观测 → 决策 → 执行 → 反馈"闭环，可以直接用于收集 RL 训练数据。
