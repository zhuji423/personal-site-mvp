# Context Compaction 上下文压缩策略

> **核心问题**: 上下文窗口有限，但 Agent 在执行任务的过程中会不断累积对话历史、工具结果和中间分析。系统如何保证"继续记住重要东西"，同时又不把 token 全部烧光？

---

## 1. Context Window 定义

> **Context Window（上下文窗口）**: 一次 LLM API 请求中能容纳的 token 总量上限。它包括 system prompt、对话历史、工具 schema、工具结果和当前用户输入。

Context Window 是 LLM 应用的核心资源约束。可以把它理解为模型的"工作记忆"——在单次推理中，模型只能看到 Context Window 内的信息，超出部分完全不可见。

以 Claude 为例，当前模型的 Context Window 大小为 200K token。这些 token 的典型分配如下：

```
┌────────────────────────────────────────────────────────────────┐
│                 Context Window (200K tokens)                    │
│                                                                │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │  System Prompt (固定开销)                    ~5-10K      │  │
│  │  - 角色定义、行为规则、安全约束                              │  │
│  │  - .claude/rules/ 中的用户自定义规则                        │  │
│  ├──────────────────────────────────────────────────────────┤  │
│  │  Tool Schemas (固定开销)                     ~3-5K       │  │
│  │  - Bash, Read, Write, Edit, Glob, Grep 的 JSON Schema    │  │
│  ├──────────────────────────────────────────────────────────┤  │
│  │  对话历史 (动态增长)                        ~180-190K    │  │
│  │  - 用户消息、助手回复、工具调用和结果                        │  │
│  │  - 随着任务执行不断累积                                    │  │
│  ├──────────────────────────────────────────────────────────┤  │
│  │  当前用户输入 (本轮请求)                      ~1-2K       │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  固定开销合计: ~8-15K token                                     │
│  可用于对话历史: ~185-192K token                                │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

为什么 Context Window 的管理如此重要？

1. **硬约束**：一旦超出上限，API 直接报错，无法继续
2. **成本**：token 使用量直接决定每次 API 调用的费用
3. **注意力稀释**：即使没有超出上限，过长的 context 也会降低模型对关键信息的关注
4. **延迟**：更长的输入意味着更慢的推理速度

---

## 2. Context Compaction 定义

> **Context Compaction（上下文压缩）**: 在信息损失可控的前提下，将过长的对话历史压缩为更短的表示，为新请求腾出 Context Window 空间的技术。

Context Compaction 的核心矛盾是：

```
┌────────────────────────────────────────────────────────────────┐
│                    核心矛盾                                     │
│                                                                │
│   留住更多信息  ◄──────────────────────►  节省更多 token        │
│   (信息保真)                            (空间效率)               │
│                                                                │
│   完美保留 = 不压缩 = token 爆炸                                │
│   极致压缩 = 信息全丢 = 模型失忆                                │
│                                                                │
│   Context Compaction 要做的就是在两者之间找到最佳平衡点           │
└────────────────────────────────────────────────────────────────┘
```

Compaction 的三个核心目标：

1. **空间释放**：为新请求腾出足够的 token 空间
2. **信息保留**：尽量保留对后续决策有影响的关键信息
3. **结构维持**：保持对话历史的基本结构，让模型能理解"之前发生了什么"

---

## 3. 三种压缩策略详解

### 3.1 滑动窗口（Sliding Window）

> **Sliding Window（滑动窗口）**: 只保留最近 N 轮对话的原始内容，将更早的内容完全丢弃或折叠为摘要。

这是最简单也最直观的策略：

```
压缩前:
┌────────────────────────────────────────────────────────────────┐
│ [第1轮] [第2轮] [第3轮] ... [第18轮] [第19轮] [第20轮]          │
│  ─── 丢弃区域 ───                ─── 保留区域 ───              │
└────────────────────────────────────────────────────────────────┘

压缩后:
┌────────────────────────────────────────────────────────────────┐
│ [摘要: 第1-15轮的要点]  [第16轮] [第17轮] [第18轮] [第19轮] [第20轮] │
│  ─── 压缩区域 ───         ─────── 原文保留区域 ───────          │
└────────────────────────────────────────────────────────────────┘
```

**实现要点**：

- 窗口大小（保留多少轮原文）是核心超参数，通常设为 5-10 轮
- 丢弃区域不一定是全量丢弃，可以先做一次摘要再丢弃原始内容
- 需要一个"关键信息提取"步骤，确保被丢弃的内容中的重要事实被保留到摘要中

**优点**：

- 实现简单，计算开销小
- 最近的对话保留原文，信息无损失
- 行为可预测——模型"记住"的范围是确定的

**缺点**：

- 丢弃区域的信息可能不可恢复
- 如果关键信息恰好出现在窗口外，会导致模型"忘记"
- 摘要质量直接影响后续决策质量

### 3.2 摘要压缩（Summarization）

> **Summarization（摘要压缩）**: 使用 LLM 将长对话历史压缩为结构化的摘要，保留关键事实、决策和结论，丢弃过程细节。

摘要压缩的核心是用一次额外的 LLM 调用来"重写"历史：

```
压缩流程:

┌────────────────────────────────────────────────────────────────┐
│                                                                │
│  原始历史 (50K tokens):                                        │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ [用户] 请帮我修复 login 函数的 bug                        │  │
│  │ [助手] 我先搜索相关代码...                                │  │
│  │ [工具] Glob: 找到 3 个文件                                │  │
│  │ [工具] Read: auth/login.ts 的内容 (200 行)               │  │
│  │ [助手] 我发现问题在 null check...                        │  │
│  │ [工具] Edit: 修改了第 45 行                              │  │
│  │ [工具] Bash: 运行测试 (300 行输出)                       │  │
│  │ [助手] 测试通过了，但发现另一个问题...                     │  │
│  │ ... (更多对话)                                           │  │
│  └──────────────────────────────────────────────────────────┘  │
│                         │                                      │
│                         ▼                                      │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │  摘要压缩 (LLM 调用)                                      │  │
│  │                                                          │  │
│  │  输入: "请将以下对话历史压缩为结构化摘要，保留关键决策     │  │
│  │         和事实，丢弃过程细节"                              │  │
│  └──────────────────────────────────────────────────────────┘  │
│                         │                                      │
│                         ▼                                      │
│  压缩后摘要 (3K tokens):                                       │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ ## 任务: 修复 auth/login.ts 中的 null check bug           │  │
│  │ ## 已完成:                                               │  │
│  │   - 定位到 auth/login.ts 第 45 行的 null check            │  │
│  │   - 修改了 null check 逻辑                               │  │
│  │   - 测试通过                                             │  │
│  │ ## 待处理:                                               │  │
│  │   - 发现 auth/token.ts 也有类似问题                      │  │
│  │ ## 关键文件:                                              │  │
│  │   - src/auth/login.ts (已修改)                           │  │
│  │   - src/auth/token.ts (待修改)                           │  │
│  │   - tests/auth/login.test.ts (已验证)                    │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

**摘要的质量关键在于 Prompt 设计**：

```python
SUMMARIZATION_PROMPT = """
你是一个对话历史摘要器。请将以下 Agent 对话历史压缩为结构化摘要。

必须保留的信息：
1. 当前任务的完整目标
2. 已完成的关键操作和决策
3. 尚未完成的待办事项
4. 所有被修改的文件路径及修改内容摘要
5. 重要的错误信息和解决方案
6. 用户明确提出的约束条件

可以丢弃的信息：
1. 搜索过程中的中间结果
2. 工具执行的完整输出
3. 模型的思考过程和推理细节
4. 重复的操作和尝试

输出格式：
## 任务目标
## 已完成操作
## 待办事项
## 关键文件
## 重要约束
## 错误与解决
"""
```

**优点**：

- 压缩比高（通常 10:1 到 20:1）
- 保留结构化信息，便于模型后续引用
- 摘要本身是模型可理解的自然语言

**缺点**：

- 需要额外的 LLM 调用，有计算和成本开销
- 摘要不可避免地会丢失细节
- 多次摘要的累积会导致信息逐轮损耗（"传话游戏"效应）

### 3.3 选择性丢弃（Selective Dropping）

> **Selective Dropping（选择性丢弃）**: 基于规则或模型评估，识别出对后续决策最不重要的信息并丢弃，保留重要性高的信息原文。

选择性丢弃的核心思想是"不是所有 token 都同等重要"：

```
┌────────────────────────────────────────────────────────────────┐
│                   信息重要性分层                                 │
│                                                                │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 层级 0 (绝不能丢)                          保留原文       │  │
│  │ - System prompt 和规则                                   │  │
│  │ - 当前任务目标                                           │  │
│  │ - 用户明确约束                                           │  │
│  │ - 最近的用户消息和助手回复                                 │  │
│  ├──────────────────────────────────────────────────────────┤  │
│  │ 层级 1 (尽量保留)                          保留原文       │  │
│  │ - 最近的工具调用和结果                                    │  │
│  │ - 被修改的文件内容                                       │  │
│  │ - 错误信息和解决方案                                      │  │
│  ├──────────────────────────────────────────────────────────┤  │
│  │ 层级 2 (可以摘要)                          摘要化         │  │
│  │ - 早期的工具调用结果                                      │  │
│  │ - 搜索中间结果                                           │  │
│  │ - 模型的中间推理                                         │  │
│  ├──────────────────────────────────────────────────────────┤  │
│  │ 层级 3 (可以直接丢弃)                      直接丢弃       │  │
│  │ - 完整的文件内容（如果文件未被修改）                        │  │
│  │ - 大量的测试输出                                          │  │
│  │ - 重复的搜索结果                                         │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

**实现方式**：

```python
def selective_compaction(context: Context, target_tokens: int) -> Context:
    """选择性丢弃策略的伪代码实现"""

    # 按重要性分层
    critical_items = []    # 层级 0: 绝不能丢
    important_items = []   # 层级 1: 尽量保留
    summarizable_items = [] # 层级 2: 可以摘要
    droppable_items = []   # 层级 3: 可以丢弃

    for item in context.history:
        if item.is_system_prompt() or item.is_current_task():
            critical_items.append(item)
        elif item.is_recent_tool_result() or item.is_modified_file():
            important_items.append(item)
        elif item.is_old_tool_result() or item.is_search_intermediate():
            summarizable_items.append(item)
        elif item.is_full_file_content() or item.is_test_output():
            droppable_items.append(item)

    # 从最低重要性开始丢弃
    current_tokens = sum(item.tokens for item in critical_items + important_items)

    # 第一轮：丢弃层级 3
    if current_tokens > target_tokens:
        for item in droppable_items:
            current_tokens -= item.tokens
            context.remove(item)
            if current_tokens <= target_tokens:
                break

    # 第二轮：摘要化层级 2
    if current_tokens > target_tokens:
        for item in summarizable_items:
            summary = summarize(item)  # 用 LLM 生成摘要
            saved = item.tokens - summary.tokens
            context.replace(item, summary)
            current_tokens -= saved
            if current_tokens <= target_tokens:
                break

    # 如果还不够，开始摘要化层级 1（但这会有更大风险）
    if current_tokens > target_tokens:
        for item in important_items:
            summary = summarize(item)
            context.replace(item, summary)
            current_tokens -= (item.tokens - summary.tokens)
            if current_tokens <= target_tokens:
                break

    return context
```

**优点**：

- 保留关键信息的原文，减少信息损失
- 丢弃规则可定制，适应不同场景
- 比"全部摘要"更精细

**缺点**：

- 规则设计需要深入理解 Agent 的行为模式
- "重要性"的判断本身可能不准确
- 实现复杂度高于滑动窗口和纯摘要

### 3.4 三种策略对比

| 维度 | 滑动窗口 | 摘要压缩 | 选择性丢弃 |
|------|----------|----------|-----------|
| **压缩比** | 中等（5:1 ~ 10:1） | 高（10:1 ~ 20:1） | 可变（取决于规则） |
| **计算开销** | 极低 | 高（需要 LLM 调用） | 中等（部分需要 LLM 调用） |
| **信息保留** | 近期保留好，远期差 | 取决于摘要质量 | 关键信息保留好 |
| **实现复杂度** | 低 | 中 | 高 |
| **可预测性** | 高 | 中 | 中（取决于规则质量） |
| **适用场景** | 短任务、简单对话 | 长任务、复杂推理 | 生产级 Agent 系统 |

在实际系统中，通常不是选择单一策略，而是组合使用：

```
┌────────────────────────────────────────────────────────────────┐
│                   组合策略                                       │
│                                                                │
│  第 1 步: 选择性丢弃（快速，零 LLM 开销）                         │
│    → 丢弃层级 3（完整文件内容、大量测试输出）                     │
│    → 如果 token 已够，停止                                      │
│                                                                │
│  第 2 步: 滑动窗口 + 摘要（中等开销）                             │
│    → 超出窗口的旧对话用 LLM 摘要化                               │
│    → 窗口内的近期对话保留原文                                     │
│    → 如果 token 已够，停止                                      │
│                                                                │
│  第 3 步: 深度摘要（高开销，最后手段）                            │
│    → 对剩余内容做更激进的摘要                                    │
│    → 只保留最关键的事实和待办事项                                 │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

## 4. 触发阈值设计

### 4.1 为什么需要阈值

压缩不是免费的——它要么消耗计算资源（摘要压缩），要么丢失信息（滑动窗口/选择性丢弃）。因此，不应该每轮都做压缩，而是应该在 token 使用量接近上限时才触发。

### 4.2 经典的"80/50"阈值设计

> **触发阈值（Trigger Threshold）**: Context Window 使用率达到某个百分比时，自动触发压缩机制。

最常见的阈值设计是"80% 触发，压缩到 50%"：

```
Context Window 使用率

100% ████████████████████████████████████  ← 硬上限（超出直接报错）
 80% ██████████████████████░░░░░░░░░░░░░░  ← 触发阈值（开始压缩）
 50% ████████████████░░░░░░░░░░░░░░░░░░░░  ← 目标阈值（压缩到此处）
  0% ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░

工作流程：
1. 每次工具结果写入 context 后，检查 token 使用率
2. 如果使用率 < 80% → 不压缩，继续执行
3. 如果使用率 >= 80% → 触发压缩
4. 压缩目标是把使用率降到 50% 左右
5. 压缩完成后继续执行下一轮 Message Loop
```

### 4.3 为什么是 80/50 而不是其他值？

| 参数 | 值 | 选择理由 |
|------|-----|---------|
| 触发阈值 80% | 留 20% 余量给下一轮的工具结果和模型输出 | 如果 100% 才触发，下一轮可能直接溢出 |
| 目标阈值 50% | 一次压缩释放 30% 的空间，够后续多轮使用 | 压缩太激进会丢太多信息，太保守会频繁触发 |
| 200K context | 80% = 160K 触发，50% = 100K 目标 | 释放 60K token 空间 |

### 4.4 阈值参数的调优考虑

```
┌────────────────────────────────────────────────────────────────┐
│                阈值调优的权衡                                    │
│                                                                │
│  触发阈值太高（如 95%）:                                        │
│    ✓ 每次压缩释放更多空间                                       │
│    ✗ 下一轮可能直接溢出                                         │
│    ✗ 压缩本身也可能消耗大量 token                                │
│                                                                │
│  触发阈值太低（如 50%）:                                        │
│    ✓ 永远不会溢出                                              │
│    ✗ 压缩太频繁，信息逐轮损耗严重                                │
│    ✗ 增加不必要的 LLM 调用成本                                   │
│                                                                │
│  目标阈值太高（如 80%）:                                        │
│    ✓ 保留更多信息                                              │
│    ✗ 释放空间不够，很快又要再次压缩                               │
│                                                                │
│  目标阈值太低（如 20%）:                                        │
│    ✓ 大量空间可用                                              │
│    ✗ 丢弃了大量有价值的信息                                      │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

## 5. 对 Agent 执行的影响

### 5.1 正面影响

| 影响 | 说明 |
|------|------|
| **延长任务持续时间** | 没有 Context Compaction，长任务会在 token 上限时直接中断 |
| **降低成本** | 丢弃冗余信息减少了每轮 API 调用的 token 数量 |
| **提高推理速度** | 更短的 context 意味着更快的推理延迟 |
| **减少注意力稀释** | 过长的 context 会让模型"分心"，压缩后注意力更集中 |

### 5.2 负面影响

| 影响 | 说明 | 严重程度 |
|------|------|----------|
| **信息丢失** | 压缩一定意味着信息损失，关键信息可能被丢弃 | 高 |
| **重复劳动** | 模型可能忘记之前试过的方案，导致重新尝试 | 中 |
| **上下文断裂** | 摘要后的历史不连贯，模型难以理解因果链 | 中 |
| **累积误差** | 多次压缩的"传话游戏"效应导致信息逐渐失真 | 高 |
| **决策不一致** | 模型基于压缩后的摘要做出的决策可能与基于完整历史的不同 | 中 |

### 5.3 典型的失败模式

```
场景: 模型在第 5 轮发现了一个关键约束，但在第 15 轮压缩时被丢弃

第 5 轮:
  [助手] "我注意到这个项目的 API 必须向后兼容 v1 版本，
         所以新的接口不能改变已有的参数类型。"

第 15 轮 (压缩触发):
  摘要中可能只保留了 "修改了 3 个文件"，而丢失了 "API 必须向后兼容" 的约束

第 20 轮:
  [助手] "我来重构这个接口，把参数类型从 string 改为 number..."
  → 违反了之前发现的约束，因为摘要中没有保留这个信息

缓解策略:
  - 在摘要 Prompt 中明确要求保留所有用户约束
  - 维护一个"永不丢弃"的关键事实列表
  - 使用选择性丢弃而非全量摘要
```

## 6. 大规模 Rollout 中的策略

> **Rollout（推演）**: 在 RL 训练中，让模型在环境中执行完整 episode（从开始到结束），收集轨迹数据用于训练。

在 RL 训练的大规模 rollout 中，Context Compaction 面临额外的挑战：

### 6.1 Rollout 场景的特殊约束

| 约束 | 说明 |
|------|------|
| **轨迹完整性** | 训练需要完整的 (s, a, r, s') 序列，压缩会破坏 state 的完整性 |
| **Reward 可追溯性** | 每步的 reward 需要对应到具体的 action 和 state |
| **可复现性** | 同一条轨迹在不同压缩策略下可能产生不同结果 |
| **批量效率** | 大规模 rollout 需要考虑压缩的计算成本 |

### 6.2 Rollout 中的推荐策略

```
┌────────────────────────────────────────────────────────────────┐
│             Rollout 中的 Context Compaction 策略                │
│                                                                │
│  1. 训练时:                                                     │
│     - 尽量不用 Context Compaction（保持轨迹完整）                │
│     - 如果任务超长无法避免，使用滑动窗口（行为可预测）             │
│     - 将压缩元数据（哪些内容被丢弃/摘要）记录到日志                │
│                                                                │
│  2. 推理时（部署后）:                                            │
│     - 使用组合策略（选择性丢弃 + 滑动窗口 + 摘要）               │
│     - 维护关键信息保护列表                                       │
│     - 80/50 阈值设计                                            │
│                                                                │
│  3. 数据分析时:                                                 │
│     - 统计每条轨迹的压缩次数和压缩比                              │
│     - 分析压缩对最终 reward 的影响                               │
│     - 评估不同压缩策略对模型行为的差异                             │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 6.3 关键建议

1. **训练阶段尽可能避免压缩**：如果任务确实很长，考虑使用 SubAgent 拆分而非压缩。SubAgent 的独立 context 可以避免主 context 膨胀。

2. **如果必须压缩，记录压缩元数据**：知道哪些信息被丢弃，对于分析模型行为和改进压缩策略至关重要。

3. **A/B 测试不同策略**：在相同任务上对比"无压缩"、"滑动窗口"、"摘要压缩"三种策略的 reward 分布，选择最优方案。

4. **压缩策略应该可配置**：不同任务的最佳压缩策略可能不同。允许通过配置文件调整触发阈值、策略类型和关键信息保护规则。

## 面试高频问题

### Q1: Context Compaction 什么时候触发？触发条件是什么？

**A**: 通常在 Context Window 的 token 使用率达到 80% 左右时触发。触发后会执行压缩策略，目标是把使用率降到 50% 左右。选择 80% 而不是 100% 是因为要给下一轮的工具结果和模型输出留出余量——如果 100% 才触发，下一轮可能直接溢出报错。选择 50% 作为目标是因为需要一次释放足够多的空间（30%），避免频繁触发压缩。压缩太频繁有两个问题：一是增加不必要的 LLM 调用成本，二是信息逐轮损耗严重（"传话游戏"效应）。

### Q2: Context Compaction 一定会导致模型丢失重要信息吗？如何缓解？

**A**: 一定会导致信息损失，这是信息论的必然结果。但可以通过以下策略将损失降到最低：（1）使用选择性丢弃而非全量摘要——关键信息保留原文，只丢弃或摘要化低价值内容；（2）维护"永不丢弃"列表——系统 prompt、任务目标、用户约束、待办事项等关键信息绝不被压缩；（3）结构化摘要——用固定格式（目标、已完成、待办、关键文件）生成摘要，减少信息遗漏；（4）减少压缩频率——用 80/50 阈值而非每轮压缩。核心原则是："压不压缩"不是问题，"哪些信息绝不能丢"才是关键设计决策。

### Q3: 在 RL 训练的 rollout 中，Context Compaction 会带来什么特殊问题？

**A**: 三个核心问题。第一，轨迹完整性被破坏——RL 训练需要完整的 (state, action, reward, next_state) 序列，压缩会改变 state 的内容，导致同一条轨迹在不同压缩策略下可能产生不同的训练效果。第二，Reward 可追溯性受影响——如果某步的 reward 依赖于被丢弃的 context 信息（比如模型在第 5 轮发现了一个约束，但第 15 轮被压缩掉了），后续的 reward 信号就变得难以解释。第三，策略评估偏差——训练时的压缩策略和推理时的压缩策略如果不一致，会导致 train-test mismatch。因此，训练阶段建议尽量不压缩（用 SubAgent 拆分长任务），如果必须压缩则使用行为可预测的滑动窗口策略。

### Q4: 如果 Context Window 很大（比如 1M token），Context Compaction 还重要吗？

**A**: 仍然重要，原因有三个。第一，成本——即使窗口很大，每轮 API 调用的费用仍与 token 数量成正比，压缩可以降低成本。第二，注意力稀释——研究表明，即使模型在技术上能看到完整的 1M context，它对中间位置信息的关注会显著降低（"Lost in the Middle"现象），压缩可以通过保留关键信息来缓解这个问题。第三，延迟——更长的输入意味着更慢的推理速度，压缩可以改善用户体验。用一句话概括：Context Compaction 解决的不是"能不能装下"的问题，而是"装太多会变差"的问题。
