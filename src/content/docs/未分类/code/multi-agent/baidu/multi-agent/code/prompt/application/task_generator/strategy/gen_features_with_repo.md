# 任务目标

充分考虑业务逻辑、代码库职责与交互边界，分两步完成 策略方向 功能点设计：

1. 先基于需求点提炼功能点（遵守单库拆分约束，确保可独立开发、上线、验证）；
2. 再结合代码库职责为每个功能点分配所属或协作的仓库。

# 步骤说明

## 第一步：功能点拆分（核心）

### 拆分思路

从用户故事中提炼 策略方向 功能点，每个功能点必须具备：

- 独立上线、独立验证的能力；
- 完整的输入 → 处理 → 输出逻辑闭环；
- 明确的系统响应行为。

### 拆分约束

1. **复杂度判断**

   - 简单需求：仅涉及单一系统行为 → 输出 1 个功能点；
   - 复杂需求：涉及多个阶段或状态流转 → 输出 2 ～ 4 个功能点。

2. **拆分原则**

   - 聚合同类用户故事形成业务功能点；
   - 避免非职责内容：UI 细节、用户交互等
   - 避免过度拆分：配置修改、实验逻辑不得单独成点；
   - 若逻辑强耦合（如弹窗与奖励绑定）→ 合并为同一功能点；
   - 若逻辑可独立上线（如任务创建与上报）→ 拆为独立功能点；
   - 仅保留 策略方向 核心责任，忽略统计类或云控类描述。

3. **阶段聚合参考**
   参数解析（DMP+传参） → 实验判断（可选） → conf匹配（实验sid、活跃度） → 数据组装下发

4. **输出顺序约束**
   - 核心逻辑优先；
   - 条件/触发逻辑其次；
   - JSON 数组顺序需符合依赖顺序。

## 第二步：仓库分配（结合职责）

### 匹配优先级
请按照以下优先级判断需求是否涉及到不同的仓库：
1. 如果需求内容中没有明确提到"目标人群"字样及相关语义，则认为不涉及`baidu/uts-strategy/incentiveauthorize`仓库的开发工作
2. 如果需求内容中没有明确提到"策略"、"策略逻辑"、"奖励数值"、"增发减发"等字样及相关语义，则认为不涉及`baidu/explorer/jst`仓库的开发工作
3. 否则，请自行根据"仓库职责匹配"识别

### 仓库职责匹配
结合输入的代码库职责，判断每个功能点的实现归属与协作方式：
1. **单库负责型**：功能点逻辑完整地在一个仓库实现，`linkedRepos` 仅包含一个条目；
2. **多库协作型**：功能点涉及跨仓库写作，共同完成一个需求或者功能，`linkedRepos` 包含多个条目；

# 输出格式

- 严格遵守以下 JSON 格式输出，禁止输出额外解释
- 注意字符串内引用使用单引号，避免 JSON 无法解析

```json
[
  {
    "idTag": "格式：功能点{N}，示例：功能点1",
    "featureName": "功能点名称（<=10字）",
    "featureDesc": "功能点概述（<=30字）",
    "linkedStories": ["挂载的需求点标签，示例：需求点1"],
    "acceptanceCriteria": [
      // 用户故事对应验收标准，严格遵守EARS 格式
      "[序号]. 当 [事件] 发生时，系统应当 [响应]",
      "[序号]. 如果 [前置条件] 成立，系统应当 [响应]",
      "..."
    ],
    "linkedRepos": [
      {
        "iCodePath": "关联的代码库",
        "relation": "PRIMARY | SECONDARY | CROSS",
        "reason": "分配的理由",
        "acceptanceCriteria": [
          // 代码库需要承接的验收标准，严格遵守EARS 格式，覆盖完整细节无遗漏
        ]
      }
    ]
  }
]
```

# 自检要求

输出前请确保：

- 功能点数符合复杂度约束（简单 ≤2，复杂 ≤4）；
- 每个功能点具备可独立上线与验证能力；
- 强耦合逻辑已合并，未遗漏关键交互；
- 仓库分配符合职责边界与时序依赖；
- 输出为有效 JSON 数组，无额外解释文本。
