## 分析目标

从代码库中提取以下信息，形成结构化知识图谱：
- **业务场景**：主要功能模块及其逻辑范围
- **核心逻辑列表**：每个场景下的核心逻辑特性（如：含接口的场景按照接口进行组织）、功能描述和代码入口
- **通用能力**：存储对象（数据库、缓存）、下游服务（微服务、消息队列、第三方API）
- **调用关系**：业务核心逻辑（如：业务场景接口）与存储、服务的调用关系
- **交互时序**：核心逻辑（如：接口）调用链路及顺序

### 任务1：识别业务场景

识别线索（以有接口的业务场景为例）：
- 目录结构：如 src/user/, internal/task/, services/order/
- 路由前缀：如 /api/v1/user, /api/v1/task
- Service/Handler命名：如 UserService, TaskService
- 输出格式如下：
```markdown

|---------|---------|---------|---------|---------|
| <接口名称> | <HTTP方法+路径> | <功能说明> | <Service/Handler方法> | <文件名> |
| ... | ... | ... | ... | ... |
---
> 场景差异说明（仅当存在与其它场景高度相似时必填）：
> - 相似场景：<另一个场景名>
> - 差异点：<列出 2-5 个关键差异，如业务场景、权限、数据粒度、同步/异步、事务边界、SLA 等>
> - 核心中英文关键词：<关键词1, 关键词2, 关键词3,......>
```

## 输出要求

1. **只提供定位锚点**，不输出实现代码
2. **目录级精度**，如 `services/user/` 而非具体行号
3. **相似场景对比**：对容易混淆或高度相似的场景必须提供差异化说明（至少 1-3 点）。
4. **结构化表达**，使用表格和简单的文本时序图
5. **完整覆盖**，确保所有场景、接口、存储、服务都记录
6. **保持简洁**，重点是"是什么"和"在哪里"，不是"怎么做"
