# 任务目标

根据输入的第三方信息和需求详情，理解需求内容，采用 EARS 语法 生成对应的用户故事与验收标准，用于 PM 与 RD 的需求澄清。

# 生成约束

1. 严格基于输入需求

- 不得引入文档未明确说明的功能、角色或场景。
- **对需求内容进行逐行扫描，任意一行包括配置、实验、业务变更等明确业务描述内容，则必须在输出对应的用户故事或验收项，避免遗漏隐含要求**。
- **若需求中未明确提及的任务或操作，不生成对应的用户故事或验收标准**。

2. 合理拆分需求点

- 属于同一交互链路或高度相关的子行为，应合并为单个“需求点{N}”，在该需求点下列出必要的子验收项（acceptanceCriteria），确保前后条件可追溯。
- 对于实验类需求，处理原则如下：
  - **若文档仅提及“实验”、“灰度”或“可选”但未明确启用条件或实现细节，则视为未启用状态，不生成独立实验需求点**；
  - 若文档明确说明实验已启用或具备具体逻辑，需明确实验需求点，保持需求结构的完整性与可追溯性。
- 统计、配置或独立管理类需求，其职责与验收互不依赖，可拆分为单独的需求点。
- 仅在明确独立（职责和验收标准互不依赖）时，才拆分为多个需求点，以避免过度碎片化。

3. 需求细节完整可还原

- 验收标准必须严格遵守指定 EARS 语法格式。
- 验收标准应覆盖需求中明确的所有条件、分支、展示内容和异常场景，确保输出可完整还原与追溯。
- **所有在原始需求中出现的可验证行为、展示逻辑或业务约束，均不得遗漏**。
- **对于以表格、字段列表、配置项枚举等形式给出的需求内容，应按“逐条业务约束”处理**：
  - 输入中的每一行、每一个字段、每一种取值，均需在验收标准中体现其对应的触发条件、影响范围或展示结果；
  - **不得通过“统一规则”“整体逻辑”或上位概念对多条内容进行合并、概括或替代**；
  - 仅当原文明确声明“内容等价 / 仅为示例 / 不区分处理”时，才允许合并表达。
- 若需求中给出了字段示例值（包括 JSON 示例、返回样例），则该值必须作为验收标准的一部分直接写出，否则视为不完整。

# 输出格式

- 严格遵守以下 JSON 格式输出，禁止输出额外解释
- 注意字符串内引用使用单引号，避免 JSON 无法解析
- 若无任何有效内容，输出 `[]`，**但前提是需确保已逐行扫描确认无遗漏**

```json
[
  {
    "idTag": "格式：需求点{N}，示例：需求点1",
    "storyName": "用户故事名称（<=10个字）",
    "userStory": "用户故事，格式：作为 [角色]，我想要 [功能]，以便 [收益]",
    "acceptanceCriteria": [
      // 用户故事对应验收标准，严格遵守EARS 格式
      "[序号]. 当 [事件] 发生时，系统应当 [响应]",
      "[序号]. 如果 [前置条件] 成立，系统应当 [响应]",
      "..."
    ]
  }
]
```

# 反思修复

在输出前，请进行自检，确保以下三项全部满足：

- 格式遵守：输出严格符合指定 JSON 结构，无多余文本或注释。
- 需求还原：用户故事与验收标准能够完整对应原始需求**所有行中可验证的行为或约束**，细节未遗漏或曲解。
- 不臆造：未引入任何输入中未明确提及的功能、角色、操作或场景，**特别注意禁止引入未明确说明的实验需求**。

若发现不满足，请自动修正后再输出最终结果。
