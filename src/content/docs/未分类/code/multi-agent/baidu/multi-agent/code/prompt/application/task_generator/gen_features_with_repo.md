# 任务目标

充分考虑业务逻辑、代码库职责与交互边界，分两步完成 Server 功能点设计：

1. 先基于需求点提炼功能点（遵守单库拆分约束，确保可独立开发、上线、验证）；
2. 再结合代码库职责为每个功能点分配所属或协作的仓库。
   - 若职责清晰，则直接给出确定分配结果；
   - 若职责无法确定，则在输出中**显式标记需要进一步深入分析**，并说明不确定性来源。

# 步骤说明

## 第一步：功能点拆分（核心）

功能点拆分需结合**需求语义与代码库职责/交互边界**综合判断，作为后续职责分配的基础。

### 拆分要求
从用户故事中提炼 Server 端功能点，**仅在必要时拆分**。每个功能点必须同时满足：
- 具备**独立上线、独立验证**的能力；
- 构成完整的 **输入 → 处理 → 输出** 逻辑闭环；
- 对外表现为**一个完整、可感知的系统行为**，而非行为片段。

### 拆分原则
- **以职责完整性为拆分边界**：  
  - **仅当一段逻辑天然构成独立职责单元时**，才允许拆分为独立功能点；
  - 且需**同时满足以下条件**：
    1. 在代码层面可形**成稳定、清晰的调用边界**；
    2. 拆分后**不会引入跨功能点的强同步依赖或状态耦合**；
    3. 可在**不依赖其他功能点内部过程或中间状态**的情况下完成独立验收；
  - 单一判断、校验、分支、规则计算或中间处理步骤，**不得单独拆分为功能点**；
- **存在强耦合时禁止拆分**：若逻辑在业务语义、执行时序或结果一致性上**必须协同存在**，应合并为同一功能点；
- **实现细节不成点**：UI 展示、配置形式、实验开关、参数差异等**仅作为功能点的实现细节或生效条件存在**，不得拆分为独立功能点。

> 拆分存在歧义或需要额外假设才能成立时，**默认选择合并**，
> 以确保功能点在语义、职责与验收层面均可整体归属、整体理解、整体验收。

### 顺序约束
拆分完成后的功能点，需按真实开发与运行依赖顺序输出，而非按描述顺序或重要性排序：
- 承担底层能力 / 核心业务逻辑的功能点优先；
- 承担业务编排、聚合、状态流转的功能点其次；
- 以 UI、展示、通知、弱依赖或末端交互为主的功能点最后；
> 功能点在 JSON 数组中的顺序需真实反映依赖与调用方向，不得仅按名称或主观重要性排序。

## 第二步：仓库分配（结合职责）

结合输入的代码库职责，判断每个功能点的实现归属与协作方式：

- **单库负责型**：
  - 功能点的完整执行链路（包括前置处理、核心逻辑、后置行为）均在一个仓库内完成；
  - `linkedRepos` 仅包含一个条目，且该仓库在运行时**不依赖其他仓库参与该功能点的调用链**；
- **多库协作型**： 
  - 功能点在运行时存在跨仓库调用或被调用关系；
  - `linkedRepos` 中**必须按真实代码调用 / 事件触发 / 依赖发生的时序顺序**列出所有参与仓库，包括但不限于：
    - 前置校验 / 配置 / 策略判断仓库；
    - 核心业务逻辑仓库；
    - 编排、聚合、状态流转仓库；
    - 事件发布、异步任务、通知等后置仓库；
- **主从依赖型**：
  - 主仓库承担该功能点的核心业务决策与状态变更，从仓库仅提供被调用能力或数据支撑；
  - `linkedRepos` 中仍需**完整保留主从仓库的时序顺序**，不得因“辅助性质”省略从仓库。

**时序完整性约束**：
  - `linkedRepos` 的排列顺序必须严格等价于该功能点在真实运行时的仓库交互顺序；
  - `linkedRepos` 必须覆盖运行过程中所有实际参与交互的仓库，**包括仅承担前置、编排或后置职责的辅助仓库，不得省略**。

> 若当前输入信息不足以明确判断仓库职责边界，**仍需给出当前阶段的最合理分配方案，但必须标记需要进一步深入分析**。

# 输出格式

- 严格遵守以下 JSON 格式输出，禁止输出额外解释
- 注意字符串内引用使用单引号，避免 JSON 无法解析

```json
{
  // 当前需求与代码库职责的映射是否清晰

  "isNeedDeepThink": "0｜1",
  // 不确定性的来源说明（仅在 isNeedDeepThink = 1 时重点说明）
  "reason": "简要说明职责不清晰的原因，如职责重叠、边界模糊、信息不足等", 
  // 当前阶段可给出的功能点与仓库分配结果

              // - 覆盖该仓库承担的全部关键职责，不得遗漏；
```

# 反思与修复

**在最终输出前，必须对结果进行一致性校验与必要修复**，确保：

- 每一项职责分配均可在对应代码库的知识索引中找到明确依据；
- 功能点拆分不过度、不遗漏，能够完整覆盖需求中的关键系统行为；
- 功能点与代码库的输出顺序真实反映依赖与阶段关系；
- 输出的 JSON 结构完整、字段齐全，且**可被严格解析**；
- 不存在职责缺失、仓库重复、角色混淆或语义冲突的情况。
