# 任务目标
基于输入的需求点及其验收标准等信息，提炼出 策略 端开发需要关注的功能点，要求每个功能点具备 可独立开发、上线、验证 的特征，并能完整描述系统行为与响应逻辑。

## 需求复杂度解析
**在功能点拆分前，先判断需求复杂度**：
- 简单需求：整体逻辑单一，仅涉及一个系统行为 → 输出 1 个功能点。
- 复杂需求：涉及多个系统阶段、状态流转、条件判断或依赖关系 → 输出 2 ～ 4 个功能点。

## 功能点拆分原则
- 将多个用户故事聚合为功能需求点。
- 功能点定义原则：
  1. 功能点是**独立的业务能力**，必须能单独上线或验证。
  2. 避免过度拆分：
     - UI 细节（如文案、图标）仅作为功能点的说明，不单独作为功能点。
     - **实验需求必须融入现有功能点作为分支判断条件，不得单独定义为功能点**。
       - 若需求文档中提到“实验/AB 测试”，应合并进对应的功能点，应在对应功能点的 `acceptanceCriteria` 中以条件句形式体现。
       - 禁止出现独立的 “实验功能点” 或 “实验控制逻辑功能点”。
     - **忽略与策略业务逻辑开发无关的需求，如打点上报/埋点统计/需求收益等需求描述，直接跳过**，不在功能点中体现。
  3. 耦合与交互处理：
     - 若功能点之间逻辑上存在强交互或依赖，需合并至同一功能点，以保证数据交互链路完整。
     - 若功能点逻辑可独立运行，则应拆分为不同功能点，避免不必要的耦合。
  4. 每个功能点需体现 **策略 端的核心责任**（如接口变更、奖励金额值、金额类型、到款账户、冷却时间等），避免只描述前端 UI或者其他开发方向的职责内容。

## 功能点输出顺序约束
- 核心逻辑优先：涉及系统底层处理或核心业务行为的功能点先输出。
- 条件/触发逻辑：依赖实验、灰度、AB 测试等触发条件的功能点次之。
- 禁止UI/交互：UI/交互类的内容与策略无关，禁止输出
- JSON 数组顺序必须严格遵守以上规则，保证开发依赖清晰。

# 输出格式
- 严格遵守以下 JSON 格式输出，禁止输出额外解释
- 注意字符串内引用使用单引号，避免 JSON 无法解析

```json
[
  {
    "idTag": "格式：功能点{N}，示例：功能点1",
    "featureName": "功能点名称（<=10字）",
    "featureDesc": "功能点概述（<=30字）",
    "linkedStories": ["挂载的需求点标签，示例：需求点1"],
    "acceptanceCriteria": [
      // 用户故事对应验收标准，严格遵守EARS 格式
      "[序号]. 当 [事件] 发生时，系统应当 [响应]",
      "[序号]. 如果 [前置条件] 成立，系统应当 [响应]",
      "..."
    ]
  }
]
```

# 反思与修复（输出前自检）
在输出前，必须完成以下自检与修复，仅输出最终正确的 JSON 结果：
- **功能点数符合复杂度约束（简单 ≤2，复杂 ≤4）**；
- 每个功能具备独立开发、上线、验证能力；
- **强耦合逻辑已合并，避免错误拆分或遗漏**；
- 功能点 JSON 按 核心逻辑 → 条件/触发 顺序输出。
- 保证每个流程包含输入、处理、输出的完整闭环。
- 确保需求点完全还原，验收标准覆盖原始输入。

若发现不符合项，须先修正后再输出最终结果。
