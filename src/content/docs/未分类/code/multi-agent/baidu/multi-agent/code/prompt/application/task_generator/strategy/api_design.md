# 识别流程参考
## 一、任务类型识别与分支逻辑

在进入接口挂载与变更设计前，需先识别需求类型：

1. **接口类需求（优先处理）**
- 涉及接口请求参数、响应结构、接口逻辑或核心业务处理流程变更；
- 任何可通过接口实现或扩展的逻辑，**均应输出为接口变更项**；
- 输出需包含接口路径、请求方式、参数变更、逻辑变更文件及任务列表。

2. 脚本类 / 逻辑类需求（**仅当无接口变更时使用**）
- 适用范围：
* 不涉及接口定义或交互逻辑，仅限内部脚本、定时任务、批处理、数据修复、配置调整等类型。
- 接口相关规则：
  - 若存在可关联的接口，应优先输出**关联度最高的接口基础信息**；
  - 仅在确无任何关联接口时，uri、method、relation 等字段使用 "NA" 占位。
- 代码变更项：
  - 输出涉及的代码文件路径与逻辑变更内容（`todoCodeList`）；
  - 若无接口参数变更，但存在底层结构（如 AMIS、DMP、配置结构体等）的字段调整，应以 **JSONC** 格式 在 `response` 字段中体现具体操作对象及字段变更。

* **保持结构一致，便于统一存储与追溯**。

> **判断优先级：**  
> 若需求中既可通过接口调整实现，又可通过脚本实现，需**优先输出接口变更方案**，脚本仅作为无接口变更时的替补实现手段。

## 二、**接口精筛与挂载**

针对每个功能点，逐一分析候选接口，并明确其在业务流程中的位置，以及与功能点的关联程度，完成功能点到接口的挂载。

- **步骤说明**

（1）**功能点遍历与接口校验**

遍历每个功能点，基于验收标准、输入输出及业务逻辑明确其预期系统行为。

（2）**接口关联判断维度**

针对每个候选接口，从以下三个维度评估与功能点的逻辑关联：
  - 输入输出契合度：接口的参数及返回值是否匹配功能点的业务输入/输出要求。
  - 逻辑实现一致性：接口核心逻辑实现是否已覆盖功能点的目标逻辑。
  - 上下游依赖关系：接口在业务流程中的位置是否符合功能点的处理顺序和依赖。

（3）**筛选结果分类**
- 根据评估结果将接口归类为：
  - `CORE`：核心接口，承载主要功能逻辑，必需变更。
  - `PARTIAL`：部分相关接口，仅涉及辅助或部分逻辑，可选择变更。
  - `NONE`：不相关或无需参数/逻辑变更，可剔除。

---

- **挂载约束**
  - 每个功能点理论上需挂载至少一个明确相关接口，如果没有挂载接口请给出明确理由；
  - 保留逻辑相关但变更不确定的接口，避免遗漏；
  - 同一接口尽量只挂载在一个功能点下，除非确有多职责情况。

# 反思与修复

- 校验输出的合理性与准确性，确保接口挂载与功能点对应正确。
- 确保接口变更设计遵循“优先复用、最小改动”原则。
- 保证变更设计无遗漏，功能点的验收标准得到完整覆盖。
- 输出必须为严格符合 JSON 标准的文本，可直接解析。
- **若字符串中存在字符引用，请使用转义后的双引号\"**.
- 输出字段名称、层级、类型与预定义结构一致，不得遗漏、拼写错误或新增未定义字段。
- 若发现接口挂载错误、结构不符或格式解析失败，应及时修正并重新生成结果。
