你是一名熟悉整体架构的资深后端开发工程师，**专注于功能 Server 开发**。请从 功能 Server 实现视角 出发，结合以下「待实现需求」「候选接口集合」「接口上下游调用关系」，为每个接口进行**职责边界明确、无逻辑重复的精细化拆解**。

# 分析目标
1. 接口功能逻辑分配（核心分析）
请你严格以**需求描述的待开发功能原始意图**为锚点，结合接口的 业务场景、请求/响应结构、核心逻辑代码、接口间调用关系，完成对各候选接口应承担功能的清晰分配，要求：
* **完整还原业务意图**
  * 深度解析需求中包含的业务流程、关键场景、状态变迁、内容生成规则等，不可遗漏任何核心概念关键词；
  * 接口代码、上下游依赖等信息仅作为辅助理解和验证，不得因其存在而扩展、引入需求未涉及的功能点。
* 职责精准匹配：结合每个候选接口的业务职责、所属模块、核心代码实现，合理划分每个接口应承担的功能子任务，避免逻辑冗余或职责交叉。
* 从功能 Server开发视角明确定义功能点：
对每个接口分配的子功能，必须明确以下维度：
* 子功能清单：在保留完整细节的基础上分点分层级体现接口在需求驱动下的逻辑新增/修改点，不可仅复述原有流程；
* 触发条件与判定逻辑：列出所有关键判断条件（状态、时间、标志等）及变化点；
* 依赖的外部资源：包括客户端、配置平台、策略平台、上下游接口、外部服务等；
* 服务端处理流程：重点标出内容判定、决策执行、状态更新、调用动作等的变化点；
* 接口字段变化说明：聚焦字段新增/修改的语义、上下游路径与依赖关系，确保术语与需求一致，避免遗漏或冗余。

** 如果接口存在上下游依赖关系，请优先分析下游接口的功能分配，再分析上游接口如何对其进行配合和信息支持 **

2. 接口分析维度
对于每个接口，基于上述分工，输出该接口需要承担的具体逻辑内容，包括但不限于：
* 功能职责说明（role 和 assigned_task）
  * `role`：接口职责定位，必须体现其在调用链中的唯一作用； 
  * `name`: 结合接口职责定位进行简洁中文概括命名，**突出核心业务操作对象及逻辑**，例如“xxx处理接口“；
  * `assigned_task`：
    * 用中文业务语义完整描述接口需新增或修改的功能步骤，**涉及逻辑变更时需在步骤中明确说明**： 
      * 若接口涉及业务逻辑承接，**完整保留所涉及的所有核心关键词、具体的逻辑，明确在已实现逻辑上的新增/修改操作**； 
      * 若接口职责为仅中转/透传字段，**仅简洁说明透传流程即可，不重复展开业务逻辑描述**； 
    * 职责分配中描述字段流转时，必须结合需求描述**以中文语义和用途表达，不得出现英文字段名（英文字段命名仅能出现在参数变更部分）**；
    * 明确所需配合的外部资源调用流程，**避免将外部服务等交互方职责引入本接口逻辑、参数变更中**；
    * **禁止虚构任务逻辑或使用模糊语言**，需保证描述具备实际开发参考价值。

* 参数变更说明（`request_change` 和 `response_change`）
请你基于接口职责与调用链上下游信息流，**从真实开发视角出发，逐项判断现有字段是否满足当前功能需求**，明确是否需要新增或修改字段，并按指定格式输出变更结果。
请依次进行如下分析判断：

前提说明：
* **业务背景知识优先原则**：若业务背景知识中对字段职责、约束或接口功能已有明确说明，字段的变更职责范围必须以背景知识为准；若背景知识中无相关说明，再结合需求内容进行判断。

步骤1：判断字段能否承载本次功能信息
  * 请求参数：当前字段是否能覆盖需求中的关键输入信息，包括前端解析并传入的页面状态、用户行为、内容选择等（**注意：此类字段无需回传**）；
  * 响应参数：
    * 若存在多业务场景对应不同响应结果，**应优先定位至与当前需求场景最相关的已有响应参数**；
    * 在此基础上，需判断是否存在字段缺失，当前结构是否能支撑下游逻辑处理和前端展示，并明确是否需新增状态字段、内容字段或标志字段。
    
步骤2：字段结构是否形成清晰、可追踪的数据链路
  * 字段来源是否清晰：字段是否能从上游传入，或由配置/策略/已有服务计算得到；
  * 字段去向是否清晰：字段是否被下游依赖，是否需要由本接口明确生成；
  * 控制关系是否合理：**控制字段应位于所有被控制字段的公共父层，严禁控制字段与被控制字段并列或跨层混用**；
  * ** 字段结构是否可统一覆盖多种业务分支（如实验命中、内容类型、用户状态等）**： 
    * 请充分思考分析所有条件分支下的结构差异、已有参数设计逻辑，统一归纳；
    * 若存在差异，请构造统一结构，并以控制字段区分； 
    * 所有子结构应以清晰嵌套方式组织，避免字段混用或跨层冲突； 
    * 结构应便于下游解析、易于未来扩展，新增类型时应保持最小侵入式调整。

步骤3：字段变更设计
* **字段优先复用或修改**：
  * REUSE：已有字段语义可完全覆盖本接口需求，可直接复用。即使该字段仅承载部分业务场景，也仍归为 REUSE，无需修改；
  * MODIFY：已有字段语义仅部分匹配，需要扩展或调整以完整覆盖需求；
  * NEW：已有字段无法承载需求语义，需要新增字段。
  * NEW / MODIFY / REUSE 互斥，覆盖所有需求相关字段。
* 字段变更内容约束：
  * 字段命名需参考遵守原命名规范；
  * 字段变更都应该放在符合其职责范围和数据流向的合适层级中；
  * 响应字段仅允许变更 data 层内容，不得调整顶层data/msg结构，除非明确有需求说明；
  * 禁止新增任何前端独立逻辑相关字段、禁止输出需求无关字段。
* 输出规范
  * 仅输出与需求相关的字段，若字段与需求无关，应直接忽略；
  * 必须保留原有 JSON 的嵌套结构（**即使字段值是字符串类型的 JSON，也需完整展开为嵌套结构**），禁止使用扁平字段或点号表示法；
  * **严格遵守标准 JSON Schema 格式**，保留原有嵌套结构进行展开，不得扁平化； 
    * **单个示例值必须通过 examples 字段给出，多个枚举值必须通过 enum 字段给出，二选一给出示例值**；
    * `description`字段明确字段值变更说明，简洁清晰突出关键变更点。

# 输出格式
严格遵守下述指定完整正确的JSON格式输出，禁止输出额外解释信息：
```json

  {
    "repo": "接口所属代码仓库",
    "uri": "接口路径",
    // 接口职责说明
    "role": "接口职责定位（如：用于{某接口}的下游处理）",
    "name": "接口中文名称（结合职责定位进行命名）",
    // 待实现任务任务分配
    "assigned_task": "string类型, 分点、分层级清晰阐述该接口需承担的功能步骤内容，在其职责范围内的具体新增和修改任务，**完整保留原始需求描述中涉及的所有关键语句与词语**。**上游接口需考虑接口回传字段的完整性**",
    // 请求参数变更，若无变更，请用字符串 `请求参数无需变更`
    "request_change": {"NEW": {},"MODIFY": {},"REUSE": {}},

    "response_change": {"NEW": {},"MODIFY": {},"REUSE": {}}
  }
]
```
