# 任务目标

根据输入的需求文档，先提取用户故事，再聚合为功能点，并在功能点层面生成验收标准与完整的业务流程图（flowchart），用于接口职责分配。

**核心要求**：

1. 用户故事提取

- 必须严格基于输入需求生成，不得引入文档未明确说明的功能、角色或场景。
- 验收标准使用 EARS 语法，必须覆盖所有条件、分支和场景，并保留需求中明确的展示内容等信息，确保需求可完整还原与追溯。
- 若需求中未明确说明的任务或操作，不生成用户故事或验收标准。

2. 功能点拆分

- 将多个用户故事聚合为功能需求点。
- 功能点定义原则：

  1. 功能点是**独立的业务能力**，必须能单独上线或验证。
  2. 避免过度拆分：

     - UI 细节（如文案、图标、顺序）仅作为功能点的说明，不单独作为功能点。
     - 实验需求仅作为现有功能点的补充条件，不得单独定义为功能点。若需求文档中提到“实验/AB 测试”，应合并进对应的功能点，作为触发条件或分支逻辑描述。
     - 配置类需求（如任务规则、文案、开关、奖励参数）由运营在配置平台完成，不单独生成 Server 功能点，但若配置相关内容变更影响 Server 逻辑（如任务状态流转、接口返回或业务规则校验），需在功能点验收标准中体现 Server 责任。
     - **忽略与客户端业务逻辑开发无关的需求，如打点上报/埋点统计等统计类需求描述、云控配置等配置类需求描述内容，直接跳过**，不在功能点中体现。

  3. 耦合与交互处理：

     - 若功能点之间逻辑上存在强交互或依赖（如前后端紧密绑定、弹窗与奖励领取绑定），需合并至同一功能点，以保证数据交互链路完整。
     - 若功能点逻辑可独立运行（如“任务下发”和“任务完成上报”），则应拆分为不同功能点，避免不必要的耦合。

  4. 按“业务流程阶段”来聚合：**任务创建/下发 → 任务执行 → 任务完成/上报 → 后续弹窗/奖励**，每个阶段定义一个功能点。
  5. 每个功能点需体现 **Server 端的核心责任**（如接口、任务状态流转、依赖调用），避免只描述前端 UI。

- 每个功能点需包含：

  - 功能点 ID 与名称
  - 功能点描述（从 Server 工程师视角总结，不写成 UI 设计需求）
  - 关联的用户故事 ID
  - 功能点聚合验收标准（覆盖所有关联用户故事的条件、分支和场景，并保证细节信息完整需求可还原）

- **功能点输出顺序约束**：
  1. 基础功能优先（认证、权限等底层能力）
  2. 独立功能次之（不依赖其他功能的模块）
  3. 依赖功能最后（需调用其他功能的复合业务）

3. 交互流程图（flow）

- 必须在功能点层面生成完整流程，覆盖输入、处理、输出及系统响应。
- 一个功能点对应的流程图必须完整、一体化，保证逻辑不割裂。
  - actor: 枚举值（USER/FRONTEND/BACKEND）
  - type: NORMAL 常规节点，DECISION 判断节点
- 总节点个数不超过 15 个。

**输出约束**：

- 功能点清晰独立，层次结构明确。
- 功能点拆分粒度避免过细导致逻辑链路断裂，**简单需求拆分个数<=3，复杂需求拆分个数<=5**。
- 严格基于输入文档展开，**禁止引入未明确说明的功能、角色或场景**。
- 输出需保持层次清晰、语义明确，可直接作为接口职责分配的输入。
- 所有内容需保持纯中文语义描述，用自然语言准确表达系统行为和预期结果，**禁止生成任何未在原文中出现的英文变量名、字段名或接口名**。
- 所有验收标准必须包含详细信息，覆盖功能点或场景中涉及的所有关键信息（标题、文案、提示语、按钮/弹窗内容、奖励说明、条件分支等），确保需求可完整还原。

**反思与校验**：

- **输出内容必须自检**，确保严格遵循输出约束，不遗漏涉及的关键信息、逻辑自洽且完全符合原始文档意图。
