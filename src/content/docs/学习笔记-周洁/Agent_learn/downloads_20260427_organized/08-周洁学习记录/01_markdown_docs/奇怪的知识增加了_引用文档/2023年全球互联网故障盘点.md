2023年全球互联网故障盘点

**副标题：如何应对不确定性**

2023年的互联网世界故障不断，“XXX 崩了”频频登上热搜。这些故障的原因五花八门，大多数是由突发、不可预测的事件引起的。这些故障不仅给用户带来了不便和困扰，也暴露了线上服务在应对**突发事件**方面的薄弱之处。我们应该如何去**应对不确定性**，并真正在业务场景中做好高可用，这是本文想跟大家探讨的问题。

# 一、故障回顾
跟大家回顾一下2023年有代表性的故障事件：

[流程图]
## 1）2023-01-25 微软Azure全球大瘫痪
故障时间：2023-01-25 07:05～12:43 故障时长5小时；

故障影响：云平台Azure、Teams和Outlook等服务瘫痪，影响全球数百万用户；

故障原因：微软广域网（WAN）的设备发生问题，影响互联网上客户端与Azure之间的连接，以及数据中心服务之间的连接。

## 2）**2023-03-29 **腾讯广州机房**故障14+小时**
故障时间：2023-03-29 00:23～15:00 故障时长14+小时；

故障影响：微信、QQ 等腾讯旗下社交软件出现功能异常。微信包括语音呼叫、[账号登录](https://so.csdn.net/so/search?q=%E8%B4%A6%E5%8F%B7%E7%99%BB%E5%BD%95&spm=1001.2101.3001.7020)、朋友圈以及支付在内的多个功能无法正常使用，QQ 文件传输、QQ 空间、QQ 邮箱等也同样出现问题；

故障原因：广州电信机房制冷系统故障。

故障影响：谷歌区域控制平面发生故障，一些云功能在全球范围内受到影响，如Cloud Console；

故障原因：谷歌欧洲西部9区（巴黎）集群因漏水引发火灾，不得不切断电源、关闭服务器。

故障影响：小红书的iOS版本出现大规模闪退问题，用户反映卸载重装也无法解决；

## 5）**2023-10-23 语雀服务重大故障**
故障时间：2023-10-23 14:07～22:00 故障时长近8小时；

故障影响：阿里旗下的在线文档服务品牌语雀发生重大服务故障，导致平台无法正常访问和使用；

故障原因：服务语雀的数据存储运维团队在进行升级操作时，由于新的运维升级工具 bug，导致华东地区生产环境存储服务器被误下线。受其影响，语雀数据服务发生严重故障，造成大面积的服务中断。

## 6）2023-11-02 Cloudflare 控制平面和分析服务中断
故障时间：2023-11-02 11:43～2023-11-04 04:25 故障时长超40小时；

故障影响：Cloudflare 的控制界面和分析服务中断。控制界面主要包括Cloudflare所有的服务（包括网站和 API）面向客户的界面，分析服务包括日志记录和分析报告；

故障原因：其位于北美的Flexential数据中心PDX-DC04的电源发生故障，整个机房服务不可用。由于部分关键服务（如Kafka）仅在PDX-DC04单机房部署，导致故障影响全部控制界面和分析服务。

![](/personal-site-mvp/img/doc-placeholder.svg "")
## **7）2023-11-12 阿里云控制台故障**
故障时间：2023-11-12 17:44～21:11 故障时长3.5小时；

故障影响： 阿里云云产品控制台访问及管控 API 调用出现异常、部分云产品服务访问异常，故障导致阿里云、淘宝、闲鱼、钉钉等几乎阿里全系应用都出现了问题；

故障原因（推测）：访问密钥服务 (AK）在读取白名单数据时出现读取异常，因处理读取异常的代码存在逻辑缺陷，生成了一份不完整白名单，导致不在此白名单中的有效请求失败，导致云产品控制台及管控 API 服务出现异常、部分依赖 AK 服务的产品出现异常。

![](/personal-site-mvp/img/doc-placeholder.svg "")
## **8）2023-11-27 滴滴大规模故障**
故障时间：2023-11-27 22:09～ 2023-11-27 07:31 故障时长9.5小时；

故障影响：事故发生时，上海、北京、广州等地滴滴出行 APP 无法使用，地图无法加载；

故障原因（推测）：在Kubernetes升级后系统出现了异常情况，在操作回滚过程中，发生了版本不兼容的错误，导致所有的Pod意外终止，随之整个集群服务出现异常。

# 二、故障原因分析
[流程图]
各公司公布的故障原因五花八门，有的故障是因为某地域 IDC 冷冻系统故障，有的故障是因为升级工具 bug 导致服务器被误下线，有的故障是因为 K8s 版本升级导致容器全部宕机……经过汇总，我们可以发现绝大多数的故障是由**突发的、不可预期的事件**导致的，这些故障暴露了线上服务在稳定性方面的风险，比如变更操作不规范、架构容灾能力不足、对关键服务存在单点依赖等。

随着互联网用户数量的不断增多，高流量带来的系统『**熵增****』**风险也在与日俱增。近年来，『**黑天鹅**』事件在每个领域都时有发生，导致各大型互联网企业似乎都要无时无刻地提防着这一突如其来的「不可抗力」。堵不如疏，黑天鹅事件的出现，看似毫无预兆、难以防范，但从架构和组织上，是否能够预防？我们就来聊聊如何**应对不确定性**，构建持续**高可用系统**。

# 三、如何应对不确定性
![](/personal-site-mvp/img/doc-placeholder.svg "")
应对不确定性，构建持续高可用系统是一个**系统化的工程**，从硬件到软件，从人员到机制，内容涉及组织内多部门协作、稳定性流程规范制定、体系化技术实现、质量意识宣贯等一系列工作结合。本文将围绕应对不确定性，结合持续高可用系统建设目标，给出**应对不确定性的关键路径**（如图所示）。

## 1）流程组织
应对不确定性，构建持续高可用的系统要花费很大的时间和精力，需要完善的流程组织保证在稳定性建设方面的**持续投入和支持**。一方面需要建设**稳定性保障机制**，包括规范编制、方案评审&Code Review机制、值班和责任奖惩机制、故障管理机制等；另一方面需要建设**组织保障能力**，涉及稳定性委员会设立、质量目标对齐等内容。以下是对一些关键内容的介绍：

* **规范编制**：稳定性工作，规范先行。制定代码编写规范、测试准入准出规范、变更规范、运维操作规范等，在研发、测试、运维等各阶段指导工作**规范化、标准化**进行；
* **评审机制**：系统的建设或改造方案需通过由业务、技术、测试、运维领域专家组成的专家团队评审，才能进一步实施；代码需要经过**Code Review**才可以合入，代码评审工作需要严格认真；
* **值班****机制**：设置**oncall值班**制度，每天有技术人员负责值班，能够对线上故障及时干预止损。故障结束后，由专家团队对问题进行详细分析，确定问题原因、明确责任团队，针于**质量红线问题**明确**奖惩措施**。
* **稳定性委员会**：集团各业务设立**稳定性委员会**，旨在保障百度的产品质量，重点工作包括制定产品服务稳定性的标准和规范、规划并开展产品服务的稳定性项目、组织产品服务稳定性事故调查处理和Casestudy等；
* **质量目标对齐**：稳定性工作贯穿软件生命周期的全过程，需要各团队方向对齐质量okr要求，明确产品的**质量目标**以及核心要求，质量目标可以通过评价指标实现**量化**。

## 2）技术保障
从技术的角度来说，问题永远可能发生，不能被彻底消灭，但是可以通过一系列技术手段，大幅度减少问题发生的概率。首先，具有多活容灾能力的架构是构建持续高可用系统的基石。其次，各种稳定性工程在维持系统高可用方面发挥着重要作用，这些工程与应对不确定性有紧密关系，如变更平台、混沌工程、架构感知、数字免疫、故障管理等。以下是对这些技术的简要介绍：

* **多活容灾**：多活容灾是一种系统设计和架构策略，它通过在不同地理位置或数据中心部署多个活跃节点，使系统在某一地点发生故障或灾难时能够迅速切换到其他节点，具备**快速恢复业务**的能⼒，保障业务的连续性和稳定性。多活容灾本质上提供**⾃上而下的流量隔离**能⼒，**故障爆炸半径可控**制在一个最小隔离单元内。
* **变更平台**：变更管理流程是确保系统稳定可靠的关键环节，数据显示70%的线上故障都是由变更发布引入的。为了降低变更带来的稳定性风险，需要完善各业务的**变更规范**，并且通过**平台化**的手段保障落地执行，以确保其持续性和有效性。变更平台的功能包括标准化审批、强制分级发布、强制分级拦截检查等。
* **混沌工程**：混沌工程通过主动注入随机故障，验证应用程序、基础架构或平台是否可以自我修复，**披露系统潜在风险**，并且故障不会对客户产生明显影响。 混沌工程旨在发现系统风险盲点（例如监控或自动伸缩技术），增强团队在故障发生期间的协作沟通能力。
* **架构感知**：架构感知系统通过网络连接、eBPF、日志、配置等多数据源共同作用**自动发现服务拓扑和架构风险**，实现了对系统架构的全面、实时的感知和管理。这不仅大大提高了系统架构管理的效率，也为企业提供了更加准确、全面的系统架构信息，有助于企业更好地进行业务决策和风险控制。
* **数字免疫**：数字免疫系统重点在于协助企业识别系统风险、推动风险闭环，保障稳定性能力的长期有效。从**基础能力的建设保鲜**，到上层**评价体系**的产出及场景化的应对能力结论验证，数字免疫系统建设了一套可持续的保障体系，打通了风险发现(感知)、风险闭环(治理)、数字评价(评价结论)的流程闭环。
* **故障生命周期管理**：无论是理论还是实践，均证明大的事故是由无数小的风险隐患累积导致的。故障生命周期管理通过对故障整个生命周期进行**平台化、规范化管理**，供团队从中汲取对稳定性提升有帮助的经验和有效手段，从预防、发现、定位、止损、复盘、演练多个阶段进行有效提升。

## 3）意识宣贯
端到端系统性地建设稳定性保障能力，除了关键的技术能力支撑外，人员意识建设也是不可或缺的重要环节。相较于技术能力，人员意识更容易出现生疏退化，如：误操作、通报滞后、漏检查、拦截误跳过等场景。人员的稳定性意识建设，主要围绕流程和意识的建设展开，重点在于通过**培训、考试、宣讲**等多种方式不断宣贯、强化。为了培养同学们的稳定性意识，我们应在日常工作中重视以下几个方面：

* 通过深入学习各种**高危操作、禁忌点**和过去事故的报告，增强同学们对稳定性的认识；
* 在工作中要始终关注稳定性指标，并严格遵循**变更流程规范**和**故障管理流程规范**；
* **定期考试**也是加强稳定性意识的重要方式，考试内容可以包括规范和历史线上事故的案例，以评估同学们对线上业务稳定性的理解和应对故障的能力。

# 四、总结
回顾2023年全球互联网的重大故障，思考一个终极的哲学问题：我们能否构建出永不出问题的系统？很遗憾，答案是“不能”。但是**应对不确定性**的挑战，我们可以通过系统化、工程化手段加强流程组织、技术保障和人员意识，构建高可用系统，减少故障发生的概率和损失。

在**流程组织**方面，我们着重建设稳定性保障机制和组织保障能力，从“团队、组织”层面保障稳定性建设。**技术保障**则包括多活容灾、混沌工程、数字免疫等一系列稳定性工程，从“技术”层面保障稳定性建设。在**意识宣贯**方面，通过培训、考试、宣讲等方式强化个人流程意识和质量意识，从“个人”层面保障稳定性建设。

这三个方面共同构成一个整体，持续保障系统稳定性建设。未来几期月刊，我们也会围绕如何应对不确定性，深入介绍数字免疫、故障生命周期管理、架构感知等技术内容，敬请期待。
