# unicode 与 emoji
## unicode 基础知识
Unicode （中文名：统一码/万国码. [WikiPedia: Unicode](https://zh.wikipedia.org/wiki/Unicode)）整理、编码了世界上大部分的文字系统。能够使用统一的字符集来处理和显示文字。

**每一个文字（/符号）有唯一的编号**（叫做**码位/码点，Code Point**），形如 A (U+0041)​、啊 (U+554A)​ （最高 6 位、最低 4 位前面补 0）的规则。（长一些的，比如 🤗 (U+1F917)​）

Unicode 目前划分成了 17 大组（叫做 平面（Plane））（[WikiPedia: Unicode字符平面映射](https://zh.wikipedia.org/wiki/Unicode%E5%AD%97%E7%AC%A6%E5%B9%B3%E9%9D%A2%E6%98%A0%E5%B0%84)）。分别是 0000-FFFF​, 10000~~-~~1FFFF​ ... F0000-FFFFF​ 和 100000-10FFFF​

### 编码方式
前面提到的 Unicode 是一种**字符集**，即将每一个字符与一个唯一标识（U+XXXX​）进行对应的集合。不同的字符集（如中文 GB 系列、繁中 BIG5 等），同一个文字有不同的编号。

而在实际使用中，出于**各种原因（编码效率、体积、适用范围等）** ，Unicode 字符集内的符号，是有不同的 **编码方式** （如 UTF-8​，UTF-16 LE/BE​ 等）来保存的

而 GB 系列、BIG5 等，既是字符集，又是编码方式。

‍

严格来说，现代的字符编码（[WikiPedia: 字符编码](https://zh.wikipedia.org/wiki/%E5%AD%97%E7%AC%A6%E7%BC%96%E7%A0%81#%E7%8E%B0%E4%BB%A3%E7%BC%96%E7%A0%81%E6%A8%A1%E5%9E%8B)）划分成了若干层次，每一层解决不同的问题。以 Unicode 为例

|层次|名称|解释|Unicode 例子|补充备注|
|-|-|-|-|-|
|第一层|抽象字符表 (Abstract character repertoire)|系统支持的所有抽象字符的集合，可以是封闭的或开放的。|Unicode 字符集，包含了各种语言和符号，如拉丁字母、汉字、表情符号等。例如，"A"、"中"、"😊" 等都是 Unicode 中的抽象字符。|这个东西是抽象的概念。没有实体|
|第二层|编码字符集 (Coded Character Set, CCS)|将字符集中每个字符映射到一个非负整数，即码位 (code point)。|Unicode 为每个字符分配了一个唯一的码位，范围从 U+0000 到 U+10FFFF。例如，"A" 的码位是 U+0041，"中" 的码位是 U+4E2D。|将第一层（抽象）的东西进行编码，以便形成一个规范。每个抽象的字符对应了一个数字|
|第三层|字符编码表 (Character Encoding Form, CEF)|将编码字符集的非负整数值（即码位）转换成有限比特长度的整型值（称为码元，code units）的序列。|UTF-8、UTF-16 和 UTF-32 都是 Unicode 的字符编码表。例如，在 UTF-8 中，"A" 的码元是 0x41，"中" 的码元是 0xE4 0xB8 0xAD。|**这一层关注的是 码位 -> 码元。码位是一个非负整数**，而码元则是有规范的一个/一组整数。即无规范的数字到有规范的数字（数组）|
|第四层|字符编码方案 (Character Encoding Scheme, CES)|将定长的整型值（即码元）映射到 8 位字节序列，以便编码后的数据的文件存储或网络传输。|UTF-8、UTF-16BE、UTF-16LE、UTF-32BE 和 UTF-32LE 都是 Unicode 的字符编码方案。例如，在 UTF-8 中，"A" 的字节序列是 0x41，"中" 的字节序列是 0xE4 0xB8 0xAD。|相较于第三层而言，这里更关注的是码元（数字/数字数组）**如何对应到字节序列上**（如 UTF-16 就涉及到了 BE/LE）|
|第五层|传输编码语法 (Transfer Encoding Syntax)|用于处理上一层次的字符编码方案提供的字节序列，如压缩或映射到更受限制的值域内。|Base64 编码可以将 Unicode 字符的字节序列转换为仅包含 ASCII 字符的文本。例如，"中" 的 Base64 编码是 "5Lit"。|具体传输和使用时，出于各种目的，如压缩、防注入等，进行一层额外的包装（如百分号编码或者 Base64 等）|

### UTF-8 与变长编码
UTF-8 是一种变长编码。

**优点：**

* **兼容 ASCII 码**：ASCII 被很多非全球性编码兼容（如 GB 系列、BIG5 等等），基本字符的内容可以不受编码限制进行查看
* **ASCII 内容编码长度较短**：由于兼容 ASCII 字符，因此对于英文为主的文章来说，字符 / 字节的比值接近于 1
* **易于同步**：当数据发生错误时，可以很容易确定下一个字符的起点重新同步（判定为一个字符开始），从而控制影响范围
* **易于搜索**：一个字符的序列不会包含在另一个字符的序列中，因此基于字节为基础的比较适用于 UTF-8 内容。不需要额外判断是否是字符片段（[WikiPedia: UTF-8 - 设计UTF-8的理由](https://zh.wikipedia.org/wiki/UTF-8#%E8%A8%AD%E8%A8%88UTF-8%E7%9A%84%E7%90%86%E7%94%B1)）

**缺点：**

* **变长编码**：规则比较复杂
* **非 ASCII 编码占用空间较大**：1 字节字符与 ASCII 相同；2 字节字符覆盖了一些语言的字母；其他内容（如 CJK）需要三个字节

|2 字节|​U+0080​ 至 U+07FF​|​110xxxxx 10xxxxxx​|19202048|2048|代码点 U+00A9​（版权符号 ©）的二进制表示是 00000[000 10101001]​，对应的 UTF-8 编码是 110[00010] 10[101001]​，即 0xC2 0xA9​|
|3 字节|​U+0800​ 至 U+FFFF​**绝大部分基础平面**|​1110xxxx 10xxxxxx 10xxxxxx​|63488|65536|代码点 U+4E00​（汉字 "一"）的二进制表示是 [01001110 00000000]​，对应的 UTF-8 编码是 1110[0100] 10[111000] 10[000000]​，即 0xE4 0xB8 0x80​|

### UTF-16 与代理对
[WikiPedia: UTF-16](https://zh.wikipedia.org/wiki/UTF-16)

UTF-16 的基本单位（码元）是两个字节。

||内容|数量|
|-|-|-|
|​U+0000​-U+D7FF​|文本|55296|
|​U+D800​-U+DBFF​|UTF-16 高半区（高位代理 / 前导代理）|1024|
|​U+DC00​-U+DFFF​|UTF-16 低半区（低位代理 / 后尾代理）|1024|
|​U+E000​-U+FFFF​|文本|8192|

其中，U+D800​~U+DFFF​ 是 Unicode 特地预留给 UTF-16 的。

‍

**优点：**

* **大部分非 ASCII 文字内容反而比 UTF-8 节省（尤其是中文）** ：覆盖 0 号平面需要两个字节。两位的 UTF-8 只能覆盖到一部分字母文字（参考 [WikiPedia: Unicode字符平面映射 - 基本多文种平面](https://zh.wikipedia.org/wiki/Unicode%E5%AD%97%E7%AC%A6%E5%B9%B3%E9%9D%A2%E6%98%A0%E5%B0%84#%E5%9F%BA%E6%9C%AC%E5%A4%9A%E6%96%87%E7%A7%8D%E5%B9%B3%E9%9D%A2)），对于剩下的大部分内容都需要至少三位的编码。而 UTF-16 能涵盖除了表情符号和生僻字之外的中文的绝大部分内容。
* **更容易处理**：码元是固定长度的（2 字节），一个字符由 1~2 个码元组成。（由于前导代理、后尾代理、基本平面中的有效字符的码位，三者互不重叠，利于搜索）
* **UTF-16是自同步（self-synchronizing）的**：可以通过仅检查一个码元来判定给定字符的下一个字符的起始码元。

**缺点：**

* **不兼容 ASCII 码**：所有字符至少是两个字节，即 ASCII 字符如 ABCD 41 42 43 44​ 会变成 00 41 00 42 00 43 00 44​
* **对于英文内容（ASCII 内容）比较浪费空间**
* **大小端问题**

‍

**代理对**

对于辅助平面（1~16 号平面）的字符来说，需要两个码元（4 字节）来表达，计算规则如下

1. 码位减去 0x10000​，得到的值的范围为20比特长的 0...0xFFFFF​。
2. 高位的10比特的值（值的范围为 0...0x3FF​）被加上 0xD800​ 得到第一个码元或称作高位代理（high surrogate），值的范围是 0xD800...0xDBFF​。由于高位代理比低位代理的值要小，所以为了避免混淆使用，Unicode标准现在称高位代理为**前导代理**（lead surrogates）。
3. 低位的10比特的值（值的范围也是 0...0x3FF​）被加上 0xDC00​ 得到第二个码元或称作低位代理（low surrogate），现在值的范围是 0xDC00...0xDFFF​。由于低位代理比高位代理的值要大，所以为了避免混淆使用，Unicode标准现在称低位代理为**后尾代理**（trail surrogates）。

‍

**说人话，就是把 U+1xxxx 的字符（**000​​**0 000*****1 00000000 00000000​****​*  **~**  **​**000***1 0000 11111111 11111111*****​**​ **）减去** **​1 00000000 00000000​**​ **后得到的** **​**0000 **0000 000000|00 00000000​**​  **~**  **​**0000 **1111 111111|11 11111111​**​

**然后，前十位前面加上前导代理的 0xd800（​​110110xx xxxxxxxx​**​ **），后十位加上 0xdc00（​​110111xx xxxxxxxx​**​ **）**

**即，如果一个码元是 110110 开头，则一定是前导代理（后面跟第二个码元）；如果一个码元是 110111，则一定是后尾代理（前面跟第一个码元），否则则为普通的码元。**

‍

### 对比
例如，UTF-8 是非常典型的变长编码，一位的情况下，与 ASCII 字符（0~127）兼容；两位、三位、四位等有着不同的规则。

对于一篇纯英语的文章，可能只有极少数的特殊符号（如 emoji、特殊符号），以 UTF-8 的方式存储，其 体积/字符 近似于 ASCII 的 1；但是以 UTF-16 存储则是 2 字节，而 UTF-32 是 4 字节。

而如果是一篇中文文章，显然一个字节（255 种）是不够用的，如果采用 GB 系列，基本上两个字符能覆盖大部分日常需求；而 UTF-8 则以三字节（代码点范围：U+0800​ 至 U+FFFF​）为主。采用 UTF-16 反而会是两字节（更短）。而采用 UTF-32 是四字节

### 渲染过程
一个文件，从硬盘/网络到显示在屏幕上，大概要经过三个过程

$\text{硬盘数据} \quad \xrightarrow{读取} \quad \text{二进制数据} \quad \xrightarrow{\text{编码方式}} \quad \text{字符集码点} \quad \xrightarrow{\text{字体编码表（Cmap）}} \quad \text{字形}$

**a. 读取文件**

将数据以二进制的方式，从外部读到自己应用内

**b. 解码二进制数据**

按照编码方式，从二进制数据到字符集的码点进行处理

**c. 字符集到字体的映射**

先了解一些字体的基础知识

1. **字符的码点（Code Point）** ：每个字符都有唯一的码点。例如，Unicode 中字符 'A' 的码点是 U+0041​，汉字 '一' 的码点是 U+4E00​。
2. **字体编码表（Cmap Table）** ：字体文件中包含一个编码表（通常称为 cmap​），它定义了字符码点到字形索引的映射关系。例如，U+0041​ 可能映射到字形索引 65，U+4E00​ 可能映射到字形索引 2000。
3. **字形（Glyph）** ：字形索引指向字体中的具体字形数据，这些数据定义了字符的外形。

通过编码表，字体可以在内部维护一套字形到不同字符集内同一个『现实中的字符』的映射关系。进而实现一个字体适配不同字符集。

### 如果解码失败……
以 UTF-8 为例，其 m 字节编码规则是，第一字节 m 个 1，然后一个 0，后面 m-1 个字节以 10 开头。如 0xxxxxxx​ 、110xxxxx 10xxxxxx​、 1110xxxx 10xxxxxx 10xxxxxx​ 、11110xxx 10xxxxxx 10xxxxxx 10xxxxxx​。

很容易构造出一些非法字符（如 01000001 01000001 10101011 10101011 01000001​ 里面的 10101011 10101011​）。以 python 为例

```
with open('AAxxA.txt', 'rb') as f:
    binary = f.read()

    try:
        utf8 = binary.decode('utf-8')
        print('utf8: ', utf8)
    except UnicodeDecodeError as e:
        print(e)

    try:
        utf8 = binary.decode('utf-8', errors='ignore')
        print('utf8: ', utf8)
    except UnicodeDecodeError as e:
        print(e)

    try:
        utf8 = binary.decode('utf-8', errors='replace')
        print('utf8: ', utf8)
    except UnicodeDecodeError as e:
        print(e)

```
这里分别用了三个规则

* 默认：报错 'utf-8' codec can't decode byte 0xab in position 2: invalid start byte​
* ignore（忽略错误）：utf8:  AAA​
* replace（替换）：utf8:  AA��A​

‍

在解码失败时，很多语言都可以（且通常会这样）替换成所谓的 菱形问号 �​。如果要具体划分情况，可能会有这些情况

* **解码失败**：二进制数据不符合当前编码方式 如 UTF-8 的编码规范，无法正常解析
* **字符编码非法**：解码后被映射成了一个非法（不存在/保留）的 Unicode 码点

‍

进一步地，如果考虑具体 case

* **选错了字符编码**：一种编码的二进制数据，往往在另一种编码方式下是不合法的（不符合编码规范），强行解码会出现解码失败；哪怕碰巧成功，还有概率映射到一个不存在的码点上
* **被打开的东西不是纯文本文件**
* **部分字符丢失（不完整的编码）** ：如逐字节的打印一个 UTF-8 内容，很可能会因为暂时无法拼凑出一个完整的字符，而显示成 U+FFFD
* **字节序错误**：如 UTF-16 编码下，LE 与 BE 的内容在在另外一种编码往往会导致解析失败（也算是选错编码）
* **传输错误**：目前不是很常见了，但是也有



## 对于前端开发来说
### HTTP 规范以 UTF-8 为主
HTTP 协议各个部分主要采用 UTF-8 编码，现代浏览器在处理请求时会自动地进行编码转换。如 [decodeURICompoenent](https://developer.mozilla.org/zh-CN/docs/Web/JavaScript/Reference/Global_Objects/encodeURIComponent)

在发送请求等情况，缺省配置同样是 UTF-8，因此可以直接发送和接收一个带有中文字符的 JSON 而不需要特别强调编码方式

### JS 内部是基于 UTF-16 存储的
JavaScript 内部是采用 UTF-16 存储的（[MDN: utf-16_字符、unicode_码位和字素簇](https://developer.mozilla.org/zh-CN/docs/Web/JavaScript/Reference/Global_Objects/String#utf-16_%E5%AD%97%E7%AC%A6%E3%80%81unicode_%E7%A0%81%E4%BD%8D%E5%92%8C%E5%AD%97%E7%B4%A0%E7%B0%87)），js 引擎底层中采用的是主机字节序，但是绝大部分情况下不需要考虑这一点。

大多数情况下除了针对字符串做处理可能需要区分码元/码位/多码元字符之外，甚至不需要考虑 UTF-16 的问题

### 面向 UTF-16 的字符串处理
> 字符串基本上表示为 [UTF-16 码元](https://zh.wikipedia.org/wiki/UTF-16)的序列。在 UTF-16 编码中，每个码元都是 16 位长。这意味着最多有 2^16 个或 65536 个可能的字符可表示为单个 UTF-16 码元。该字符集称为[基本多语言平面（BMP）](https://zh.wikipedia.org/wiki/Unicode%E5%AD%97%E7%AC%A6%E5%B9%B3%E9%9D%A2%E6%98%A0%E5%B0%84)，包含最常见的字符，如拉丁字母、希腊字母、西里尔字母以及许多东亚字符。每个码元都可以用以 \u​ 开头的 4 个十六进制数字写在一个字符串中。
正常地写代码就可以——尽管 JS 文件是以 UTF-8 保存的，但是运行时字符串会以**相同字符**的 UTF-16 进行操作。大部分情况下不需要额外考虑

#### 通过 Unicode 构造字符串
使用 \uXXXX 插入一个 0 号平面（四位）的字符（使用两个来插入一个非基本平面字符）

使用 \u{XXXXX} 插入一个 Unicode 字符（可以超过 4 位）

使用 String.fromCharCode 来按照码元输入一个字符串

```
String.fromCharCode(0x0041, 0x4e00, 0xd83d, 0xde02, 0x1f602)
'A一😂'
String.fromCharCode(0x0041, 0x4e00, 0xd83d, 0xde02, 0x1f602)[4] === String.fromCharCode(0xf602)
true
```
使用 String.fromCodePoint 来按照码位创建字符串（但也支持码元）

```
String.fromCodePoint(0x0041, 0x4e00, 0xd83d, 0xde02, 0x1f602)
'A一😂😂'
```
#### 使用 String 读取字符串
使用 str.length 来获取码元长度（即 UTF-16 二进制长度 / 2），例如对于 `x = 'xk😂xk'`，有 `x.length === 6`

使用 str.chatAt 或者中括号来获取按照码元计算的字符，例如有 `x[2] === '\ud83d'`，`x.charAt(3) === '\ude02'`，`x[2] + x.charAt(3) === '😂'`

使用 str.charCodeAt 或者中括号来获取码元索引对应的数字，例如有 `x.charCodeAt(2) === 55357`，`x.charCodeAt(3) === 56834`，`String.fromCharCode(x.charCodeAt(2), x.charCodeAt(3)) === '😂'`

使用 str.codePointAt 来获取按照码位（字符）索引的位置，例如 `x.codePointAt(2) === 128514`，`String.fromCodePoint(x.codePointAt(2)) === '😂'`

JavaScript 没有直接提供按照码位索引获取字符和总长度的功能。

#### 枚举与遍历
****`str.split('')` 可以按照码元拆分。如 `x.split('')` 的产物是 `[ 'x', 'k', '\ud83d', '\ude02', 'x', 'k' ]`（可以理解成每个单位一分割，最小单位是码元）



`str.slice`, `str.substring`, `str.splice` 都是基于码元操作的，如 `x.slice(1, 3) === 'k\ud83d'`

`str.indexOf` 是基于码元操作的，如 `a = 'ab😂cd'`，`a.indexOf('b') === 1`，`a.indexOf('c') === 4`



`String.prototype@@iterator()` 是按照码位（字符）的，即针对 String 的遍历会按照码位进行遍历，因此：

如 `Array.from(x)` 的产物是 `[ 'x', 'k', '😂', 'x', 'k' ]`；`arr = []; for(const chr of x) { arr.push(chr) }` 的产物同样是 `[ 'x', 'k', '😂', 'x', 'k' ]`



至于其他的一些东西，如 `str.split(NonEmptyStr)` 或者 `startsWith` 等，由于单码元字符、双码元字符的码元不重叠，基本不涉及到区分，就按照字面理解来就可以。



**个人总结：**

**如果涉及到『索引』的概念，那么操作对象以码元为主（推测是因为可以直接根据码元（2字节）快速定位到对应的对象上。而如果按照码位操作需要遍历）（例如 [x], charAt, substring 等）**

**如果涉及到『迭代』的概念，由于底层的 @@iterator()​ 是基于码位（字符）实现的，因此通常会以码位为操作对象。（如 for, Array.from 等）**

另外，如果强调了 charCode，则是码元（基础单元）；强调了 codePoint，则是码位（字符）

### JSON \uxxxx 表示方法
尽管网络传输中，带有中文的 JSON 是以 UTF-8 方式传输的。但是 JSON 本身是支持使用 Unicode 字符的。

[RFC 8259: The JavaScript Object Notation (JSON) Data Interchange Format](https://datatracker.ietf.org/doc/html/rfc8259)

```
[{"one": "一"}, {"one": "\u4E00"}, {"xk": "😂"}, {"xk": "\uD83D\uDE02"}]
JSON.parse > [ { one: '一' }, { one: '一' }, { xk: '😂' }, { xk: '😂' } ]
```
JS 中没有内置的 JSON 转换成 \u 的方式，但是解析没有问题。python 使用的是 `json.dumps(obj, ensure_ascii=True)`

JSON 只能按照码元书写，不支持 \u{xxxxx}​ 的语法（尽管实测 js 能解析 JSON.parse('["\u{1f602}"]')​，但是这不在规范中，如 python json.loads​ 报错）

### 变体选择符（Variation Selectors），VS15/VS16
有些 Unicode **符号**，可能既有传统的、字符样式的展示方式，又有 emoji 风格的彩色样式。

比如早期作为符号已经被 Unicode 所收纳，但是随着发展，用户更倾向于丰富多彩、形象生动的表情样式；或者除了作为表情之外也适合书面表达（如 🉑）的情况

比如下面这些，在不同的地方（与应用、系统、字体等有关）可能会有不同的展现样式，例如

```
☃ ☀ ♥ ★ ☎ ✉ ✂ ✏ 🔍 📖 🉑 ☺︎
```
![](/personal-site-mvp/img/doc-placeholder.svg "")
那么，如果想强制按照某种形式展示（假设平台支持）呢？

* **VS15 (U+FE0E)** : 变体选择符 15，通常用于指示字符应以文本形式显示。这意味着字符将以传统的字符形式呈现，而不是作为图形或表情符号。
* **VS16 (U+FE0F)** : 变体选择符 16，通常用于指示字符应以图形形式（通常是表情符号）显示。这意味着字符将以彩色图标形式呈现，而不是传统的字符形式。

### 零宽连接符（Zero Width Joiner, ZWJ）和零宽非连接符（Zero Width Non-Joiner, ZWNJ）
很多 emoji 不是由一个字符组成的。有一种“造字”的方案：ZWJ（Zero Width Joiner）。

ZWNJ 则与表情关系不大，主要个别语言中防止连字

而 ZWJ 则是表示前后两个东西是一体的，需要连起来（如果能连体显示最好，不能的话那么也需要一起选中）

### 结论
**emoji（和 unicode）的各种组合和变形规则有很多。**

**比如一些连体使用 ZWJ，但是也存在不使用 ZWJ 组合的符号（如肤色、区域）；有半角空格、全角空格、不换行空格、零宽空格、连字符（减号）、只有换行才有的软连字符等等**

**还有一些特殊旗帜（如**[英格兰旗](https://emojipedia.org/zh/%E6%97%97-%E8%8B%B1%E6%A0%BC%E5%85%B0#technical)** 🏴󠁧󠁢󠁥󠁮󠁧󠁿 ）并不是使用区域指示符拼接的，而是另一套规则**



总之，如果想完美地支持 emoji 很难

但是如果想不那么突兀的展示�，通常只要处理好代理对问题就可以。（即 `Array.from(x)` 按照真正的字符拆开）。agent 目前就是这么干的
